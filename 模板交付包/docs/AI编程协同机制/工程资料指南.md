# 工程资料指南

本指南把软件工程资料接入现有项目事实体系，供初始化、补齐专题资料或修正断链时使用。它说明正文应该讲清什么、怎样互相连接，不是新的任务流程。优先链接项目已有文档；下面是内容分工，不是每个项目必须创建的文件清单。

## 1. 从业务结果连到实现依据

资料应能沿着这条关系找到原文：

```text
项目目标与用户
  → 业务流程、规则与预期结果
  → 页面/交互或系统输入输出
  → 模块职责、数据与接口契约
  → 实现规则、代码入口与开发示例
  → 测试断言、运行验证与交付边界
```

阶段方案连接“最终要做到什么”和“怎样分步实现”，贯穿上述关系；它不是任务状态流水。仅有文件名、模块目录或命令清单，不能代替中间的业务规则和实现依据。反过来，正文已经在项目原位置讲清楚时，登记其适用范围和章节即可，不再复制一份。

## 2. 各类正文应解释什么

| 内容 | 正文需要回答的问题 | 与其他资料的连接 / 可复用格式 |
| --- | --- | --- |
| 项目全貌 | 为谁解决什么问题；完整业务链是什么；有哪些项目、仓库和模块，各自输出什么、互相依赖什么；哪些明确不做 | [项目总览](项目总览.md)连接产品、模块主文档和当前阶段方案；不复制任务进度 |
| 需求与业务流程 | 谁在什么条件下发起；正常过程和用户可观察结果；业务对象、状态、权限、例外及边界；哪些是已定目标，哪些尚待决定 | [产品设计与契约基线](模板/产品设计与契约基线模板.md)连接每个流程涉及的界面、服务和验收 |
| 产品交互与视觉 | 页面/入口、角色可见性、前后操作关系、加载/空/错误状态；字段与操作对应哪个业务规则；原型、设计图、组件与响应式约束在哪里 | 优先产品正文及已有页面清单、设计资产；无界面的工具或服务不必建立视觉文档 |
| 架构与核心逻辑 | 为什么这样分模块；边界、依赖、输入输出、主链路和关键算法；失败传播与恢复；实际需要的容量、性能、可靠性约束怎样验证 | [技术架构与核心代码逻辑](模板/技术架构与核心代码逻辑模板.md)连接具体数据/API、实现专题和测试；不得只剩目录树 |
| 数据与接口 | 对象及关系、业务标识、字段类型/含义/单位/空值；来源、转换与责任；接口请求/响应/错误/权限；状态和兼容边界 | [数据与接口设计](模板/数据与接口设计模板.md)连接生产方、消费方、实现入口和契约测试；已有 schema/API 文档继续唯一承载 |
| 工程环境与开发 | 正确工作目录、技术栈、依赖、构建/启动/自测入口及适用条件；怎样新增或修改本项目的一类功能 | [工程开发基线](模板/工程开发基线模板.md)组织通用工程入口，具体做法下钻到[专题实现与开发指南](模板/专题实现与开发指南模板.md) |
| 阶段方案与关键决策 | 整体目标怎样拆为可验证阶段；前后依赖、每阶段业务完成标志、暂未实施范围；重要取舍及原因；哪个新决定替代了哪个旧决定 | [阶段方案与关键决策](模板/阶段方案与关键决策模板.md)连接相关需求、设计、实现和验收；工作台仍是活动任务状态所有者 |
| 测试与验收 | 每种业务结果用什么断言证明；正常、边界、异常及权限条件；测试层级、数据、环境、命令、覆盖范围；模拟与真实环境分别证明什么 | [测试与验收基线](模板/测试与验收基线模板.md)连接需求/契约和可运行测试；单次结果留在证据记录 |
| 运行与交付 | 环境、服务、配置来源、依赖和连接入口；构建、部署、健康检查、诊断、回滚如何做；何种现象表示业务恢复 | [运行环境](模板/运行环境与服务器信息模板.md)与[部署发布](模板/部署发布运行手册模板.md)连接测试和业务验证，不把构建成功写成上线成功 |
| 安全与权限 | 数据归属、角色/资源范围、敏感数据处理、风险边界和凭据合法来源；怎样证明不会越权 | [安全与凭据](模板/安全与凭据索引模板.md)与业务/API 原契约互相引用；不保存秘密值 |

这些问题按项目实际需要展开。简单库可以由一份 README 加测试说明承载；有界面的产品可复用页面清单和设计图；复杂服务可拆为数据、API、同步/计算等专题。缺少不适用类别不算缺陷，不能为了数量建立空文档。

### 正文深度的边界

主题已经需要展开时，应让后来的人能追溯一项行为的依据，而不只是知道“有这个模块”。例如“金额如何处理”应能找到业务单位、来源字段、转换规则、空值/异常语义和验证示例；“用户能否看到操作”应能找到角色、资源范围、页面状态和接口权限依据。具体数值、规则和示例来自当前项目，不从模板或别的项目照抄。

文档不是另一套源码。可从 schema、类型、配置或测试直接取得的明细，链接正式入口并补充源码不能解释的业务含义和取舍即可。实际存在的性能、容量、可靠性和安全要求归入相关专题，并说明适用条件与验证方式；不替项目发明指标。

## 3. 接入已有项目与新项目

初始化先核实已有资料的内容和适用范围，再建立[项目事实索引](项目事实/README.md)：

- 已有正式正文：保留原位置，登记可读取的文件或章节、负责的内容及适用模块；同一文件有不同实现分支时分别定位。
- 内容已存在但入口遗漏：只补入口和必要的互相引用，不重新写正文。
- 缺失且当前确实需要：先从用户已定目标、代码、测试或现场核实，补入已有所有者；没有合适所有者时再使用本指南的格式。
- 缺失但暂不影响当前工作：如实写明未整理、待核对或不适用，不虚构完成状态、不以补齐全套资料为开工条件。
- 旧内容与当前决定/现场不一致：区分是目标改变、设计改变还是实现偏差，再按第 6 节纠正。

新项目先有目标、主要业务场景、边界和初步模块关系；其他内容随真实设计和实现逐步形成。已有项目升级不需要重新初始化所有正文，也不默认迁移目录。受管初始化仍使用原有七个资料组和“迁入、登记、暂不处理”选择；本指南只细化这些组里的内容，不新增初始化阶段。

### 索引如何分层

项目索引登记全局主事实和各模块主入口；大型专题可由主文档再链接详细章节。主文档必须讲清模块对整个业务的贡献、当前约定和直接依赖，不能只有一个目录链接。专题、历史和原始证据分开标识，不能把全部文件混成“PM 必读”。

项目已有文档导航可以继续承担分层职责。数据/API 原文只有一个所有者，产品、架构、开发和测试文档各自链接它，不重复维护字段表。

## 4. PM 与执行者怎样读取

身份规则仍是读取范围的依据，这里只说明如何使用这套工程资料：

| 场景 | 读到什么程度 | 把资料用于什么 |
| --- | --- | --- |
| 新 PM 接手 | 按现有接手链读取总览、工作台、项目事实索引和全部当前主事实正文；看懂业务全貌、模块关系、当前阶段方案及已知缺口，不遍历历史和全部原始证据 | 判断主线与阶段目标，识别跨模块依赖；不能只凭工作台标题派单 |
| PM 设计具体任务 | 在已有全局理解上刷新相关需求、阶段方案和直接受影响的契约，必要时下钻专题 | 任务说明带上业务结果、范围、验收和精确原文入口，说明关键上下游关系，不复制整套文档 |
| 执行者开始或遇到问题 | 从任务点名资料开始，沿影响实现/验收的直接依赖读取业务、数据、架构或开发专题；PM 点名不是资料白名单 | 理解为什么这样做，核实当前实现，选择正确实现与验证路径；资料足够后继续任务 |
| 同一任务进入测试/交付 | 读取受影响的验收、环境和发布正文，仍按对应 Action 的职责与授权执行 | 以业务断言核对成果，区分本地通过、部署通过和真实业务可用，不因换方法重建任务 |

需要的资料未知或冲突时先定点调查；只能由用户决定的业务取舍、跨模块方向或真实授权问题，沿现有沟通路径解决。本指南不新增回传、唤醒、等待、验收或暂停规则。

## 5. 在任务中补齐与逐步沉淀

复用已有正文，变化写回原所有者。PM维护全局目标、模块关系、阶段方向和已确定的业务取舍；有写入授权的执行者维护本任务核实的数据/API、实现方法、测试和运行事实。任务相关性不自动扩大写权限。

文档更新与真实变化一起完成：例如接口改变时更新契约及直接消费者引用；一种重复开发方式被验证后补入对应开发专题；一项业务决定明确后补回产品正文并指出受影响方案。没有新知识就不写，不另建沉淀任务、日报或文档审批。

保留三种不同内容，不能互相覆盖：

| 内容性质 | 表达方式 | 不能误写成什么 |
| --- | --- | --- |
| 已确认目标 | 用户要得到的结果、边界、验收及来源 | 不能因实现尚未做到就删掉目标 |
| 已定方案 / 阶段安排 | 选定做法、理由、依赖、每阶段完成标志与尚未实施范围 | 不能冒充已实现，也不能当作旧任务流水丢弃 |
| 当前实现事实 | 代码/配置/测试/现场能证明的实际行为及与目标的差距 | 不能反向替用户决定需求 |

待确认的设计仍注明待确认，不提升为当前契约。阶段设计可以长期保留，但当前谁执行、进行中/暂停和单轮进度仍归工作台；不建立第二份任务状态表。单次测试、部署或失败输出留在原证据位置，正文链接有用证据而不堆日志。

## 6. 纠正旧内容与验证路径

发现冲突先确认适用对象、分支/环境和来源。用户的当前决定裁定目标与取舍；源码、测试和现场裁定实际行为。错误实现不能自动变成正确需求，更新日期也不能单独证明一份文档正确。

在已有授权内修正受影响正文和仍在使用的直接引用，说明替代关系及必要理由。仍有效的阶段设计保留；被替代内容退出当前主入口，需要追溯时链接已有历史位置，不擅自删除。文档移动或拆分时，从项目索引及直接消费者重新走一次读取路径。

本次资料接入按两条标准核对：

1. **内容结构**：相关软件工程主题有正式承载者，正文能说明业务含义、依据和相邻契约；未整理、不适用、待确认和已定方案没有混淆。不按文档数、行数或字段填满率判定。
2. **路径可达**：从总览/项目事实索引能打开正确原文；相对链接按所在文件的目录解析，章节锚点存在；PM 的全局入口和执行者的专题入口都没有断流。代码块里的路径示例或普通文字提及不算已经接通的入口。

可读并不证明文档内容正确，更不证明模型一定能完整交付。涉及项目事实仍需对照来源；上述检查不扩大为模型能力测评或生产验收。
