# 团队任务与协同

本文只在用户明确要求建立、查看、领取、更新团队任务或协同事项，或者说“拉取一下任务和协同”时读取。个人模式、普通项目任务、单个 Worker 内部执行和既有 3.0.9 主链不进入本文。

## 1. 边界

- 团队任务是共享 Git 中可由一名当前承担者完成的结果；可以暂时无人领取。
- 协同事项是多个人围绕一个共同目标分别承担责任；不增加新的身份或状态。
- 任务和协同只使用`进行中 / 已暂停 / 已完成`。
- 当前承担者不是任务锁；其他有权限成员实际接手时更新承担者并继续即可。
- 未完成内容继续保留在共享区，任何有权限成员都可以处理；不建立成员退出、强制交接或人事流程。
- 团队协同只传 Markdown 目标、责任、结果和必要证据入口，不接管业务代码、分支、测试、发布或回滚。

## 2. 团队任务

活动任务保存在`shared/tasks/active/<task-id>.md`：

```markdown
---
id: TASK-2026-001
status: 进行中
owner: git-account
projects: backend-api
collaboration:
updated_at: 2026-08-09
---

# 任务名称

## 当前目标

## 当前预期结果

## 关键调整

## 最终结果与证据
```

记录只保存当前真相和会改变交付的关键调整，不复制调试流水。重复拉取同一编号只更新同一个本地关联任务，不创建第二个 Worker。

## 3. 协同事项

协同主记录保存在`shared/collaborations/active/<collaboration-id>.md`。发起方维护共同目标、当前责任和整体结果；每名参与者只更新`shared/collaborations/responses/<collaboration-id>/<git-account>.md`中的自己的结果。长内容确有消费者时才放入`details/`并由主记录链接。

协同事项本身不是“派单专用”：它也可以表达互相核对、提供资料、共同排障、联合设计和彼此帮助。

## 4. 同步与 Git

用户继续用自然语言让 PM 建立或拉取任务和协同。位于控制仓时，PM调用`scripts/beyond-control.mjs`；位于已经融合的业务项目时，PM按项目根`AGENTS.md`中的`BEYOND-CONTROL-ROOT`定位同一控制仓脚本。不得从全局Skill安装目录或业务项目自身的`scripts/`猜测路径。

- 普通同步默认只汇总当前用户相关内容和少量待领取任务；
- 当前用户按远程平台登录账号确认；不得用`git user.name`或邮箱冒充平台账号。平台CLI无法确认时，只接受用户已经明确给出的Git账号。
- 日常共享记录直接使用控制仓默认分支，不创建 worktree、任务分支或 PR；
- 只精确提交当前团队任务或协同文件；
- 非重叠远端变化可以自动整合；同一文件出现业务语义冲突时停止自动推送，向用户展示冲突文件、双方当前内容和需要选择的差异；
- 不得强制推送、重置或丢弃他人改动。

PM 对普通协同 Git 的例外权限只覆盖`shared/tasks/`和`shared/collaborations/`。项目接入另有一个严格例外：用户单独授权远端Git后，`project-registration`只可同步同一项目的共享登记、最小项目总览和最小事实索引。后续项目事实正文、其他项目文档、业务代码、仓库配置、成员权限和发布资料继续服从原有授权与执行路径。

## 5. 回收

任务或协同完成后，先把仍有长期价值的事实写回对应项目文档，再运行公开归档命令从活动目录移除。协同归档默认同时回收已经进入Git的详情和参与者回复；命令返回`syncPaths`，PM只用该清单精确同步删除项与月度归档。月度归档只保留编号、目标、参与人、最终结果、交付入口和完成时间；详细过程由 Git 历史恢复，不长期累积在活动文档中。
