# 工程开发基线模板

> 本模板记录开发动作可跨任务复用的稳定工程事实。项目值必须来自代码、配置、命令结果、正式文档或用户确认，不得按通用经验补全。

按[工程资料指南](../工程资料指南.md)复用已有 README、贡献指南、模块说明和开发脚本，不为使用本模板复制正文。通用工程基线回答“在这个项目怎样正确开发”，专题业务规则和详细实现回到原模块文档；章节按当前项目需要选用，不是每任务必填清单。

### 3.1 一项功能落到哪些代码

以项目里已有、可核验的一条代表性功能为例，给出“页面/调用入口 → 业务逻辑 → 数据或外部适配 → 返回/状态 → 测试”的代码位置与作用。没有某层就略过；关键在于开发者知道规则放在哪里、共享逻辑从哪里复用、哪些层不能反向承担责任。

补充生成代码与源文件、公共组件与业务组件、配置与运行数据的边界。已有更详尽的模块指南只链接相关章节，不为了这张入口表重新压缩原文。

### 3.2 扩展与接入位置

针对项目真实支持的扩展，说明新增一种实现需要接入的工厂/注册表/路由/配置/迁移或测试位置，复用的抽象与限制，以及最小可参照实现。明确扩展点允许改变什么、不允许改变哪些既有契约；项目没有扩展机制时不为模板新增机制。

具体处理算法、代码示例、边界样例和失败诊断按[专题实现与开发指南模板](专题实现与开发指南模板.md)在原专业位置展开，避免只列路径而没有使用说明。

## 4. 工程约定

| 类型 | 正式约定 | 自动检查或事实来源 | 例外处理 |
| --- | --- | --- | --- |
| 命名/格式/类型/错误/日志/配置/迁移 |  |  |  |

说明约定背后的工程效果，并链接真实代码或检查器。例如错误如何从内部转换为调用者可判别的结果、日志如何关联一次请求且不暴露敏感内容、配置缺失怎样表现、生成物如何更新。不要单写“遵守规范”，也不把通用风格偏好当成已存在的项目约定。

项目有数据迁移或外部契约时，指出变更源、兼容读写边界和相应验证入口；运行部署参数及秘密管理回到运行/安全原文，不复制凭据或现场配置值。

## 5. 依赖、构建、运行与自测

| 动作 | 命令或入口 | 工作目录 | 前置条件 | 成功断言 | 副作用 |
| --- | --- | --- | --- | --- | --- |
| 安装/构建/运行/lint/单测/集成测试 |  |  |  |  |  |

不能运行的命令必须写明替代证据和未覆盖风险，不得把“看起来正确”写成已验证。

命令说明应足以在受支持环境复现：所需输入或样本、配置项名称及安全取得方式、期望退出码/产物/业务断言，以及是否触及网络、服务或共享数据。模板登记命令不授予执行权限，也不把本地构建、模拟测试和真实链路验收混为一谈。

复用现有测试、fixture和开发工具，给出局部功能应跑哪个最小入口、修改共享边界时哪些直接消费者受影响；不要把全仓测试或依赖安装写成每次默认动作。

### 5.1 可复用示例与常见故障

开发示例应引用实际可用的短实现及其测试，解释输入为何这样构造、关键规则是什么、期望输出与失败断言是什么。脱离代码的示意片段须明确标为示意，不能称为已运行样例。

对已有现场反复出现、确有证据的故障，记录“可见症状 → 最有区分度的定位点 → 正常与异常结果 → 已知修复或处理边界”，链接对应模块或运维原文。没有证据时不堆砌排障猜测，也不在这里保存单次日志流水。

## 6. Git 与工作区约定

| 项目 | 约定 | 事实来源 | 动作前核验 |
| --- | --- | --- | --- |
| 主分支/任务分支/正式工作目录/正式目标源码基线确认入口/既有 worktree现场/生成物 |  |  |  |

BEYOND 不创建或推荐 worktree；既有 worktree只作为当前 Git现场记录。同一目录内，任务拥有路径和副作用不重叠时可以并行编辑、测试；共享对象只串行受影响动作。同一 Git工作区的索引、HEAD和历史动作串行，每次精确暂存任务路径。`add/commit/push/merge/清理`分别服从任务授权；本基线不能预授权 Git 写操作。

## 8. 维护规则

- 缺失项先从项目事实自动调查；只有工程取舍或调查后仍不明确的事实才引导用户确认。
- 当前动作所依赖的真实契约、写入边界或环境事实未明时，先定点核清该项；文档未填满、尚未补写或无关章节缺失本身不是开发门禁。
- 已有可信记录时只刷新命中的版本、模块、命令或 Git 现场，不重复扫描整个仓库。
- 单次任务的提交、diff 和测试结果留在正式任务线程或 Git，不复制进本基线。
