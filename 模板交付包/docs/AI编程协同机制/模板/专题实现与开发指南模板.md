# 专题实现与开发指南模板

> 用于需要保留实现深度的主题，例如一条数据处理链、某类适配器、复杂业务计算或关键页面交互；不是每个功能都要新建的说明书。按[工程资料指南](../工程资料指南.md)优先扩展已有模块设计、开发指南或 README，内容足够时保留其原入口。

## 1. 专题范围与使用入口

说明本专题解决的业务结果、适用模块/版本、使用者，以及明确不负责的边界。给出对应产品规则、架构主链路、数据/接口契约和代码/测试的具体章节或入口。

区分目标行为、已定实现方案、当前代码行为和已验证范围；不把示意代码当成可运行实现，不把待接入扩展点写成已有能力。注明关键来源、核验方式和什么变化会使本指南失效。

## 2. 一次实际处理怎样完成

围绕一个代表性输入，解释从触发到结果的完整路径。复杂步骤可以展开，简单模块无需照填所有项：

1. **触发与输入**：入口、输入对象及其来源、前置状态、范围和需要保持的上下文。
2. **识别与校验**：怎样定位业务对象、验证输入和权限；无效输入在哪里被拒绝，调用者如何区分。
3. **处理顺序**：读取、转换、计算、选择、合并或调用的次序，以及次序对正确性的影响。
4. **写入与输出**：持久化/事务/状态边界、响应或事件何时产生，后续消费者从哪里取得结果。
5. **失败与继续**：真实可能的失败点、是否已有副作用、失败停留位置、恢复或重试条件及可判别信号。

每个关键步骤对应实际代码符号或计划中的明确落点，并说明数据来自哪里、规则由谁维护、结果交给谁。只有“先校验、再处理、最后返回”不足以指导开发；需要写出该项目的具体条件和保证。

## 3. 关键规则、算法与理由

对改错会改变业务结果的规则逐项展开：

- 输入的有效域、业务不变量和期望输出；计算公式、优先级、排序或状态条件是什么。
- 选择该算法/结构的原因，实际约束是什么，哪些替代已排除及为什么。
- 边界和异常如何处理：未知与空、单位/时间转换、重复、乱序、并发等只写该专题实际涉及的情形。
- 与共享契约的对应关系；规则改动会影响哪些调用者、派生数据或用户表现。

必要时保留短伪代码，并在旁边解释不变量与失败语义；源代码能直接复用时链接真实实现，不复制一份会过时的大段代码。技术动作不能替代业务解释，例如“捕获异常”“更新游标”还需说明捕获后对结果的影响、游标代表什么。

## 4. 样例与可验证断言

优先使用项目已有去标识样本、fixture或单元测试。选一组能解释关键规则的正常输入和必要边界输入，给出中间值或关键分支、期望输出、应保持的不变量和不应发生的副作用。

可以采用以下表达结构，填入真实规则后才是项目样例：

```text
输入样例：来源、字段和值、对象初始状态
命中规则：指向上文具体规则
处理结果：精确输出、状态变化及应有/不应有副作用
验证入口：测试位置或可复现操作
证据层次：设计示例 / 自动测试已验证 / 实际链路已验证
```

样例中的输入、代码和断言应互相一致；不能用“输出正确”代替预期值。运行过的结果注明环境和覆盖范围，未执行的样例明确写未验证，不虚构命令输出。

下面仅演示展开深度，**不是项目默认规则，也未在项目执行**。假设某项目已经确定“标签必须是字符串，去除首尾空白后不能为空，保持大小写”，则说明可以写成：

```text
normalize_label(raw):
  非字符串 → 返回 invalid_type，不写入
  value = 去除 raw 首尾空白
  value 为空 → 返回 empty_label，不写入
  否则返回 value，由调用方按原契约决定是否写入

断言："  Alpha  " → "Alpha"；"alpha" → "alpha"
断言："   " → empty_label；null → invalid_type
```

这里的关键不是函数名，而是输入约束、处理边界、错误可判别及副作用责任都能被检查。实际项目应以已有真实规则和实现替换整个示意，不把示意变成新增需求。

## 5. 开发与扩展指南

### 5.1 复用位置和最小改动面

解释已有公共实现、业务实现、适配层和调用方怎样协作，推荐参照哪一个实际例子及它为何适合。列出本主题需要修改的职责位置和保持不变的共享边界，不把全目录树当作开发说明。

### 5.2 接入一种受支持的变化

当项目确有扩展能力时，用一种当前支持的变化说明：

- 新实现需要满足的接口、输入/输出、不变量和错误行为。
- 应放在什么位置，通过什么已有路由、工厂、注册、配置或组合入口接入；没有注册步骤就不虚构。
- 哪些代码可复用，哪些规则不能在新实现中重复或覆盖，什么情况不适合使用这个扩展点。
- 相应测试、样本和消费者需要怎样更新，如何证明新分支被实际调用且既有行为保持。

示例是工程做法，不授予修改无关模块、安装依赖或操作环境的权限；不得为了模板中出现“扩展点”而新建框架。

### 5.3 调试与验证入口

给出项目已有的局部命令/测试/调试入口、工作目录、前置输入、配置名称、成功断言和副作用。涉及网络、服务或共享数据的入口明确标识，运行仍服从当前授权。

开发环境的完整安装与构建约定链接[工程开发基线](工程开发基线模板.md)对应的项目原文，不在每个专题重复一套。修改共享边界时指出需要一起核对的直接消费者，不自动要求全仓回归。

## 6. 常见问题与定位线索

只收录已知且与本专题直接相关的问题，以“症状 → 最有区分度的检查点 → 正常/异常判别 → 已知处理与边界”说明。日志字段、指标或数据位置应能对应第 2 节的某个步骤，而不是一列无顺序的排障命令。

无法从证据确定原因时写未知；不把猜测列为已知故障。恢复服务、迁移数据、发布回滚等实操回到现有运维原文，不在这里创造另一份操作流程或保存秘密。

## 7. 变化与关联维护

影响业务规则、字段语义、接口或架构边界时，更新其唯一原文及本指南的对应实现/样例/测试引用；不会影响外部行为的实现调整只维护实际受影响内容。对仍有工程价值的旧实现说明保留适用版本和替代入口，不让读者误用历史方案。

尚未实施范围、关键选择理由和阶段依赖可以保留在现有方案中，参考[阶段方案与关键决策模板](阶段方案与关键决策模板.md)；当前谁在做、逐次执行记录和临时排错留在当前任务，不以文档篇幅证明任务完成。
