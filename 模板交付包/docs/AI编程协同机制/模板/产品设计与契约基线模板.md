# 产品设计与契约基线模板

> 本模板记录可跨任务复用的产品、体验、设计和共享契约事实。它不是需求流水，也不能用候选设计覆盖真实产品、代码或当前验收。

按[工程资料指南](../工程资料指南.md)复用已有需求、产品说明、页面设计和契约原文。本模板提供内容深度，不要求另建同名文件或每次填写全部章节；已有正文足够时只补精准入口和本次真实变化。无界面的服务、脚本等可略过页面与视觉内容，保留调用者流程和业务结果。

同一节中有不同事实层次时分别写明：**目标**是希望得到的结果，**已定方案**是有来源的产品取舍，**当前实现**是已核验的实际行为。尚未实现的已定方案仍保留其范围与依据，不能因为现状不同就悄悄改成现状；“设计已定”也不等于实现、发布或验收通过。

项目总览或项目事实索引维护本文件入口；本文件只记录可复用事实、来源、核验和失效触发，不维护能力状态或当前任务进度。需求拥有“用户要得到什么”，技术设计拥有“由什么实现、为什么这样做”，可分别建文件或在既有正文分节互链。任务只引用适用章节、修订与本轮验收范围；一个任务结束不关闭仍有效的模块需求和设计。

### 2.1 业务对象、规则与功能范围

围绕实际用户结果说明，不只列功能名：

- 谁在什么条件下处理什么业务对象，对象归谁、哪些角色可以查看或改变它；同名概念的定义、口径和边界是什么。
- 用户动作成立的前置条件、产生的结果和业务副作用；互斥、优先级、计算口径、时间范围及例外如何处理。
- 哪些行为属于当前范围，哪些只展示、只读、使用模拟数据或尚未实施；“入口存在”与“业务动作可用”分别说明。
- 规则的确认来源、当前代码或产品证据、尚未决定的取舍，以及影响的上下游。

一条规则应能推导出可检查的结果。可按“条件 → 允许/拒绝的动作 → 对象变化 → 用户可见结果 → 例外”写短段落；不把“支持管理”“体验友好”当成详细规则。

## 3. 主流程与体验约定

| 流程/页面 | 入口 | 正常路径 | 空态/失败态 | 权限或可见性 | 验收方式 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

若已有正式设计稿或组件规范，只登记唯一链接、版本和适用范围，不复制整份材料。

对本次需要的可交互原型，登记可运行位置/启动方法、适用修订、关键操作、用户已确认范围，以及模拟数据与真实能力的区别。开发者应能从这里实际打开并操作，而不只看到截图；需求、原型和唯一契约互相指向，同一范围发生变化时更新原入口。原型可体验、真实实现和业务验收分别记录，不用原型获认可代替后端或组合验收。

### 3.1 页面与用户流程

需要界面时，在原有页面清单或流程正文中落到具体入口：页面/路由、服务的用户结果、所需角色、前后页面关系、关联功能和正式设计位置。页面是否已接真实数据、是否只有静态展示须有当前证据，不能由设计稿推断。

对影响结果的流程展开：

1. 从哪里进入，进入时带哪些上下文、默认值或已有选择；没有前置数据时怎么办。
2. 用户看见什么、操作什么；筛选、编辑、提交、取消、返回和再次进入分别保留或丢弃哪些状态。
3. 每个动作读取或改变什么业务对象，何时算成功；重复提交、中途离开、权限变化和服务失败时呈现什么、允许怎样继续。
4. 正常、空、加载、部分成功、失败、不可用等实际存在的状态如何区分；提示文案应说明事实和可执行下一步。

只展开该产品实际有的分支，不为通用完整性虚构功能。复杂流程用步骤或状态图，比把全部行为塞进一行表更清楚。

### 3.2 页面内容与字段责任

对有业务含义的展示或输入字段，说明它回答什么问题、来源对象和接口、转换/计算位置、空值与未知的显示语义、校验规则、谁维护真实值。对本轮相关的筛选和排序，说明可选值或动态选项的产生规则、默认值、组合关系及计算口径；契约已有具体定义时引用对应章节，正文只补业务含义和使用方式，不重复抄写枚举或公式。不能只写“支持筛选”“沿原规则”，却没有可定位的具体依据。跳转和操作按钮同样对应真实能力与权限，不把前端展示逻辑写成数据生产责任。

字段类型、来源映射和接口参数的详细定义回到唯一契约正文；本节保留页面字段与契约章节的对应关系。需要补充深度时参考[数据与接口设计模板](数据与接口设计模板.md)，不复制第二份字段字典。

**贯通示例（仅示范写法，不是项目默认需求）：**假设用户已确认目录查询需要“地区与关键词同时生效，保存重开保留条件”；已核实地区目录提供省市选项，现有接口按地区名称包含查询。

| 内容 | 如何接起来 |
| --- | --- |
| 业务规格 | 省市选项引用现有目录；选省后展示所属城市，切省清除不再适用的城市；地区和关键词同时约束结果，保存重开恢复同一条件。这些交互作为示例方案列明，不由“支持地区筛选”几个字代替 |
| 技术衔接 | 页面选项的代码值与接口接收的名称值分别说明，引用原契约中的映射、组合规则和兼容方式。名称包含不等于行政区精确匹配；若用户需要精确匹配，列明服务端缺口与方案，不用改标签掩盖差距 |
| 验收例子 | 用同时满足地区与关键词、只满足其中一项的数据检查结果；切省后旧城市不残留；保存重开后的条件与结果语义一致。验证业务链路，不只验证下拉框能选 |

真实任务用自己的已定规则替换示例，标明当前实现与目标的差异；Demo中的模拟选项、临时默认值或前端计算只是调查依据，不能未经核实就变成正式业务规则。已确认方案内的局部修复只补受影响内容，不因此重写整份设计。

### 3.3 交互、视觉与非功能约束

已有设计体系时复用并指出适用版本；没有时，只对本产品需要稳定复用的约定写正文：

- 页面信息层级、布局区域、主要/次要操作、列表与详情的结构；布局和组件如何支持用户决策。
- 排版、间距、色彩语义、组件尺寸及选中/禁用/错误等状态；链接到实际设计稿、组件或样例截图，并说明它们是目标还是当前表现。
- 涉及移动端、键盘操作、可访问性、长文本或不同分辨率时，写明适用条件和预期行为，不照抄通用指标。
- 响应速度、结果新鲜度、容量、可用性等若影响体验，写业务容忍界限、测量条件和来源；未知指标保留未知，不替用户设定承诺。

| --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |  |

已有正式数据字典、API/schema或状态契约时，只登记适用对象、用途和原文章节入口，不复制第二份正文；没有独立文档时，在现有产品或架构正文中维护即可。

契约至少能把“用户结果 → 页面或调用入口 → 业务字段及责任 → 接口/状态 → 观察断言”连起来。对跨模块边界，说明生产方提供什么、消费方可以依赖什么，未提供或失败时不能假装成功；实现细节分别回到架构和专题实现原文。

## 5. 决策与待确认

| 决策项 | 候选事实与来源 | 用户确认或裁决 | 决定理由/替代关系 | 影响范围 | 写回位置 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  | <候选/已确认/待核验/已废弃> |

调查得到的候选事实不能直接写成用户偏好。只有影响业务结果、体验取舍或共享契约且无法从现状确认时，才进入引导问题。

业务任务开工前，在已有决策记录中注明本次需求与技术设计的路径/章节、适用修订、用户确认来源、批准实现范围及剩余未决项。模型审查意见及采纳/未采纳理由链接原审查记录，不把审查通过当用户批准；重大变更沿用此处补充替代关系，不另建审批文件。普通实现细节不重复确认，具体流程由`task-design`负责。

## 6. 验收基线

| 验收项 | 通过标准 | 证据方式 | 不覆盖范围 |
| --- | --- | --- | --- |
|  |  |  |  |

验收描述要能实际观察：给定哪类用户、对象和前置状态，进行什么操作，页面/响应/持久化状态应怎样变化，哪些副作用不应发生。对本次相关的正常路径、规则边界和失败恢复分别写出断言，并链接现有用例、测试数据构造方式或人工复验入口。

例如“给定无查看权限的调用者，读取受保护对象时不返回对象内容”是断言结构示例，不是项目默认权限规则。项目正文应使用自己的业务规则、输入、预期值和证据；设计稿符合、接口测试通过、真实用户链路通过分别记录，不能相互替代。

## 7. 维护规则

- 首次使用先调查现有产品、代码、数据和契约，再请用户确认剩余取舍。
- 事实来源或核验为空的判断标为候选或待核验；只处理当前动作真正依赖的不确定性，不因无关章节未填而停工。
- 已有可信记录时只刷新受影响流程、契约和验收，不重做全量设计。
- 当前任务进度、临时讨论和测试流水留在正式任务线程；仍约束后续实现的重要方案、取舍理由和替代关系保留在原专业正文或[阶段方案与关键决策](阶段方案与关键决策模板.md)的相应章节。
