按[工程资料指南](../工程资料指南.md)原地复用现有架构、模块设计和核心实现说明；下列内容可以是现有文档的章节，不要求为每类另建文件。架构要解释系统如何完成业务结果及为何这样划分，不止是一张技术栈和目录表。

### 2.1 系统上下文与模块边界

说明用户或外部系统从哪里进入，哪些业务结果由本系统负责，哪些交给外部依赖。模块划分应能回答：每个模块拥有什么业务对象/规则/写入权，公开什么调用或事件边界，依赖什么，以及明确不负责什么。

仓库、代码模块、进程和部署单元并不必然一一对应。有多仓、多进程或共享组件时指出对应关系、入口和依赖方向；环境地址和实时实例留在运行事实，不在此硬编码。边界图只有在比文字更清楚时使用，并附关键边的含义。

### 2.2 结构选择与约束

对真正影响实现的选择，解释业务约束、候选方案、采用理由、代价和失效条件，例如职责分层、读写模型、外部适配、同步/异步或存储选型。已有决定只链接其正文，避免在此维护第二套决策状态。

性能、数据新鲜度、可用性、隔离或容量要求写出适用负载和测量口径；没有现状证据或已定目标时不编造指标。约束用于解释结构，不以“可扩展、高性能”替代具体设计。

## 3. 核心链路

| 链路 | 触发入口 | 关键步骤 | 输出结果 | 失败时看哪里 |
| --- | --- | --- | --- | --- |
|  |  |  |  |  |

核心链路优先写决定项目成败的主流程，例如登录、查询、同步、采集、任务调度、支付、发布或数据处理。

对需安全修改的链路，在对应正文展开一次完整流转：

```text
业务触发及前置状态
→ 入口校验与对象识别
→ 读取的事实及其来源
→ 核心规则/转换/状态变化
→ 写入与提交边界（如有）
→ 返回、事件或下游可见结果
```

每一步对应真实代码入口或设计位置，并解释失败发生在提交前还是提交后、调用者会看到什么、是否允许重试以及如何确认已完成。并非每条链路都有持久化、事件或重试；只保留实际存在的步骤。

涉及跨模块数据流时指出生产者、消费者、顺序和一致性窗口，尤其是列表与详情、源数据与派生结果、缓存与持久化各自读哪份事实。不能用“调用服务”“同步数据”略过决定正确性的转换和边界。

这里记录“必须理解才能安全改代码”的逻辑，不写普通函数说明。

每段关键逻辑宜包含：输入有效域与不变量、算法或规则次序、边界条件、选择理由、输出保证、对应代码与测试。必要时保留短伪代码或真实实现片段的精准链接，解释为什么如此而不是逐行复述代码。

按真实链路选择说明去重/幂等、并发冲突、排序/分页、时间或单位转换、重试与终止等内容；不默认套用某种通用算法。例如涉及检查点时，需要说明检查点代表“已读到”还是“已成功提交”、失败后的续跑位置及避免遗漏的断言，而非只登记一个字段名。

专题算法、接入一个新处理器或扩展一类能力所需的细节可原地独立成节，篇幅或消费者不同再使用[专题实现与开发指南模板](专题实现与开发指南模板.md)；本节保留主链路入口和关键约束。

## 10. 维护规则

- 本文件只记录稳定架构和核心代码逻辑，不记录执行流水。
- 当前任务、谁在做、做到哪一步，写入当前工作台或任务卡。
- 当前实现与本文冲突时核验事实，由有对应写入授权的执行者修正专业正文；涉及整体目标或跨模块业务取舍时由PM收敛。实现偏离已确认目标不自动改变目标。
- 实施反馈只影响阶段细节时，回改阶段设计或任务卡；影响主链路、模块职责或关键技术路线时，回改本文。
- 不得凭空补全技术栈、模块职责、核心链路或代码入口；没有真实代码、既有文档或用户确认支撑时，写“待核对”。
