# 复杂业务设计文档模板

> 本模板用于需要跨模块、跨执行线、跨检查周期，或需要被开发、测试、发布独立消费的复杂业务设计。它只提供正文格式，不保存项目事实，也不定义路径、授权或生命周期；实际落位与回收以[项目文档入口](../00-模板入口.md)为准。

只保留当前设计真正需要的章节。不要复制空栏目，不要用模板完整代替事实调查。

| 最终处置 | 活动 / 已完成 / 已取消 / 已被替代 |

## 1. 给用户看的设计说明

### 1.1 做成什么

用不懂代码也能判断的语言说明：

- 当前要解决的问题是什么；
- 完成后用户能看到、做到或得到什么；
- 明确不做什么；
- 现在仍然没有发生什么变化。

### 1.2 实现路径

按实际先后说明从现在到完成要经过哪些步骤，每一步解决什么、依赖前一步什么结果。先写业务流程和各部分作用，再在后文给代码位置；不要只列框架、服务、接口或英文缩写。

1. `<第一步及其结果>`
2. `<第二步及其依赖>`
3. `<第三步及其完成条件>`

### 1.3 测试路径

说明怎样证明设计真正成立：

- 用户主流程怎样验证；
- 失败、权限、边界和重要状态怎样验证；
- 哪些旧功能可能受影响，需要怎样回归；
- 需要什么测试环境、数据或人工检查；
- 什么证据出现时才算通过，哪些范围本次不证明。

具体命令和技术入口放在第5节，本节先让用户理解“怎么证明”。

### 1.4 发布路径

说明实现和测试通过后怎样到达用户：

- 进入哪个目标环境；
- 发布前要确认什么；
- 按什么顺序投放和检查；
- 失败时在哪里停止、怎样回退；
- 何时只能说代码完成，何时才能说用户可用；
- 本任务不含发布时，后续由谁依据哪个正式入口继续核对。

### 1.5 需要用户决定的事项

只保留调查后仍无法确定、确实会改变业务结果或方向的最小决定项。能从项目事实和现场调查的内容不要变成用户技术问卷。

## 3. 方案与落地结构

### 3.1 主流程

写清入口、关键步骤、状态变化、成功结果和失败收敛。需要图时图后仍要有一段普通语言解释，不能只交付图。

### 3.2 模块、文件与复用

| 设计/契约项 | 目标模块、入口或文件类型 | 复用的现有能力 | 必须保持的行为/不变量 | 明确不改 |
| --- | --- | --- | --- | --- |
|  |  |  |  |  |

### 3.3 业务与技术契约

| 对象或契约 | 用户可见语义 | 输入/输出或状态 | 失败/权限/边界 | 唯一正式位置与版本 | 消费者 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

已有正式API、schema、事件或设计稿时只登记链接、版本和本次影响，不复制第二份原文。

### 3.4 数据、安全与运行边界

只写本次实际涉及的内容：

- 数据所有者、关键不变量、事务/并发/幂等和部分失败；
- 信任、认证授权、隐私和秘密边界；
- 外部调用、异步、超时、取消、重试和资源上限；
- 性能、容量、可观测性和故障定位；
- 兼容、迁移、双写、回滚和临时代码退出条件。

## 5. 测试与发布执行入口

### 5.1 测试入口

| 验收项 | 测试层级/环境/数据 | 正式命令或人工步骤入口 | 可观察通过标准 | 不覆盖范围 |
| --- | --- | --- | --- | --- |
|  |  |  |  |  |

本节登记计划和正式入口，不伪造尚未执行的测试结果。实际证据由测试动作或任务证据保存。

### 5.2 发布与回滚入口

| 阶段 | 目标环境/制品 | 正式发布或检查入口 | 停止条件 | 回滚入口 | 责任与证据 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

本节登记计划和入口，不保存秘密，不把设计中的发布路径冒充实际发布。真实发布仍需运维现场、权限和当前证据。

## 6. 验收追溯

| 用户目标/业务决定 | 事实或约束 | 设计项 | 实现位置 | 测试/验收入口 | 发布后可观察结果 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |
