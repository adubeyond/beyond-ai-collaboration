# BEYOND 项目协同入口

本文是项目文档链入口，不是 Codex 初始化首入口。若项目根有 [../../AGENTS.md](../../AGENTS.md)，应先读它，再由它路由到本文。本文只负责文档链内的冷启动、身份路由、动作路由和数据归位。详细协同规则见 [机制/03-多智能体协同机制.md](机制/03-多智能体协同机制.md)。

## 0. 输出方式

所有智能体对用户回复时，先说结论，再说依据和下一步。默认不输出长字段清单，不复述内部机制名，不把英文状态码当正文。

- 面向用户：用中文短句，例如“可以做”“需要补证据”“不能直接创建这个文件”。
- 面向表格：可保留机器状态码，便于任务流转，但不要放在用户正文里。
- 面向交接：只在需要跨智能体接手、验收或回写时列出必要字段。
- 面向阻塞：说明卡在哪里、已经确认什么、谁来决定下一步。
- 身份称呼：正文用“PM 总控、执行者”。设计、开发、测试、运维是动作技能；后台助手是主智能体的助手实例，不作为身份入口。
- 用户称呼：若项目无其他约定，默认称呼用户为`老板`。若本轮漏掉这个称呼，只能视为弱异常信号，不能单独据此判断上下文丢失。

除非用户要求审计过程，否则不要逐项列出“已读、任务来源、输入材料、写入边界、证据位置”等字段；这些内容写入当前工作台或交付包即可。

接手场景默认先按最小路径读入，再给轻回执，不先堆长字段：

```text
接手确认：
- 模式：
- 当前主线：
- 当前边界：
- 当前下一步：
```

这四项必须来自当前工作台、项目总览或被当前工作台点名的项目内入口，不能把“下一步先去读文档”当成合格回执。

只有出现称呼遗漏、当前主线含糊、当前边界含糊、当前下一步失真、与动态事实冲突、直接跳执行，或用户明确要求复核读入链时，才升级补：

```text
补充校验：
- 进入路径：
- Git 状态：
- 写回位置：
- 当前校验码：
```

长对话里若怀疑上下文漂移，不重复整套接手回执，先做一次最小自检：

```text
上下文自检：
- 你怎么称呼用户：
- 当前主线：
- 当前边界：
- 当前下一步：
```

若这四项里有两项以上与当前工作台或被点名的项目内入口不符，先重新读取最小路径，再继续。

## 0.1 反驳机制

AI 不得为了顺着对话而默认认可用户、PM、执行者或后台助手的判断。只要出现“意图合理但判断失真”的情况，必须先纠偏，再决定是否执行。

固定判断顺序：

1. 用户最新目标，决定我们想做什么。
2. 当前代码、Git、测试、环境结果，决定现在真实是什么。
3. 机制边界、写入边界、验收标准，决定现在能不能这样做。

若三者冲突，事实和门禁优先于口头判断；AI 必须明确指出冲突，不得先附和再改口。

必须提出异议的典型情况：

- 用户、PM 或执行者把“未验证”说成“已完成”。
- 用户判断与当前代码、Git、测试或环境结果冲突。
- 用户要求直接跳过门禁、回收、验收、证据或文件创建登记。
- 执行方案会明显扩大风险、污染主线或破坏既定边界。
- 用户明确要求“这是故障，必须解决”，但当前回复还停在环境解释、平台解释或现象描述，没有继续下钻到本地可验证根因。

反驳时用三步短句：

1. 先说结论：哪里不能直接认可。
2. 再说依据：冲突事实、测试结果或门禁依据。
3. 最后说替代：现在可执行的下一步。

若只是偏好不同、不是事实冲突，AI 可以提出建议，但不强行反驳。

处理故障时还有一条固定要求：

- 不得把“环境限制、平台限制、当前会话未加载、入口暂不可用”直接当终点。
- 只要当前工作区、本地配置、文件内容、缓存或状态库还能继续排查，就必须继续定位到可验证根因层。
- 只有完成本地链路排查后，仍能证明问题落在外部系统且当前无控制权时，才能明确记录为外部阻塞。

## 1. 启动读入

新线程、新智能体或新任务接手时，只读：

1. 项目根 `AGENTS.md`；若不存在，再从本文开始。
2. 本文。
3. [项目总览.md](项目总览.md)；项目级接手或需要稳定背景时优先读取，若当前工作台已足够说明本轮任务边界，执行者可先不展开。
4. [当前工作台.md](当前工作台.md)。
5. Git 状态；非 Git 仓库记录原因。
6. 当前工作台明确指定的机制、模板或项目事实。

不得默认读取历史资料、样例事实或未明确指定的资料。

若项目总览显示是多项目或项目群场景，`当前工作台.md` 默认先承担总控当前真值面：先用它判断总主线、当前阻塞、待接力事项和 PM 下一步，再决定是否下钻某个子项目。

真实项目或子项目可以保留自己的文档入口，通常是项目内的 `docs/README.md`。它不是 Codex 初始化首入口，但应作为该项目线的文档首入口，至少回答六件事：

1. 先看哪份当前真值面
2. 先看哪份关键规则或决策面
3. 当前任务主面是谁
4. 跨线或跨项目接力看哪里
5. 发生变化后优先改哪里
6. 以该项目线身份接手后，默认先做什么

没有这份项目内入口时，PM 首轮必须在当前工作台里把这些信息点名出来，不得让新线程自己在子项目文档树里摸索。
项目内入口的作用，不是只告诉 AI “我理解了项目”，而是把它直接带到该项目线的当前默认动作上。

若该项目线存在重复高频场景，项目内入口可以再补一层`场景化阅读顺序`，但只作为快捷读法，不替代当前真值面、任务主面或接力面。默认只保留 3 到 5 个高频场景，例如：

- 第一次接手
- 准备开始开发
- 准备跨线接力
- 准备测试或验收
- 准备运维或发布

每个场景只回答两件事：

1. 先读哪几份最小必要材料
2. 读完后默认进入什么动作

不要把场景化阅读顺序写成第二套臃肿目录地图，也不要让它覆盖当前工作台给出的动态主线判断。

## 2. 缺失处理

| 缺失项 | PM | 执行者 |
| --- | --- | --- |
| 项目总览缺失 | 根据用户最新指令创建最小项目总览 | 不自行补项目目标，要求 PM 提供 |
| 当前工作台缺失 | 创建最小当前工作台，再进入判断 | 不自行定义主线，要求 PM 提供任务、边界、验收和写回位置 |
| Git 不可用 | 记录不可用原因 | 记录不可用原因 |

最小当前工作台必须包含：

```text
状态快照：更新时间 | 项目/子项目范围 | 项目阶段 | 当前状态 | 红黄绿 | 协同模式 | 活跃任务 | 阻塞任务 | 最近证据 | Git 状态
本轮工作定义：当前主线 | 本轮目标 | 主要矛盾 | 本轮边界 | 验收标准 | 禁止事项 | 待澄清点 | 下一步
```

若是多项目或项目群场景，再补一块最小子项目摘要：

```text
子项目状态摘要：子项目 | 当前主线 | 当前状态 | 当前活跃任务 | 当前阻塞 | 需要他线配合什么 | 最近证据 | 下一步
```

## 3. 身份路由

| 身份 | 触发 | 默认写入 |
| --- | --- | --- |
| PM | 接手、规划、拆分、验收、回写 | 当前工作台 |
| 执行者 | 领取任务、实现、局部修改 | 当前工作台任务行或 PM 指定位置 |

若用户已明确指定身份 Skill，以 Skill 为准；若身份无法判断，先澄清，不得猜测执行。

## 4. 动作路由

动作路由是任务控制实例可组合调用的执行模块，不是四道独立审批。任务授权已经允许完整路径时，实例应按当前事实自动切换动作；前置条件不足时，优先在任务内调查或设计补齐，只有触发红灯才暂停。

| 动作 | 进入条件 | Skill |
| --- | --- | --- |
| 设计 | 目标、边界和需要冻结的决策可识别 | `$task-design` |
| 开发 | 当前轮设计或契约已足以约束实现，写入边界清楚 | `$task-dev` |
| 测试 | 有可验证对象和验收标准；证据路径可在本轮建立 | `$task-test` |
| 运维 | 任务授权已覆盖目标环境、验证和回滚；未覆盖时只做发布前检查 | `$task-ops` |
| 回收 | 已有结论、证据和存放位置 | PM 回写到当前工作台或记录区 |

动作 Skill 不替代身份 Skill。任务控制实例只能在授权范围内触发动作；任务按预先登记的`自动收口 / PM 证据验收 / 用户授权`方式结束，不默认全部等待 PM。

## 5. 数据归位

| 内容类型 | 写入位置 |
| --- | --- |
| 项目目标、业务边界、稳定背景 | [项目总览.md](项目总览.md) |
| 状态快照、本轮工作定义、调度表 | [当前工作台.md](当前工作台.md) |
| 总设计 | 当前工作台点名的唯一正式设计文件；没有正式设计文件前，先在当前工作台保留摘要 |
| 阶段设计 | 默认先写 [当前工作台.md](当前工作台.md)；一行装不下且跨两个以上检查周期或需要独立验收时，展开任务卡或任务明细 |
| 共享契约、字段表、状态机、接口约定 | 当前工作台点名的唯一正式契约文件；不得并行存在多份口头版本 |
| 通用规则、门禁、协同机制 | `机制/` |
| 任务卡、交接包、记录格式 | `模板/` |
| 技术架构、核心代码逻辑、主链路、关键契约 | 当前工作台点名的技术架构或核心代码逻辑事实文件；可使用 [模板/技术架构与核心代码逻辑模板.md](模板/技术架构与核心代码逻辑模板.md) 作为格式来源 |
| 服务器、域名、端口、服务、环境变量、权限边界 | 当前工作台点名的运行环境或服务器事实文件；可使用 [模板/运行环境与服务器信息模板.md](模板/运行环境与服务器信息模板.md) 作为格式来源 |
| 发布冻结、构建、部署、发布后验证、回滚记录 | 当前工作台点名的发布记录或生产运行记录；可使用 [模板/发布与回滚模板.md](模板/发布与回滚模板.md) 作为格式来源 |
| 日常巡检、故障接单、恢复动作、运维复盘 | 当前工作台点名的运维记录或 `记录/生产运行记录/`；可使用 [模板/运维巡检与故障处理模板.md](模板/运维巡检与故障处理模板.md) 作为格式来源 |
| 任务详情、长过程、长证据 | `记录/任务明细/` 或 `记录/生产运行记录/` |
| 已完成、已废弃、已转出的历史任务 | `记录/历史任务回收/` |

回写时不要把所有变化都往当前工作台里堆。先按变化类型分流，再决定写哪里：

- 状态变化：优先更新当前真值面或当前工作台状态快照。
- 决策变化：优先更新唯一正式设计文件、正式契约文件或决策落点。
- 执行推进：优先更新任务主面、任务卡或任务明细。
- 阶段切换：优先更新项目总览、阶段设计落点或当前工作台的本轮工作定义，并判断是否启动回收。
- 跨线或跨项目且需要他线明确执行：优先更新正式接力面、正式契约或已存在的正式协作文档，不得只留在聊天里。
- 稳定软件工程事实：优先更新当前工作台点名的技术架构、运行环境、发布流程或运维巡检事实文件；当前工作台只保留摘要和链接。

`模板/` 下的文件只提供格式，不直接承载真实项目事实。真实项目事实必须写入当前工作台、项目总览或 PM 点名的具体项目事实文件。只有本轮任务明确是“修改模板本身”时，才允许修改模板源文件。

审查这些事实文件时，必须分开判断：

1. 模板能不能承接这类事实。
2. 当前项目是否已有真实材料、命令结果、日志、Git、测试或用户确认支撑。

没有真实支撑时，只能写“待核对”或“模板层可承接”，不得写成“当前项目已满足”。

同类事项优先更新现有正式文档，不重复新建多份口径相近的文件。

只要本轮改变了下面任一类内容，就不得只停留在聊天里，必须回写至少一处正式文档：

- 当前主线、当前阶段或当前总判断
- 本轮优先级、开发顺序、执行顺序或下一步安排
- 项目之间、执行线之间的边界与职责
- 字段口径、接口范围、共享契约、状态枚举或数据语义
- 同步策略、接力策略、验收口径或发布口径
- 目录结构、正式入口、任务主面或正式落点

普通确认、闲聊、未改变项目事实的短对话，不强制回写。

## 5.1 阶段切换门禁

当项目从一个大阶段切到下一个阶段时，PM 不得只写“本阶段完成，下一阶段开始”。必须先完成阶段切换判断：

1. 上阶段采纳什么、不采纳什么。
2. 哪些任务、接力、测试单、派工单已经完结并进入历史索引。
3. 哪些事项仍是当前阻塞、上线风险或下一阶段前置条件。
4. 下一阶段的正式主稿、项目内入口和任务主面分别是什么。
5. 暂停新增什么，允许继续推进什么。
6. Git 状态是否支持阶段切换，尤其是当前分支、协作线、hook 或提交门禁、新建正式文档、源码、配置是否已纳入跟踪或明确说明原因。

以上六项缺任一项，只能判为“阶段切换准备中”，不得直接分派越过缺口的下一阶段动作；不受缺口影响的调查、回收和准备工作仍可在授权内继续。

阶段切换时，当前工作台只保留阶段摘要、当前风险、下一阶段入口和待办；上阶段长过程、旧测试单、旧派工单、旧协同单进入历史回收或项目原有历史索引，不再占用默认读入链。

多子项目场景下，不要求每个子项目文档名完全一致，但 PM 首轮必须能稳定映射出四个面：

1. 当前真值面：回答当前主线、当前状态、当前阻塞、当前下一步。
2. 当前任务面：回答当前在做什么、每条任务是什么状态、谁在做、等谁。
3. 接力面：回答跨线或跨项目事项由谁发起、谁接收、现在卡在哪一步。
4. 历史面：回答已完成过程、旧证据和旧阶段结论去哪里找。

如果一个子项目里同一份文档长期同时承担“当前真值 + 当前任务 + 历史仓库”三种职责，PM 应先判为读入风险，再决定是补映射关系还是拆分承载，不默认直接扩文档。

当前任务面还必须满足一条硬要求：本轮只能有一个主任务面。

- 可以存在补充面，例如阶段路线、运行待办或局部证据索引。
- 但 PM 首轮必须能明确指出“现在到底先看哪一份任务面”。
- 若旧项目把当前任务散在多份文档里，PM 先指定一份主任务面，其他只作补充，不先重建文档树。

接手旧项目、历史项目或尚未完全模板化的项目时，PM 首轮先做一次最小“四面映射”：

- 哪份文档临时承担当前真值面
- 哪份文档临时承担当前任务面
- 哪份文档临时承担接力面
- 哪份文档临时承担历史面

先把映射说清，再决定是否需要补正式工作台、接力表或任务面；不要一上来重建整套文档。

业务状态、实例状态和 PM 判断不要混写成一层：

- 业务状态用于任务流转：`待排期 / 可执行 / 进行中 / 已暂停 / 候选完成 / 已完成 / 阻塞`
- 实例状态用于资源责任：`待领取 / 执行中 / 等待事件 / 待回收 / 已关闭 / 失联`
- PM 判断用于采纳结论：`采纳 / 限定采纳 / 退回 / 阻塞`

`验证中`只表示当前技能为测试，`待验收`迁移为业务`候选完成`。任务领取、恢复、暂停和候选完成通过统一生命周期事件进入 PM 单写控制面；实例已释放时，不能因为业务仍待裁决而写成运行中。

当前工作台只保留当前结论、调度状态、证据位置和下一步。PM 判断是否回收时，先看它是不是还只服务“当前要做的事和当前判断”，不先看行数。

出现以下任一情况时，必须在当轮启动回收：

1. 任务已完成、已阻塞、已废弃或已转出，且当前主线不再依赖它的完整过程。
2. 文件创建登记表、验证与证据索引或调度表中，最近结论已经覆盖旧过程，但旧过程仍在继续占据当前入口。
3. 新线程读到当前主线前，必须先穿过旧判断、旧证据或旧任务组。
4. 当前工作台已经不再只服务“当前动作”，而是在替历史记录充当长期仓库。

以下只作为预警信号，不是单独的硬触发：

- 当前工作台明显变长，例如超过 120 行。
- 任务授权与调度表中已完成、已废弃或已转出的任务明显堆积，例如超过 10 行。
- 读到当前主线前，需要连续跳过两屏以上旧内容。

回收时，已完成任务组进入 `记录/历史任务回收/`，长过程进入 `记录/生产运行记录/` 或 `记录/任务明细/`；当前工作台只保留阶段摘要、证据位置和遗留项。

## 6. 文件创建门禁

新建文件前必须满足：

1. 任务授权与调度表或本轮工作定义允许创建。
2. 已写清文件类型、目标路径、创建原因、谁会用、入口位置和回收方式。
3. 代码、测试、配置文件必须落在任务写入边界内。
4. 文档、证据、记录文件必须进入本入口定义的位置。

未登记存放位置的新文件不得创建。临时草稿必须在 PM 验收前删除、并入正式文件或登记到记录区。

若项目是 Git 仓库，新建正式文档、源码、配置、跨项目通知或规则文件后，PM 验收前必须确认它已经被 Git 跟踪，或记录为什么暂时不能纳入。未跟踪的关键文件不得被 README、当前工作台、任务主面、接力表或聊天当作正式入口引用。

用户不需要按字段填写“上游入口、下游去向、索引位置”。PM 必须根据用户意图自行翻译成内部登记项；只有无法判断时，才用自然语言追问一个最小问题。

标准项目能力事实文件走[项目事实索引](项目事实/README.md)的确定路径。正式任务实际使用某项能力且对应文件不存在时，PM 直接在原任务授权和文件创建登记表中补齐文件类型、路径、使用者、入口和持续保留方式；任务控制实例按对应模板创建并继续原任务，不把内部文档路径或是否建立项目能力档案再次转问用户。用户明确禁止文档写入、目标越出项目或要求另建非标准文件时，仍按普通文件创建红灯处理。该规则不授权 Git 暂存、提交、推送，也不授权业务源码之外的任意文件。

PM 或已获文件创建授权的任务控制实例，新建文档前必须先完成文档地图判断：

- 这个文档解决什么问题。
- 谁会读取或使用它。
- 为什么当前工作台、接力表、记录区或已有文档放不下，或说不清这个问题。
- 建成后链接挂在哪里。
- 用完后保留、合并、归档还是删除。

以上判断由控制面或任务控制实例从上下文完成，不要求用户逐项填写。若缺少关键信息且无法推断，形成红灯并只追问一个最小问题，不得先建文档。

跨线协同默认使用当前工作台的任务授权与调度表、接力与验收表、证据索引和记录区，不得另建协作文档。任务授权明确允许新增协作文档时，由任务控制实例完成文档地图判断并同步入口；未授权时形成红灯。

跨项目或跨线正式接力默认走当前工作台的“接力与验收表”。来源线发起后，接收方必须在本地当前工作面或任务面回写接收状态和下一步；不能只有发起，没有接收。

多任务并行时，默认先扩当前工作台里的任务授权与调度表、接力与验收表、验证与证据索引，不先扩文档。只有“当前工作台一行装不下、任务会跨两个以上检查周期、且需要独立验收”同时满足时，才允许展开任务卡。

同一任务默认只允许一个主展开文件：任务卡、任务明细、生产运行记录三选一。已有任务卡时，不得再为同一任务并行新建总结文档、协作文档、第二份任务说明或平行规则文档；接力、证据和临时判断继续回到当前工作台。

设计产物也遵守同一套规则：

1. 总设计不默认新建多份设计文档。默认每个项目或子项目只保留一个主设计落点；未满足独立展开条件时，先写当前工作台摘要。
2. 阶段设计默认先写当前工作台的本轮定义、任务行和接力表；只有装不下且需要独立跟踪时，才展开任务卡或任务明细。
3. 共享契约必须只有一个正式版本。前后端、执行者、测试或后台助手不得各自保留一份平行字段表或平行接口说明。
4. 实施反馈若只影响当前阶段细节，回改阶段设计落点；若影响总边界、主链路、模块划分或阶段路线，必须同步回改总设计落点。
5. 当前工作台只保留“这轮设计结论、正式落点、变更摘要和下一步影响”；不替设计文档充当长期仓库。

## 7. 进入完成前

进入完成状态前必须确认验收、证据、任务约定的收口结论、Git 状态、正式回写、终态事件和回收位置都已记录。授权内动作与证据齐全但尚未完成约定裁决时，业务状态只能是`候选完成`；仍在测试时保持业务`进行中 + 当前技能=测试`；出现红灯时为`阻塞`。自动收口任务满足全部条件后不再额外等待 PM 逐项采纳。

涉及真实软件项目交付时，还要确认相关项目事实文件是否足够支撑后续接手：

- 改动影响核心代码链路时，对应项目事实文件里的技术架构或核心代码逻辑已更新，或记录了暂不更新原因。
- 改动影响服务器、服务、端口、环境变量或权限时，对应项目事实文件里的运行环境信息已更新，或记录了暂不更新原因。
- 改动影响分支策略、协作线、hook、提交节奏、发布基线或待归属文件时，项目总览、当前工作台、发布记录或对应项目事实文件已更新，或记录了暂不更新原因。
- 改动涉及发布、部署、回滚时，对应发布记录或生产运行记录已更新。
- 改动涉及线上巡检、故障恢复或运维风险时，对应运维记录或生产运行记录已更新。

## 8. Skills 故障优先排查顺序

当多个 Skills 使用同一套规则，但只出现“部分可用、部分不可用”时，先按下面顺序排查，不要先改文案、改命名或归咎用户不会触发：

1. 文件编码是否一致，默认要求 `UTF-8 无 BOM`。
2. 文件头是否干净，例如 frontmatter 前面不能混入隐藏字符。
3. `SKILL.md`、`agents/openai.yaml`、目录名、frontmatter `name` 是否一致。
4. 安装副本、切换副本、源码副本是否同步一致。
5. 当前工具会话是否重新加载，缓存、状态库或加载链路是否只收进了部分 Skills。

同类配置下若只有部分 Skills 可用、部分不可用，优先按“编码、文件头、格式差异、缓存、加载链路”排查，不先把问题解释成纯平台限制。
