# 多智能体协同机制

本文只定义多智能体特有的协同门禁、交付边界和冲突处理。通用反驳机制、文件创建门禁、回收判断和表格字段格式，以 [../00-模板入口.md](../00-模板入口.md)、[../当前工作台.md](../当前工作台.md)、[../模板/任务卡模板.md](../模板/任务卡模板.md) 和 [../模板/智能体交接包模板.md](../模板/智能体交接包模板.md) 为准。

## 1. 运行架构

本机制不是逐环节审批流。运行时分为四个责任面：

| 责任面 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 用户授权面 | 业务目标、真实生产权限、不可逆与高成本决定 | 不填写内部任务字段，不逐步批准普通动作 |
| PM 控制面 | 把目标变成任务授权、分配资源、处理红灯、接收证据和收口 | 不逐技能审批，不长期执行代码、测试或部署等待 |
| 任务执行面 | 由一个任务控制实例负责完整状态机，组合技能和协作实例交付业务结果 | 不改变目标、授权边界或正式契约 |
| 事实证据面 | 当前代码、Git、测试、环境、正式契约和运行记录 | 不以聊天摘要替代一手事实 |

`任务控制实例`是当前业务任务的主执行者实例，不是新身份或新 Skill。它负责让任务从可执行持续推进到可验收结果，并汇总协作实例的输出。PM 只有在 PM 自身治理任务中才兼任任务控制实例。

默认由一个执行者实例组合设计、开发、测试等技能连续推进。只有并行收益、写入隔离、专业独立性或环境隔离确实需要时，才增加协作实例。只多开对话、线程或 CLI，不等于协同。

## 2. 反驳与纠偏

多智能体协同时，任何实例都不得因为“对方身份更高”而放弃纠偏。只要用户、PM、执行者或后台助手的判断与当前代码、Git、测试、环境结果冲突，就按 [../00-模板入口.md](../00-模板入口.md) 的反驳机制处理，并回写到当前工作台的阻塞、待澄清点或协同故障处理中。

## 3. 身份、技能与实例

身份是责任模板，技能是当前动作，智能体实例是实际运行的对话、线程、CLI 或工具实例。

协同必须区分四层：

| 层级 | 回答什么 | 示例 |
| --- | --- | --- |
| 任务 | 要交付什么业务结果 | 小程序接口交付 |
| 身份 | 谁对调度或执行负责 | PM、执行者 |
| 技能 | 当前使用什么专业动作 | 设计、开发、测试、运维 |
| 实例 | 哪个真实对话在执行 | `worker-test-01` |

任务按业务交付物建立，不按技能数量拆分。PM 和执行者可以组合动作技能；切换技能只更新实例当前动作，不改变身份、任务 ID 或任务控制责任。

PM 身份一经当前对话建立，就跨轮保持到 PM 任务结束或用户明确要求角色切换。用户说`开始开发`、`修复`、`跑测试`、`测试通过后发布`、`部署`或`提交`，默认是在要求 PM 派单或推进既有任务，不会把当前 PM 实例切成执行者。只有用户明确要求“本对话切换为执行者/由本对话亲自执行”，并且 PM 控制权已经移交或不再需要保持可用时，才允许变更身份；必须先写清新的身份、控制权去向和写入边界。

PM 可以读取动作 Skill 来编译任务包、验收和红灯条件，但只写当前工作台、任务授权、接力、裁决和完成事件等控制面；不得修改业务源码、测试、运行配置或任务实现稿，不得运行实现、完整测试或发布命令，也不得替任务创建或占用分支/worktree、执行 Git 写操作、操作服务器、服务或业务数据。准备调用工具前若目标不是 PM 控制面，立即停止本实例执行，改为冻结任务包并创建或唤醒唯一正式任务线程；不得用内部协作子智能体冒充任务控制实例。

| 类型 | 默认职责 | 权限边界 |
| --- | --- | --- |
| PM 总控 | 判断主线、建立任务授权、分配实例、处理红灯、验收或自动收口 | 同一主线默认一个，不逐动作审批 |
| 执行者 | 领取任务；被指定为任务控制实例时，负责在授权内跑完整状态机 | 不改变目标、边界和正式契约 |
| 后台助手 | 调研、巡检、验证、历史回收、联调辅助 | 不是身份入口，默认只读，必须登记和回收 |

### 3.1 正式任务线程与协作子智能体

平台对象类型是任务控制契约的一部分，不能只登记一个自建实例名：

| 对象 | 定义 | 可以做什么 | 不能做什么 |
| --- | --- | --- | --- |
| PM 正式线程 | 用户当前可见、用于方向、授权、红灯和收口的 PM 对话 | 创建/唤醒正式任务、消费事件、更新总工作台 | 承担业务实现或长期等待执行 |
| 正式任务线程 | 平台创建、用户可在任务列表中看到并可直接进入纠偏的独立任务/线程 | 成为唯一任务控制实例，连续组合设计、开发、测试和运维 | 被内部 agent path、自建 UUID或普通文档路径替代 |
| 协作子智能体 | 由 PM 或任务控制实例在当前对话内部派生的辅助实例 | 只读调查、独立测试、审查或边界明确的局部实现 | 成为业务任务控制实例、直接收口业务、替代用户可进入的任务对话 |
| CLI/外部执行器 | 有稳定定位、明确工作区和回报目标的外部实例 | 在授权范围内承接正式任务或局部动作 | 没有用户入口、实际定位和持久回报目标时冒充正式任务 |

用户明确要求`启动新任务`、`另开任务`、`后台执行`，或在 PM 任务包已冻结后要求`开始开发/测试/发布`时，属于创建或唤醒正式任务的授权。在 Codex 桌面端，新业务任务使用平台正式任务创建能力（`create_thread`）并进入左侧任务列表；继续既有业务任务时优先向已登记 thread ID发送消息或恢复，不重复创建。普通判断、设计讨论、审查回答或尚未冻结方向的问题不自动创建任务。

PM 创建正式任务前先解析目标项目；项目任务使用平台登记的项目 ID，并按任务 Git 隔离事实选择本地工作区或平台 worktree。只有用户或正式任务事实明确要求从现有工作树/分支开始时才指定 starting state，不为方便擅自复制脏现场。创建成功后立即登记平台返回的真实 thread ID、对象类型、项目、环境、PM thread ID和回收条件；内部`/root/...`路径、协作 agent ID和自建 UUID只能作为辅助定位。

正式任务创建能力不可用、返回失败或无法得到真实 thread ID时，任务保持`可执行 + 待领取`并形成资源红灯；不得静默降级为协作子智能体。协作子智能体只有在正式任务已经存在、局部目标和回报位置明确且实例预算允许时才能启动，结果直接回到正式任务控制实例。

分派时不得只写角色名。若已确定实例，写智能体实例 ID，例如 `worker-frontend-01`；若还未启动具体执行者，写 `待领取`，由执行者领取任务时生成本轮实例 ID 并交 PM 登记。

智能体不是无限制常驻资源。只要没有当前任务、没有待回写结果，或结果已按任务收口方式采纳，就应进入回收判断，而不是继续挂在右侧或实例表里。

PM 默认保持调度能力，不长期承担源码全量扫描、实现、完整测试或部署等待。PM 处理新任务授权、红灯异常、资源冲突和最终责任；普通阶段切换、边界内修复、证据回写和已预授权发布不需要再次请示 PM。

平台不允许任务控制实例直接派生时，任务控制实例默认继续关键路径或取得等价证据，不为形式分工强行增加实例。只有验收硬性要求隔离、且平台只有 PM 能启动实例时，任务控制实例才提交包含用途、输入、输出去向和回收条件的一次完整请求；PM 按既有授权只做一次资源启动，助手直接向任务控制实例回报。阶段路由、修复接力、交回原测试实例和日常消息中继不转给 PM；协作实例回写后默认自行释放，平台要求 PM 操作关闭时只消费终态回收事件。无法直接回报、仍不满足隔离或资源不足时形成资源红灯，不用 PM 代路由伪造闭环。

## 4. 任务授权与领取

任务授权与调度表是默认任务池，也是任务授权面。PM 先登记业务结果和授权范围，指定或等待一个任务控制实例领取；后续协作实例均服从该任务控制关系。

正式派单的顺序固定为：冻结唯一任务包与 PM 控制目标规则 → 创建或唤醒正式任务线程 → 登记平台 thread ID和运行环境 → 完成领取/启动握手。任务简报必须作为正式任务初始输入，不把 PM 完整聊天历史直接复制过去。创建后的新任务包装中，平台自动注入的`source_thread_id`才是该任务的直接 PM 控制目标；当前 PM 自己收到的上游`source_thread_id`属于委派祖先，不能继续抄给子任务。创建前无法取得当前 PM thread ID时写`以新任务包装中平台注入的 source_thread_id 为准`；只有平台不提供直接父线程定位时才使用任务授权中预先指定的持久事件收件箱。

### 4.1 派单前意图编译

PM 先把用户输入区分为`已明确业务口径 / 可从项目事实调查 / 必须由用户决定 / 互相冲突`。可从项目入口、代码、配置、Git、测试和正式文档获得的事实，由任务控制实例调查并回写，不转成用户问卷；没有事实依据时，不得自行发明技术方案、阈值、数据规模、环境或验收指标。

PM 必须区分`继续/优化现有方案`与`重新规划/重新设计/换方案/推倒重来`。用户明确要求重新规划时，旧方案中的技术路径、阈值和下一步失去本轮默认决策权，旧进度只作背景证据；既有安全边界、不可逆限制和当前运行事实仍然有效。完成接手最小回执后，只读取足以识别对象、安全边界和正式入口的最小事实，不汇报或改写旧方案来替代新方向确认。

若用户同一轮没有给出新方向或业务结果，PM 只问一个问题：`这次重新规划，您最想改变原方案的哪一点，或希望新方案首先解决什么结果？`答复前不得修改正式文档、任务状态、任务控制实例归属、终态、主技术路径、阈值或预算，也不得派单。用户已经给出新方向时直接编译，不重复追问；旧事实只用于安全、兼容义务和证据约束。

问题对象、故障标签或症状描述只用于定位重规划对象，不自动等于完整业务结果。例如`重复发送`、`性能差`、`重做某模块`仍可能缺少会改变验收的业务口径。若“什么算问题、什么必须保留、成功或失败如何判定”的不同答案会改变业务结果、数据行为或验收，PM 不得自行补成任务口径；只问当前一个最影响方向的问题。只有可观察结果与关键业务边界已经足以冻结验收时，才按“用户已明确新方向”继续编译。

以下冲突未消除前不得进入`可执行`：

- 连续做到完成，同时要求某个里程碑后停止等待确认。
- 要求上线或发布，但目标环境、真实授权或回滚边界没有从当前事实成立。
- 业务结果、明确不做、验收、读写边界和终态条件无法同时成立。

存在方向性冲突时，PM 只问一个会改变自动路径的最小问题，答复后沿原派单继续。没有冲突时，未知实施细节写`任务控制实例自行发现并回写`，不因字段尚未预填而反复找用户。

若是多项目或旧项目场景，PM 还必须在当前工作台先点名该执行线本轮先看的`任务主面`。执行者先按当前工作台领取，再下钻到被点名的任务主面；不能自己在多份文档里猜哪一份才是当前任务入口。

执行者领取规则：

- 用户不需要知道实例 ID。
- 用户声明执行线时，优先领取同执行线的可执行任务；未声明时，领取优先级最高的可执行任务。
- 已写具体实例 ID 的任务，只能由该实例继续；写 `待领取` 的任务可由当前执行者领取。
- 领取 `待领取` 任务时，生成本轮实例 ID，并在交付包中要求 PM 回写登记。
- 多个任务同时匹配时，按 `P0 -> P1 -> P2 -> P3` 处理；同优先级先处理无阻塞且下一步明确的任务。
- 业务结果、写入边界、验收证据或红灯条件缺失且无法从正式事实推断时，不得开工。
- 没有匹配任务时，不得自行发明任务。

未知的接口细节、实现方案和测试方法可以列为任务内待解决事项，由任务控制实例先调用设计技能收敛；不得因为这些实施细节尚未生成，就把整个业务任务退回 PM。

任务授权与调度表的一行就是执行者的默认任务来源。外部交接包只补充复杂上下文，不能替代任务授权。PM 只写“下一步由执行者处理”不算分派；若没有可领取任务行，执行者必须说明无法领取。

### 4.2 项目能力初始化与任务领取握手

项目首次接入时，PM 在[../项目总览.md](../项目总览.md)建立稳定能力结果台账，只登记已知入口和结果，不先扫描全项目；当前初始化责任和阶段写入[../当前工作台.md](../当前工作台.md)的 PM 单写协调表。若首个任务仍停在方向门禁，用户回答前不写正式文档；方向冻结后、正式派单前由 PM 建立台账骨架和当前需要的协调行，任务控制实例领取后再补稳定事实。每个任务只初始化自动路径实际涉及的项目与规则、设计、开发、测试、Git、运维、安全凭据、文档与事件能力；已确认稳定入口跨任务复用，易变事实按动作刷新。

未初始化不是拒绝使用 Skill，而是该 Skill 的初始化模式。任务控制实例先从根规则、项目入口、代码、配置、脚本、测试、Git、环境和既有正式文档定点调查，不把可调查事实转成用户问卷；只把业务取舍、真实权限和调查后仍无法确定的内容编译成一个最小决策簇。问题必须给出候选事实、来源、影响和`确认 / 纠正 / 不知道，请继续调查`路径，不让用户从空白技术问卷开始。

PM 只识别项目能力缺口、在动态协调表冻结唯一初始化责任任务和任务授权，不亲自调查业务实现。其他任务复用已确认部分、登记依赖或继续不受影响的动作，不重复向用户提问。初始化责任不产生第二个业务任务控制权：实际调查、项目事实文件写回、核验和解锁仍由原业务任务控制实例完成。

项目事实标准实际路径由[../项目事实/README.md](../项目事实/README.md)预先定义。对应文件尚不存在时，PM 在原业务任务包和文件创建登记表中直接写明标准路径、类型、使用者、入口和持续保留方式，并授权任务控制实例按对应模板创建；这是项目内部能力初始化动作，不要求用户再次选择文档路径，也不扩大业务源码、Git、环境、生产或数据授权。用户明确禁止文档写入或路径越出项目时才红灯。

用户答复后，任务控制实例把事实来源、用户确认、现场核验、适用范围和刷新触发写回唯一项目事实文件和任务主面。达到当前动作最低条件后可在本任务上下文中解锁并沿同一任务继续，不等待 PM 回执；任务实例用事件回传证据，PM 消费后更新动态协调行和项目总览稳定结果。入口或现场变化时只把命中的能力转为`需刷新`，不重新扫描全项目。真实代码、Git、测试、服务和环境结果优先于旧文档。

任务从授权到运行必须完成一次可核对的实例登记；登记分为创建回执登记与阻塞领取两种模式：

1. PM 写入任务版本、`待领取`实例位、PM 控制目标和允许的工作区/Git 边界；此时业务状态最多为`可执行`。
2. PM 通过平台正式任务创建能力建立唯一线程，且任务、版本、项目/工作区和非冲突边界已经冻结时，创建回执中的真实 thread ID、项目和环境直接完成实例登记；任务包写`领取登记=创建回执完成（非阻塞）`。平台创建同时启动任务回合，worker 直接进入授权内动作，不再发送`claimed/started`唤醒 PM。
3. 来源不明、平台或用户直接恢复、重复实例、共享写入未隔离，或任务包明确要求登记后才能动作时，任务包写`领取登记=阻塞 claimed/resumed`。实例发送事件后等待一次登记结果；PM 只核对信封和冲突并立即回源。登记后任务直接执行，不再补发`started`。
4. 没有真实实例定位时不能冒充已领取。创建失败、阻塞领取失败、实例失联或无法确认唯一工作区时，任务保持`可执行/已暂停`并形成资源黄灯或红灯；不得同时登记两个任务控制实例。

PM 创建前必须把稳定业务任务 ID、任务版本和执行回合写进任务提示；新任务默认`v1/回合1`，不得把平台 thread ID当作业务任务 ID，也不得要求 worker从未暴露的平台元数据猜值。取得真实 thread ID后，创建回执证明正式实例已分配并开始运行。满足唯一任务、唯一线程、项目/工作区和授权边界冻结条件时，创建回执就是唯一领取登记事实，不再追加`claimed/started`；缺少任一条件时使用阻塞领取。阻塞事件必须来自真实正式任务线程，不得改用 collaboration mailbox。

正式任务输入包装中的直接`source_thread_id`是 worker 的 PM 投递目标。创建回执登记型任务只在`red/shared_conflict/paused/candidate_completed/completed/failed`或必须提前协调其他任务时向该目标投递；普通进展留在任务线程。阻塞领取使用该目标发送`claimed/resumed`；如果提示没有暴露自身 thread ID，事件写“以本消息到达 PM 时平台包装注入的 source_thread_id 为准”，PM 以来源 thread ID登记，不允许 worker 自造 UUID。终态事件发送成功后 worker立即释放，不等待 PM 回执。

暂停任务恢复走快速路径：只读取原任务行、最后已消费事件、任务主面当前结论，以及 Git、服务、数据和授权等本轮必须刷新的易变事实。原业务结果、边界、验收和稳定能力入口未变化时，不重新规划、不展开历史、不扫描全项目，也不重复询问已经确认的业务口径。恢复改变目标、边界、验收或真实权限时，才回到意图编译或红灯裁决。

## 5. 任务授权门禁

任务进入`可执行`前必须能够判断：

```text
任务 ID/任务版本 | 业务结果/明确不做 | 业务状态 | 任务控制实例/待领取 | 执行回合/实际会话定位 | 正式依据或设计责任 | 读写边界 | 自动执行路径 | 动作初始化包 | 允许操作、实例与修复上限 | 验收标准和证据 | 黄灯通知条件 | 红灯停止条件 | 收口方式 | 任务内纠偏 | 写回位置/PM 控制目标
```

字段不要求用户逐项填写。PM 应先从项目总览、当前工作台、代码、Git、正式契约和用户最新目标中推断；只有影响安全执行且无法推断时，才追问一个最小问题。

`动作初始化包`只覆盖自动路径实际会调用的动作。项目与规则、设计、开发、测试、Git、运维、安全凭据、文档与事件必须分别引用稳定结果台账和动态协调责任中的正式入口、写`不适用`或写`任务控制实例自行发现并回写项目事实文件`，不得留空，也不得把密钥或整套项目资料复制进任务简报。需要首次创建标准项目事实文件时同时登记文件创建授权。已确认稳定事实持续复用；写文件、测试和发布前刷新对应易变事实。

`PM 控制目标`必须能唯一定位当前 PM 对话、平台消息入口或任务授权中指定的持久事件接收位置；只写一份普通文档路径但没有消费责任，不算事件目标。平台暂时无法投递时，执行者把完整事件保存在任务主面或最终结果中并标为`待重试`，PM 后续按事件 ID 消费。

缺口按影响处理：

| 缺口 | 状态 |
| --- | --- |
| 业务结果、写入边界、验收证据或红灯条件无法判断 | 保持待排期或阻塞 |
| 正式契约尚未形成，但设计责任和冻结条件清楚 | 可执行，先进入设计 |
| 测试命令尚未确定，但可在任务内调查 | 可执行，先调查并建立验证路径 |
| 写回位置未确定但现有当前工作台可承载摘要 | 可执行，先用当前工作台；不得乱建文件 |
| 多实例可能写同一边界 | 改串行、隔离分支或指定唯一合流实例 |

文档规则只能授予机制范围，不能绕过 Codex、操作系统、Git、服务器或外部平台的真实权限。真实权限缺失属于红灯。

PM 在陈述活动任务进度、剩余、授权缺口、下一步或并发放行前，必须按已登记正式 thread ID定点读取平台当前轮；当前工作台只代表最后已消费快照，不能替代实时线程。批量派单还必须先证明新正式任务能获得所需运行时权限；PM当前权限不视为子任务继承证据，平台不能在创建时携带权限且项目默认权限未就绪时，不得先批量创建再让用户逐个切换。

多项目分派时，PM 还要明确接收方本轮先看哪一份任务主面。若子项目当前任务分散在多份文档里，但 PM 没有先点名主面，不得启动执行者。

任务包含数据写入时，PM 必须在验收和红灯中条件化登记：旧有效值不得被空的新值静默覆盖、重复运行应幂等或可识别、批量写入需有事务/检查点与回滚或补偿证据。任务包含服务启动、外部凭据或发布时，必须在启动前检查最终命令、服务单元、进程参数和日志是否泄露秘密，并确认凭据来源与回滚入口。没有这些风险的任务不展开对应门禁。

## 6. 授权内自动状态机

任务控制实例领取后，默认连续执行：

```text
调查事实 → 设计并冻结当前轮契约 → 实现 → 自测/独立测试 → 边界内修复与回测 → 证据回写 → 收口判断 → 已授权的发布与发布后验证 → 回收
```

业务状态与实例状态必须分开记录。技能阶段和测试阶段不是业务状态：

| 业务状态 | 含义 |
| --- | --- |
| `待排期` | 业务结果或关键授权尚未冻结 |
| `可执行` | 任务包已冻结，等待真实任务控制实例领取 |
| `进行中` | PM 已消费当前执行回合的领取/启动或恢复事件 |
| `已暂停` | 当前执行回合已安全收口并释放，但原任务可沿同一任务 ID 恢复 |
| `候选完成` | 授权内动作、证据和完成事件已提交，等待约定收口裁决 |
| `已完成` | 自动、PM 或用户收口已完成 |
| `阻塞` | 红灯使当前授权内无法继续或恢复 |

| 实例状态 | 含义 |
| --- | --- |
| `待领取` | 尚无真实任务控制实例 |
| `执行中` | 实例已领取并承担当前执行回合 |
| `等待事件` | 保留现场等待当前任务对话中的短期纠偏，不等于 PM 等待 |
| `待回收` | 已提交局部或终态结果，等待平台关闭 |
| `已关闭` | 实例已释放，不再占用任务控制权 |
| `失联` | 无法确认实例是否仍承担责任，必须先停止重复派发并核对 |

兼容旧项目时，`验证中`迁移为业务`进行中 + 当前技能=测试`，`待验收`迁移为业务`候选完成`；不得继续让同一个`状态`字段同时表达测试阶段和实例存活。

正常流转为：

```text
待排期 → 可执行 → create_thread 创建登记 / 阻塞 claimed(resumed) → 进行中
进行中 → paused → 已暂停
进行中 → candidate_completed → 候选完成（实例释放；PM/用户采纳时更新控制快照，不要求原实例再发 completed）
进行中 → completed → 已完成
进行中 → red/failed → 阻塞或已暂停
```

PM 在消费真实领取事件前不得把`可执行/已暂停`提前写成`进行中`。执行者发送暂停、候选完成或失败事件后，实例状态进入`待回收/已关闭`，不能继续用“业务仍待验收”解释实例常驻。

任务授权同时确定收口方式：

- `自动收口`：低风险任务有机器可验证证据，全部验收项通过后自动进入已完成，并向 PM 报告。
- `PM 证据验收`：共享契约、关键链路或跨项目任务进入`候选完成`，PM 收到事件后依据证据直接采纳或退回，不再询问用户普通技术判断。
- `用户授权收口`：生产数据、不可逆操作、真实资费、重大业务取舍或用户明确保留的事项，必须等待用户决定。

`候选完成`是业务状态，不是执行实例等待状态。任务控制实例完成授权内动作、正式文档、验收证据和完整完成事件后，必须在同一轮发送最终结果并释放，不轮询或保持运行等待 PM/用户；后续退回作为新外部输入重开同一任务的新执行回合，保留任务 ID、正式上下文和既有证据。通知失败只保留可重试事件，不反向抹掉已经完成的业务结果。

每个终态同时记录`完成剖面`，至少分开说明：授权目标完成度、验收已覆盖/未覆盖及原因、生产状态、Git 状态、worktree/分支与其他资源状态。业务状态继续使用既有枚举；不能为了表达“已上线但真实写路径未覆盖”再发明近义状态，也不能让单一`候选完成`隐藏已经交付的范围。

任务使用独立分支或 `worktree` 时，Git 收口方式写入现有`允许操作`或`收口方式`，不新增一列：至少明确目标分支、合并/提 PR/保留、是否允许推送和任务 worktree 去向。任务创建时登记`自动清理 / 正式保留 / 待裁决`；已预授权的 task-owned 生命周期清理只处理本任务创建、clean、无未跟踪/未合并内容、提交已安全合流或可达且无活动消费者的 worktree。不能安全清理时写明所有者、原因、接手入口和触发条件；非本任务、dirty、归属不明或历史 prunable 只报告。删除、丢弃、强制推送或未授权远端推送不得自动执行。

任务分支和 worktree 是执行资源，由任务控制实例领取并维护。PM 先冻结目标分支、工作区归属和 Git 分项授权，再启动执行实例；若平台创建任务时自动生成 worktree，就把该 worktree 作为任务现场，不提前另建或占用同分支 worktree。`开始开发/测试/发布`不自动授予`git add`、`commit`、`push`或`merge`，每项仍按任务授权记录。

涉及发布时，进入真实环境前必须核对任务代码基线、目标主线、当前生产实际版本或可复核锚点、尚未进入目标主线的生产补丁、正式契约和回滚版本。生产独有补丁或跨任务热修复的来源、归属、兼容性和保留方式清楚时发送`shared_notice`，保留原来源并完成候选兼容合流与回归；归属未知、契约冲突、无法隔离或不能安全合入时发送`shared_conflict`并停止受影响发布动作。缺少生产版本锚点时只能继续只读调查或发布前预检，不能把任务分支直接覆盖到生产。发布后记录实际部署提交、目标主线是否包含该提交、服务/数据真值和回滚锚点；生产已运行但代码或正式文档尚未进入授权目标主线时，业务最多为`候选完成`。

生产验证创建的账号、数据、导出物和审计记录必须在发布前声明`自动清理 / 明确保留`。保留时写清业务用途、责任方、证据位置和清理触发；没有保留授权的测试数据在取得证据后按正式流程清理。不得用“验证需要”让生产残留无限期无归属存在。

若 PM 已经越界修改执行资产，收到纠正后立即停手，不得自行暂存、提交、继续实现或破坏性回退。PM 只登记已改文件、候选 diff、分支/worktree 和实际 Git 状态，将其标记为`待任务控制实例独立验证后采纳`并移交；已有任务现场时不得再创建同分支 worktree，先明确唯一工作区归属，再由执行实例决定采用、修复或排除候选改动。

生命周期事件只在控制关系或正式真值变化时发送；命令级进展和普通调试不进入 PM 控制面。事件类型至少包括：

- `claimed`：仅用于来源不明、恢复或冲突等阻塞领取场景，声明实际会话/线程与唯一工作区。
- `started`：兼容旧任务的启动事件；新建正式任务由创建回执直接登记，不再单独发送。
- `paused`：安全停止外部影响、写回剩余范围并释放实例。
- `resumed`：沿原任务开启新执行回合；必须带新的实例定位和易变事实刷新结果。
- `yellow`：需要 PM 知道但授权内仍继续的控制偏差；普通技术日志不发送。
- `red`：资源、实例、边界或共享契约问题需要 PM 裁决。
- `shared_notice`：来源和兼容方式清楚的共享契约、用户纠正或跨任务补丁通知；不等待纯消费回执。
- `shared_conflict`：共享契约、归属、写入或生产补丁存在冲突，受影响动作必须停止并由 PM裁决。
- `candidate_completed`：证据与正式回写已提交，等待约定收口。
- `completed`：自动收口已成立；PM/用户采纳`candidate_completed`时直接更新控制快照，不要求已释放实例再发第二终态。
- `failed`：当前执行回合无法继续且已提交失败包。

统一事件结构：

```text
事件 ID：<任务 ID>:<任务版本>:<执行回合>:<序号>
任务 ID / 任务版本 / 执行回合：
事件类型 / 发生时间：
实际实例 ID / 会话或线程定位：
业务状态 / 实例状态：
授权或共享契约变化：无 / 摘要与正式位置
完成、剩余与一手证据：
Git、服务、数据等当前真值：
正式写回位置：
下一步 / 需要 PM 裁决：
```

PM 按稳定幂等键和任务版本消费，优先级固定为`显式事件 ID → 平台事件或消息 ID → 规范事件指纹`。规范事件指纹只使用任务 ID、版本、回合、类型、来源 thread、发送端事件时间和稳定制品/提交/正文哈希；平台投递时间不参与。稳定字段不足时登记`待补幂等键`，不自动改状态；已消费键不重复启动实例或收口，旧任务版本只作证据。序号跳跃、同一执行回合出现两个控制实例或业务/实例状态冲突时停止自动消费并核对。PM 在当前工作台记录消费结果和时间；投递失败沿用原键重试，不能换随机 ID伪装新事件。

完整生命周期事件到达 PM 正式线程后走`事件快消与按需回源`路径，不重新接手、规划或全量读项目。领取/启动/恢复事件只核对任务 ID、版本、回合、序号、来源 thread ID、项目/工作区和冲突实例；终态事件只读取事件点名的任务主面、证据、Git、服务/数据锚点。允许写控制面时聚合更新一次；任务授权明确禁止文件写入时只保留平台事件事实，不为消费强行改文档。

阻塞模式`claimed/resumed`是抢占式快消事件：字段完整、来源与待领取任务一致且没有双实例冲突时，PM 完成平台消息能力定位后的下一次实际平台动作必须直接向来源正式任务 thread ID发送登记结果。回源前不得推演后续事件、统计整链耗时、读取项目文件、重载任务包、规划测试或等待更多事件。创建回执登记型任务没有领取/启动消息；收到兼容`started`、即时`yellow/shared_notice`或终态时按序幂等消费，不主动发送纯消费回执，不为每条事件重开项目分析。

只有阻塞`claimed`、`red`、`shared_conflict`或其他实际需要裁决的事件才通过平台线程消息能力回发来源正式任务 thread ID；回源内容必须是登记结果或实际裁决，不先发“已收到”。回源失败时按原事件 ID登记待重试，不让执行任务更换事件 ID或长期轮询。

worker 已发送终态并释放后，PM 直接消费和收口控制快照，不再向已释放实例发送纯消费消息。需要退回时以同一任务 ID的新输入或新执行回合重新唤醒，而不是用终态回执制造记账回合。普通事件消费不生成性能报告，只有用户或测试任务明确要求时才汇总耗时。

总工作台是 PM 最后已消费控制快照。任务控制实例写任务主面、正式契约、证据和事件发送端，不直接把总控业务状态或实例登记改成已消费结果；PM 消费事件后统一更新总工作台。正式任务优先用平台线程消息能力把`shared_conflict / red / paused / candidate_completed / completed / failed`投递到实际 PM thread ID，使已空闲 PM 产生新回合并消费；普通`yellow/shared_notice`先写任务主面并随下一控制事件合并，只有必须在终态前协调其他任务时才立即投递。只写`/root`、collaboration mailbox、普通文档路径或口头“已通知”不算投递。没有活跃 PM 或线程消息暂不可用时，事件写入任务授权指定的持久事件目标并标记待消费，投递恢复后沿用原事件 ID重试。项目若明确只有一个实例兼任 PM 与任务控制，仍按相同字段完成自消费，不省略事件 ID和双状态。

事件严重度与处理方式分三级：

- `绿灯`：在目标、边界和契约内，自动推进，只在里程碑回写摘要。
- `黄灯`：出现可恢复偏差、替代实现、普通测试失败或非关键证据缺口；记录并通知 PM，但在授权内默认继续。
- `红灯`：目标或正式契约必须改变、写入越界、真实权限缺失、多实例冲突无法隔离、涉及未授权生产或不可逆操作、证据互相矛盾、修复达到上限；立即暂停并升级。

只有红灯需要等待裁决。黄灯不得被写成“等待 PM 审批”。

红灯按性质直达责任方，不默认都回 PM：

| 去向 | 适用情况 | 处理方式 |
| --- | --- | --- |
| 任务内自愈 | 普通实现错误、可恢复构建失败、同边界修复、可替代验证 | 不形成红灯；记录为黄灯并继续 |
| PM 控制面 | 资源冲突、实例编排、跨任务优先级、写入边界重分配、正式契约影响范围 | 任务控制实例提交证据和最小裁决项，PM 只处理控制问题 |
| 用户直接纠偏 | 业务语义不确定、需求取舍、验收偏好、真实生产授权、不可逆或高成本操作、连续修复后怀疑方向错误 | 原任务对话直接向用户提出一个最小问题，不经 PM 转述 |

等待人类纠偏时，任务控制实例保持原任务 ID、上下文、证据和当前现场，实例状态写`等待事件`。用户回答后，原实例更新授权或设计并继续状态机；PM只接收纠偏结果和影响摘要，不重新分派任务。

多个任务同时需要用户纠偏时，PM 可合并重复问题，但不得改写执行实例的一手事实。不得把纯技术错误包装成业务问题打断用户，也不得把需要用户决定的业务问题长期滞留在 PM。

## 6.1 并行与派生实例

默认由任务控制实例在同一对话内切换技能。两个或以上执行者并行时，再检查四件事：

- 每条执行线的写入边界不同；若同一文件、模块或文档需要多人修改，必须先指定唯一合流人，其他执行线只交付局部结果。
- 每条执行线都写清前置任务或依赖；依赖未满足时，该线状态只能是待排期或阻塞。
- 共享对象或共享契约必须只有一个正式版本，例如同一份 API 契约、状态枚举、字段表、发布通道或任务状态机。
- 最后合到哪里必须可验证，例如“前端样例、后端样例和测试证据都回到任务控制实例汇总”。

并行不等于同时改文件。真正允许并行的，是“主线一致、边界不同、契约一致、合流清楚”。

同一 Git 仓库内并行修改代码时，PM 还要先判断是否需要独立分支或 `worktree`：

- 写入边界可能交叉、需要独立提交或需要分别回滚时，优先使用独立分支或 `worktree`。
- 只读调查、完全不同边界的小改动，或项目当前不具备 Git 条件时，可以不启用，但必须写清合流顺序和替代隔离方式。
- 工作区已有未提交变更时，不得为了创建隔离环境而覆盖、移动或清理用户现有改动。

是否启用隔离由项目 Git 现实和任务风险决定，不把 `worktree` 设为所有任务的固定前置条件。

### 派生实例上下文隔离

子智能体默认只读取当前任务简报、唯一正式依据和完成任务必需的代码或证据。不得让子智能体通读 PM 完整历史后自行猜任务，也不得只发一句口头目标让它补全全部上下文。

任务简报至少包含：原任务 ID、局部目标、输入、读写边界、交付物、验证方式、写回位置和红灯条件。大段设计、日志和历史通过文件路径传递，当前对话只保留摘要。

子智能体完成后，按风险进行两层判断：

1. 任务符合度：是否做了要求的内容，是否漏做、越界或擅自扩展。
2. 结果质量：实现、测试、配置或文档是否可靠，证据是否支持结论。

两层判断可以由自动测试、独立测试实例或 PM 证据验收承担，不新增固定“审查者”身份，也不要求每个低风险任务都启动额外实例。

### 同任务实例派生

局部动作需要另一个智能体执行时，优先派生实例，不机械新增任务。派生实例必须沿用原任务 ID，并在实例表登记：启动者、身份、当前技能、输入、读写边界、交付物、写回位置、允许继续派生什么和关闭条件。

默认只允许一层派生。派生实例不得继续派生其他实例；需要更深协同时，任务控制实例先判断能否改为自身执行，仍不能解决才形成红灯升级。

普通缺陷默认由同一任务控制实例从测试切回开发、修复后再回测试，不额外启动实例。需要独立测试、并行处理或写入隔离时，再使用下面的协作循环：

1. 测试执行者取得失败证据。
2. 失败证据直接回到任务控制实例；测试实例不修改任务状态、不改变契约，也不启动或控制开发实例。
3. 任务授权已包含修复范围时，任务控制实例自行切回开发，或启动一个沿用原任务 ID、写入边界明确的开发修复实例；平台受限时按前述一次性资源启动契约处理。
4. 开发实例只修复当前缺陷，将 diff、自测和风险直接回报任务控制实例；任务控制实例负责关闭或发出终态回收事件。
5. 任务控制实例把新结果交回原测试实例重新验证；不由开发实例自宣通过，也不另建平行测试任务。
6. 原测试实例把回测证据交回任务控制实例，由任务控制实例更新任务状态并按原定收口方式继续；需要改契约、扩大边界、执行高风险操作或达到修复上限时形成红灯升级。

任务已预授权目标环境、发布对象、版本、验证和回滚锚点时，测试通过后可以自动进入运维发布与发布后验证，不再等待 PM 二次激活。未授权的生产发布、不可逆操作或真实权限缺失仍是红灯。

## 7. 多项目协同

前端、后端、爬虫、数据、测试、运维等可独立交付时，按项目群模式运行。

测试可以作为执行线长期存在，但不是新的身份入口。测试线负责接收问题、复现、判断归属、复测和给出关单证据。执行线自测不能替代任务授权中明确要求的独立测试；收口按任务开始时约定的自动收口、PM 证据验收或用户授权执行，不默认都等 PM。

| 层级 | 保留内容 | 不保留内容 |
| --- | --- | --- |
| PM 总控 | 跨线主线、调度表、接力状态、证据位置、下一步 | 子项目长日志、调试流水 |
| 子项目入口 | 本线任务、验证证据、局部风险、阻塞 | PM 总控的完整历史 |
| 正式接力面 | 来源线、目标线、当前事实、目标动作、接收状态、关闭条件 | 纯聊天结论 |

子项目入口不是默认新增文档。能用当前工作台任务行、接力与验收表、任务卡或已指定事实文件承载时，不另建子项目入口文档。

多项目场景下，`当前工作台.md` 默认先承担总控当前真值面。PM 首轮先看：

- 当前总主线
- 子项目状态摘要
- 当前阻塞项目
- 当前待接力事项
- 当前下一步

总控面只保留摘要，不复制子项目长日志。
总控当前真值面不替代子项目任务主面。它负责先判断“先盯谁、卡在哪、下一步是什么”；真正的任务领取和本线执行，仍要落到被 PM 点名的任务主面。

多子项目不要求文档树长得一样，但 PM 必须能用同一套读法看懂每条线。最低要求是每个子项目都能映射出四个面：

- 当前真值面：当前主线、当前状态、当前阻塞、当前下一步
- 当前任务面：当前任务、任务状态、当前实例、依赖关系，以及本轮先看哪一份任务主面
- 接力面：跨线事项、接收状态、下一步
- 历史面：已完成过程、旧证据、旧阶段结论

若某条子项目线把“当前真值、当前任务、历史过程”长期混在同一份大文档里，PM 应先判为读入风险；优先补清映射关系或最小拆分，不默认重建整套文档树。

若某条子项目线当前任务散在多份文档里，PM 先指定一份任务主面，其他只作补充；没有主面时，执行者不得自行猜测入口。

状态分层也要固定：

- 业务状态用于任务流转，例如`待排期 / 可执行 / 进行中 / 已暂停 / 候选完成 / 已完成 / 阻塞`
- 实例状态用于资源责任，例如`待领取 / 执行中 / 等待事件 / 待回收 / 已关闭 / 失联`
- 收口判断用于裁决结果：`采纳 / 限定采纳 / 退回 / 阻塞`
- 收口方式或裁决人单独记录：`自动 / PM / 用户`

不要把“验收证据已齐”和“任务已按授权收口”当成同一件事。

跨线事项不能只留在对话中。接收状态固定只用：

- `已发出`
- `已接收`
- `已纳入执行`
- `已验收`
- `已退回`
- `已阻塞`

来源线发起正式接力后，接收方必须在自己的当前工作面、任务面或任务卡里回写：

- 接力 ID
- 接收状态
- 下一步

没有目标线回写时，任务控制实例或 PM 不得把接力判成已成立或已闭环。
若目标线有明确任务主面，回写优先落到该任务主面或由它指向的位置，不把接力只留在聊天或来源线文档里。

## 8. 接口契约

跨智能体交付前，必须先冻结最小契约。

| 类型 | 最小契约 |
| --- | --- |
| API | 路径、方法、请求参数、响应字段、错误码、鉴权 |
| 数据 | 字段名、类型、必填项、默认值、状态枚举、样例 |
| 前端 | 页面入口、展示字段、加载态、空态、错误态、刷新方式 |
| 文件 | 允许修改、禁止修改、生成物放哪里 |
| 联调 | Mock、测试数据、验证路径、日志定位 |

契约缺失时可以进入任务内设计，但不得进入依赖该契约的实现。正式契约需要变化时形成红灯，由 PM 记录影响范围、受影响执行线和新的合流位置后重新授权。

## 9. 交付与采纳

协作实例交付必须返回最小交付包，至少包含：

```text
任务 ID | 智能体实例 ID | 完成内容 | 修改位置 | 已运行验证 | Git 状态 | 是否达到要求 | 残留风险 | 写回位置
```

协作实例结论先回到任务控制实例，未完成任务授权约定的验收前不是主线事实。没有交付包、验证证据或写回位置的输出不得并入主线。

并行结果合流时，任务控制实例必须检查：

- 前置依赖是否真的完成。
- 共享对象或共享契约是否仍是同一个正式版本。
- 最后合到哪里、由谁负责合流，是否已经确认可并线。
- 一个执行线的阻塞是否会使其他执行线结论失效。

当前工作台摘要不是验收证据。任务收口前，证据位置必须指向可读取的一手材料，例如交付包正文、日志路径、证据文件、测试命令输出、截图或外部系统记录 ID。

任务完成前先把用户纠正、正式契约、受影响验收和结果证据写回指定位置，再按收口方式只发送一个终态：需要 PM/用户裁决时发送`candidate_completed`，自动收口成立时发送`completed`。事件除统一结构外还要包含完成与未完成范围、用户纠正摘要、测试/生产/Git 锚点、残留风险和建议后续；通知失败只记录为同一事件 ID 的可重试投递，不能反向抹掉已经完成的业务结果，也不能改发另一种终态。

PM 消费暂停、失败或完成事件前必须执行终态真值核对：任务版本和执行回合正确；总工作台、任务主面、实例登记和最后事件能够互相解释；验收证据可读；Git、服务/进程、数据和发布现实与事件表述一致；最终消息不把候选完成冒充已采纳。不能核对的部分只做限定采纳或标记待补证据，不要求已经释放的实例长期等待；需要返工时沿同一任务 ID 建立新执行回合。

## 10. 文件创建门禁

多智能体协同时，文件创建仍以 [../00-模板入口.md](../00-模板入口.md) 的文件创建门禁为准。这里补两条协同特有要求：

- 跨线协同默认只使用当前工作台的任务授权与调度表、接力与验收表、证据索引和记录区，不得另建协作文档。
- 任务授权已明确允许新增协作文档时，由任务控制实例完成文档地图判断、入口挂载和回收登记；授权未包含时属于红灯，不得自行创建。

## 11. 后台助手回收

后台助手可以常驻或临时，但它不是身份入口，只是 PM 总控或执行者派生的辅助实例。每次触发后必须留下审计：

```text
名称/类型 | 目标 | 输入 | 状态 | 结论 | 依据 | 风险 | 决策 | 回收结果
```

回收结果只允许：已采纳 / 已废弃 / 已转任务 / 已关闭 / 已过期。没有审计证据，不能判定为正常运行。

## 11.1 子智能体回收门禁

子智能体不能无限制地开。默认遵守下面五条：

1. 先有任务，再启实例
   没有任务行、没有用途说明或没有写回位置时，不得启动子智能体。

2. 一次启动，对应一次责任
   每个实例都要能对应到当前工作台里的任务、用途或接力事项；不能只因为“可能后面会用到”就长期保留。

3. 结果拿回后，立刻进入回收判断
   只要交付包、证据或调查结论已经回写，就要判断该实例是继续复用，还是立即关闭。

4. 没有后续动作的实例，默认关闭
   已完成、已退回、已阻塞且短期不会继续、已被别的实例接替、或只是一次性测试/验证用途的实例，默认不继续保留。

5. 关闭也是正式动作
   任务控制实例关闭协作实例时写清结果去向；PM 只回收跨任务残留和失去责任归属的实例。

默认只在以下情况允许实例继续保留：

- 当前任务仍在执行中，且下一步明确由该实例继续
- 等待短期内的补充输入、补充验证或接力回复
- 后台助手明确是常驻监控用途，且已有审计和回收条件

以下情况必须优先关闭，而不是继续堆积：

- 测试已完成，只剩按任务约定执行收口
- 交付包已回写，当前实例没有下一步
- 右侧实例数量增长，但当前工作台没有对应活跃任务
- 同类用途已经启动了新实例，旧实例不再承担责任

PM 若无法确认某个实例是否还要继续使用，默认按“待回收”处理，先暂停继续分派给它。

## 12. 冲突处理

先判断问题类型，再按固定顺序处理。禁止一边继续扩散，一边口头说“后面再统一”。

### 12.1 进入阻塞的情况

出现以下任一情况时进入阻塞：

- 写入边界冲突，或多人同时改同一正式边界。
- 前置依赖未完成却提前开工。
- 共享对象、共享契约或共享配置被不同执行线改成不同版本。
- 最后合到哪里未指定，或拍板人无法判断是否可并线。
- 子智能体没有匹配任务、任务来源缺失，或交付结果缺验证证据。
- 新文件缺少创建登记、入口位置或回收方式。
- 历史资料、聊天结论、用户判断与当前代码、Git、测试或环境结果冲突，且尚未纠偏。

### 12.2 固定处理顺序

协同故障按下面五步处理：

1. 发现问题：明确故障类型。
2. 停止扩散：暂停继续改动、继续合流、继续新建文件或继续采纳。
3. 找当前依据：确认当前应以哪份契约、配置、代码或门禁为准。
4. 按异常性质裁决：技术问题任务内解决；资源、实例和边界问题由 PM 或合流人解决；业务语义、验收偏好和高风险授权直接由用户决定。
5. 重新验证：验证通过后，才能恢复`进行中`、进入`候选完成`或`已完成`。

### 12.3 常见问题与默认解法

| 问题类型 | 默认解法 |
| --- | --- |
| 契约或共享对象冲突 | 先冻结唯一正式版本，再改实现；未统一前不得继续联调、并线或采纳 |
| 同文件并发冲突 | 默认视为高风险；能拆边界就拆，拆不了就串行；已冲突时由 PM 或指定合流人统一结果 |
| 环境或运行基线漂移 | 先冻结唯一说法，再给出一正一反两组验证；未统一前不得继续联调、发布、交付或采纳“可运行/可发布”结论 |
| 判断冲突 | 先暂停把口头结论写入主线；事实冲突按代码、Git、测试和环境纠偏，业务目标或验收取舍直接询问用户 |
| 证据不足 | 不得采纳；先补一手证据，再继续判断 |

### 12.4 当前工作台最少记录

发生协同故障时，当前工作台至少记录：

```text
问题类型 | 当前影响 | 停止扩散动作 | 当前依据 | 谁来拍板 | 恢复条件 | 复验结果 | 下一步
```

### 12.5 完成条件

只有同时满足以下条件，故障才算关闭：

- 停止扩散动作已执行。
- 唯一版本已确定。
- 任务授权指定的责任方已完成裁决。
- 复验通过，且证据可读。
- 当前工作台已回写下一步。
