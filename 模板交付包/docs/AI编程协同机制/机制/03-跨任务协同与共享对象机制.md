# 跨任务协同与共享对象机制

> 本文件只处理不同正式任务之间已经发生的依赖、共享对象、接力或冲突。单一任务、普通 Skill切换和 Worker内部修复不进入本文件。

## 1. 当前架构中的位置

BEYOND不再把设计、开发、测试和运维组织成多个专业智能体流水线。普通业务任务由一个 Worker负责到底，Worker按当前问题切换 Action Skill。

正式任务是用户可见、可直接进入的顶层任务对话；Worker 在其中承担完整业务结果。内部子智能体只属于某个 Worker 的局部协作，不因单独运行就成为正式任务。

多个正式任务同时运行时，可能出现多个 Worker执行实例，但“实例数量多”本身不构成协同关系。任务彼此独立时，各自执行，PM通过工作台掌握结果，不读取本文件。

任务内助手、显式要求的独立测试和修复循环属于原 Worker内部协作，以[协作、修复与接力](../../../skills/identity-worker/references/collaboration-and-rework.md)为准。只有另一个普通正式任务确实消费原任务成果时，才因真实依赖进入本文件。

## 2. 什么时候读取

只有出现以下任一关系时才读取：

1. 两个正式任务实际触碰同一文件、契约、数据、账号、环境、服务或生产对象；
2. 一个正式任务的成果是另一个正式任务继续执行的输入；
3. 一个任务的写入、发布或资源占用会改变另一个任务的安全执行顺序；
4. 用户明确建立的另一个普通正式任务需要消费并返回本任务成果。

下列情况不读取：

- 多个互不依赖的正式任务同时存在；
- PM只是在工作台查看多个任务的进度；
- 同一 Worker连续设计、开发、测试、运维、修复或复测；
- Worker使用任务内助手、工具或显式要求的独立测试；
- 多开对话、终端或进程，但没有跨任务依赖和共享对象。

进入路径只有两条：

- PM发现正式任务之间出现上述关系时，先读本文件，再按需读[跨任务协调](../../../skills/identity-pm/references/cross-task-coordination.md)；
- Worker发现本任务将影响或依赖另一个正式任务时，先读本文件，再回[协作、修复与接力](../../../skills/identity-worker/references/collaboration-and-rework.md)处理本任务动作。

本文件不建立身份、任务、Worker实例或授权。

## 3. 跨任务公共事实

发生跨任务关系时，只需要确认：

```text
相关正式任务与各自 Worker / thread
各任务拥有的文件、模块与运行对象
共享对象及唯一所有者
依赖关系与安全执行顺序
正式交付物、验证入口和接收结果
```

PM在[当前工作台](../当前工作台.md)保留任务关系摘要；实时细节留在对应任务线程。不得把命令流水、完整任务包、测试日志、提交哈希清单或消息协议复制到工作台。

只有用户明确确认、既有正式规则已经生效，或新的一手事实触发现有安全边界时，跨任务变化才具有控制效力。讨论、建议、候选方案和 PM推断可以被标记知会，但在确认前不能成为其他任务的新前置、暂停条件或授权变化。

业务状态只使用`进行中 / 已暂停 / 已完成`。跨任务等待、Skill切换、普通失败和 PM是否已读消息都不是新状态。

## 4. 并行与写入顺序

- 当前主线不等于一次只能运行一个正式任务；已经授权、可独立验收且没有真实共享冲突的任务可以同时推进；
- 不同正式目录、独立 clone和只读活动可以并行；
- 同一目录内，文件/模块所有权明确、共享对象不重叠且测试或运行副作用隔离时，也可以并行编辑和验证；
- 同一文件、契约、数据、服务、环境或生成物实际重叠时，只串行受影响动作；
- 同一 Git工作区的索引、HEAD和历史动作串行；每次只精确暂存任务路径并核对 diff；
- BEYOND不创建或推荐 worktree；用户或平台已提供的既有 worktree只按当前 Git现场兼容处理；
- Git锁被另一个正常操作占用时，等待该操作结束后刷新 HEAD与状态继续，不向 PM申请方法授权；未知暂存、重叠改动或持续锁冲突才协调；
- 等待重叠对象或 Git动作的任务保持进行中并继续安全动作，不为了排队制造暂停。

不同路径、不同对象、已隔离副作用、只读无锁活动或仅名称相似，不构成共享冲突。同一仓库或目录也不能单独证明冲突；一个慢任务不能阻塞没有依赖的任务。

## 5. 共享对象冲突

共享对象只有一个正式所有者。其他任务引用正式来源，不复制第二份独立定义。

发现实际冲突时：

1. 只停止会扩大冲突的写入、合并、发布或数据动作；
2. 核对共享对象、所有者、相关任务、当前真实版本和各自目标；
3. 能安全按顺序完成时由 PM安排先后；
4. 能由唯一所有者兼容收敛时，更新正式来源并通知受影响任务；
5. 需要改变业务含义、生产授权或不可逆路径时交给用户；
6. 不依赖该对象的工作继续。

PM解决任务关系和资源顺序，不接管 Worker的任务内实现，也不把局部冲突变成全项目暂停。

## 6. 跨任务接力

只有一个正式任务的成果确实需要被另一个正式任务消费时才建立接力：

```text
来源任务与正式成果
接收任务与下一动作
共享对象及唯一所有者
文件、提交、制品或运行事实
双方读写边界
验证入口与关闭条件
```

接收方核对当前事实后，在自己的 Worker任务中继续。接力不转移来源任务的授权、控制权或用户检查点，也不静默改变双方目标和验收。

用户在 Worker任务中给出的任务内指令直接由该 Worker处理，不经 PM转述。变化影响另一个正式任务、共享对象、项目主线或高风险边界时，Worker按身份规则把最小影响留给PM在安全边界消费；本文件不另建平台直发路径。

## 7. 进展与退出

普通进展和任务内失败留在各自 Worker线程，不要求 PM逐步确认。PM需要实时状态时定点读取对应线程；只有真实暂停、完成或跨任务影响需要进入主线视图。

正式任务由各自Worker冻结一份终态，同时写入短期pending并输出相同final；原生回调只唤醒唯一PM，PM扫描全部pending和已登记Worker后用工作台事务收敛已验收结果并删除已消费回执。该路径不建立跨任务依赖、共享对象所有权或执行顺序。只有第2节关系真实出现时，PM才在收到结果后进入本机制。

暂停、完成、恢复和证据要求以 PM、Worker规则为准。本文件不另建生命周期消息、版本/回合或第二套回执协议。

满足以下条件后退出跨任务协同：

- 写入顺序或共享所有权已经明确；
- 交付结果已被接收、拒绝或明确留待处理；
- 冲突已经解除，或者受影响任务已按真实条件暂停；
- PM已把仍影响主线的结论更新到工作台。

之后各 Worker回自己的业务任务，PM回主线治理；再次命中第2节时才重新读取本文件。

## 8. 返回规则所有者

跨任务关系处理完后，其余职责返回根[AGENTS.md规则所有者](../../../AGENTS.md#2-规则所有者)指向的PM、Worker、项目事实、Action Skill或真实工具；本文件不重复建立任务状态、消息协议、授权体系或第二个事实所有者。
