# BEYOND 安装、升级与项目初始化指南

> 这是使用说明，不是新的运行规则。发生冲突时，以目标版本交付包、当前项目根`AGENTS.md`、身份Skill和固定脚本的实际结果为准。

## 1. 先分清三个结果

| 环节 | 完成标志 |
| --- | --- |
| 文件安装或升级 | 项目内`beyond-control/beyond-release.json`、六个已安装Skill和项目入口属于同一目标版本 |
| 安装验真 | 安装验真脚本退出码为`0`，没有旧版、混合版本或BEYOND旧Hook残留 |
| 项目初始化 | 项目边界、当前工作台、历史任务和长期事实入口已经调查并由用户确认 |

正确顺序是：

```text
准备目标版本交付包与六个Skill
→ 初始化或升级项目入口
→ 运行安装验真
→ 记录“完整初始化”或“后续按需补齐”的用户选择
→ 新PM接手主线
```

BEYOND标准路径不安装身份Hook，不要求`/hooks`信任或身份护栏探针。安装或升级仍应使用新的普通对话，不调用身份Skill；这样不会让已有PM或Worker一边承担业务任务，一边替换项目入口。涉及根入口或Skills替换时，先等活动任务停止；文件安装完成后必须重启Codex，并在新进程完成验真。

## 2. 准备目标版本

从正式Release取得不可变交付包。把完整`模板交付包`放到业务项目根并命名为`beyond-control`，不要把交付包散着覆盖业务文件：

```text
业务项目/
├─ beyond-control/
├─ <原有代码与文档>
└─ ...
```

把`beyond-control/skills/`中的六个Skill安装到当前Codex Skills目录：

```text
identity-pm
identity-worker
task-design
task-dev
task-test
task-ops
```

升级时保留已有控制仓中的`local/`、`projects/`和`shared/`真实内容，不用空模板覆盖。旧项目已有`.codex/hooks.json`时，固定脚本只移除其中引用`beyond-runtime-guard.mjs`的BEYOND旧处理器；其他Hook与`.codex`文件原样保留，并在修改前备份。

可复制的安装维护提示词：

```text
这是BEYOND安装维护请求，不建立PM、Worker或业务任务。
请使用目标版本正式发布包安装或升级当前项目中的beyond-control和六个全局Skill。
先备份已有项目入口和控制仓本机资料；保留项目原生规则以及local、projects和shared中的真实内容，不用空模板覆盖。
若发现BEYOND旧身份Hook，只精确移除BEYOND处理器和护栏文件，保留其他Hook与.codex内容。
完成后运行安装验真；不要宣布项目初始化或业务任务已经完成。
```

## 3. 初始化新项目

安装六个Skill后，在项目根新建对话：

```text
$identity-pm
使用 BEYOND 初始化这个新项目。
```

PM先从磁盘调查，再一次只询问一个当前确实需要且无法确认的问题。至少确认项目目标、正式目录和当前阶段需要的开发、测试或部署入口；不存在的事实保持待确认。初始化结束前，PM运行`worker-policy --action show --project-id <当前项目>`，把平台默认与BEYOND推荐分层的具体模型和推理参数原样展示给用户，再让用户选择；该选择由固定脚本写入项目总览，不写根入口和工作台。用户未确认时保持平台默认，不阻塞其他初始化或普通任务。

确认入口融合时使用：

```text
确认以BEYOND的AGENTS.md为主融合，同时保留项目原生规则。
只完成项目入口和文档地基，不启动业务任务，不推送远端Git。
```

融合结果会明确返回“现在完整初始化”或“先开始使用、后续按需补齐”的唯一选择。用户选择后由PM写入项目总览；融合后再进入第5节验真。

## 4. 接入或升级已有项目

已有项目不能按空白项目初始化，也不能整目录覆盖。在项目根新建对话：

```text
$identity-pm
使用 BEYOND 接入或升级这个已有项目。

先只读调查现有AGENTS.md、代码与Git边界、Markdown文档、旧工作台和仍在运行的任务。
不要重新安装，不启动或恢复业务任务；一次只向我确认一个迁移或融合决定。
```

依次确认：

1. 项目根、子项目、重复工作目录和各自Git边界；
2. 哪些旧任务仍在进行，哪些已暂停、已完成或只是待办；
3. 旧工作台怎样迁入当前工作台与历史；
4. 产品、架构、开发、测试、服务器、部署、回滚和安全文档由哪里承载；
5. 项目根`AGENTS.md`怎样备份、保留和融合；
6. 是否补充本机项目身份及团队协同信息。
7. 运行固定脚本展示两种Worker策略及具体参数；若旧根覆盖区存在模型策略候选，必须由用户重新确认后在同一次融合中迁入项目总览并移除旧行，不能静默继承或双重保留；没有既有候选时选择平台默认或BEYOND推荐分层，未确认则保持平台默认。

确认融合时使用：

```text
确认以BEYOND的AGENTS.md为主融合，并完整保留项目原生规则和正式文档。
旧工作台先备份，再把真实活动任务迁入当前工作台；已完成和失效内容进入历史，不删除原对话和证据。
若存在BEYOND旧身份Hook，只移除BEYOND部分并保留其他Hook。
若发现旧Worker模型策略，先展示固定脚本返回的具体选项；按我明确选择的策略迁入项目总览并从旧根覆盖区移除，不得同时保留。
本轮只完成老项目初始化，不启动或恢复业务任务，不推送远端Git。
```

最低接入完成后，PM必须运行：

```powershell
node beyond-control/scripts/beyond-control.mjs initialization --action show --project-id "<项目编号>"
```

只把脚本返回的唯一选择交给用户。选择完整初始化后逐组处理项目总览、架构、开发、测试、运维、安全和其他专属资料；选择先使用则不阻断普通任务，后续仍由同一命令恢复。全部分组处理完、项目事实索引已经指向唯一正文、根`AGENTS.md`只剩稳定边界和事实入口后，才记录完整初始化完成。最后展示当前主线、活动任务、待办/历史、项目事实入口和仍待确认内容。

固定写入动作分别是`initialization --action choose`、`record`和`complete`；运行`help`可查看参数。`record`会拒绝不存在或未被项目事实索引承接的正式入口，`complete`还会重新验真全部入口并要求明确传入根入口已核对。PM每次只执行当前用户已经确认的一个动作，不要求用户填写命令或记住分组状态。

## 5. 安装验真

从项目根运行：

```powershell
node beyond-control/scripts/verify-install-integrity.mjs --installed-skills-root "<Codex Skills目录>" --project-agents "<业务项目根>/AGENTS.md"
```

退出码为`0`且明确说明六个Skill、控制仓结构和项目运行内核一致，才算安装验真通过。脚本还会拒绝仍引用BEYOND旧身份护栏的项目。`--content-only`只核对候选内容，不证明项目已经完成融合。

| 现象 | 判断与处理 |
| --- | --- |
| 六个Skill存在但内容不一致 | 仍是混合版本，重新对账目标发布包 |
| 项目入口缺少控制仓映射 | 文件已复制但项目融合未完成 |
| 仍残留BEYOND身份护栏 | 重新执行老项目升级的固定融合脚本，不手工删除整个`.codex`目录 |
| 第三方Hook仍存在 | 正常保留；它不属于BEYOND验真对象 |
| 初始化状态为`awaiting-choice` | 只算最低接入，运行`initialization --action show`并交给用户选择 |
| 初始化状态为`on-demand` | 普通任务可继续；需要完整归位时从脚本返回的首个待处理组恢复 |
| 根`AGENTS.md`仍承载大量项目事实正文 | 完整初始化尚未收口；先核对事实索引和唯一正文，再瘦身根入口 |

## 6. PM接手

安装验真、最低接入和用户初始化选择完成后，即可在项目根新建PM。用户选择完整初始化时，应先完成全部分组再接手主线；用户选择后续按需补齐时，PM可以先接手并处理普通任务，以后从受管状态继续补齐。只改普通项目文档且不涉及根入口或Skills时不强制重启；根入口或Skills完成替换后必须重启Codex，并用新进程确认实际加载版本。

```text
$identity-pm
接手当前项目。BEYOND已经完成安装验真和最低接入；请按项目总览中的初始化状态判断是已经完整归位，还是后续按需补齐。
请读取当前工作台，只汇报当前主线、活动任务、暂停项和下一步；不要重复创建、启动或恢复任务。
```

用户确认清单无误后，再输入：

```text
恢复当前仍为进行中的原任务。已暂停任务保持暂停，已完成任务不要重新启动。
```
