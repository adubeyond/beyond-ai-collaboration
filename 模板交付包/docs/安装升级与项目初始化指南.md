# BEYOND v3.1.2 安装、升级与项目初始化指南

> 这是面向使用者的操作说明，不是新的运行规则。发生冲突时，以当前项目根`AGENTS.md`、身份 Skill和固定脚本的实际结果为准。

## 1. 先分清四件事

| 环节 | 完成标志 |
| --- | --- |
| 安装或升级文件 | 项目内`beyond-control/beyond-release.json`、六个已安装 Skill和项目入口均为`3.1.2` |
| Hook审核与信任 | 在项目根启动的 Codex CLI中，`/hooks`显示当前项目Hook已启用且已信任 |
| 安装验真 | 真实Hook探针成功，安装验真脚本退出码为`0` |
| 项目初始化 | 项目边界、当前工作台、历史任务和长期事实入口经过调查与用户确认 |

文件安装成功不等于项目初始化完成；Hook探针通过也不等于PM已经接手项目。正确顺序是：

```text
准备3.1.2交付包与六个Skill
→ 初始化或升级项目入口
→ 审核并信任Hook
→ 运行真实探针与安装验真
→ 重启Codex
→ 完成项目初始化确认
→ 新PM接手主线
```

不要在已有PM或Worker对话中执行BEYOND安装维护。安装或升级使用一个新的普通对话，不调用身份 Skill；旧Hook如果仍在运行，不让旧PM承担替换自身护栏的工作。

## 2. 准备v3.1.2

从[v3.1.2正式发布](https://github.com/adubeyond/beyond-ai-collaboration/releases/tag/v3.1.2)取得不可变版本。把完整`模板交付包`放到业务项目根并命名为`beyond-control`，不要把交付包散着覆盖业务文件：

```text
业务项目/
├─ beyond-control/
├─ <原有代码与文档>
└─ ...
```

安装或升级`beyond-control/skills/`中的六个 Skill到当前 Codex Skills目录：

```text
identity-pm
identity-worker
task-design
task-dev
task-test
task-ops
```

升级时必须保留已有控制仓中的`local/`、项目登记、项目事实和`shared/`协同内容；不得用空模板覆盖真实项目资料。安装方式无论是人工复制还是由AI执行，最终都必须通过第5节的逐文件验真，不能只看文件夹名称或模型自述。

需要让AI完成安装维护时，在新的普通对话中使用：

```text
这是BEYOND安装维护请求，不建立PM或Worker，也不恢复业务任务。
请使用正式v3.1.2发布包安装或升级当前项目中的beyond-control和六个全局Skill。
先备份已有入口、Hook和控制仓本机资料；保留项目原生规则、local、projects和shared中的真实内容，不用空模板覆盖。
完成后只报告文件版本与待执行的Hook信任步骤，不宣布项目初始化完成。
```

## 3. 初始化新项目

安装六个 Skill并重启Codex后，在项目根新建对话：

```text
$identity-pm
使用 BEYOND 初始化这个新项目。
```

PM先从磁盘调查，再一次只询问一个当前确实需要、且无法从项目中确认的问题。至少确认项目目标、正式目录和当前阶段需要的开发、测试或部署入口；不存在的事实保持待确认，不凭空填写。

当PM给出入口融合范围后，用户确认用语：

```text
确认以BEYOND的AGENTS.md为主融合，同时保留项目原生规则。只完成项目入口和文档地基，不启动业务任务，不推送远端Git。
```

融合后再进入第5节完成Hook信任与验真。

## 4. 接入或升级已有项目

已有项目不能按空白项目初始化，也不能整目录覆盖。安装六个 Skill后，在项目根新建对话：

```text
$identity-pm
使用 BEYOND 接入或升级这个已有项目。

先只读调查现有AGENTS.md、代码与Git边界、Markdown文档、旧工作台和仍在运行的任务。
不要重新安装，不启动或恢复业务任务；一次只向我确认一个迁移或融合决定。
```

PM应依次让用户确认：

1. 项目根、子项目、重复工作目录和各自Git边界；
2. 哪些旧任务仍在进行，哪些已暂停、已完成或只是待办；
3. 旧工作台怎样迁入当前工作台与历史；
4. 现有产品、架构、开发、测试、服务器、部署、回滚和安全文档继续由哪里承载；
5. 项目根`AGENTS.md`与已有Hook怎样备份、保留和融合；
6. 是否补充本机项目身份及团队协同信息。

用户确认融合时使用：

```text
确认以BEYOND的AGENTS.md为主融合，并完整保留项目原生规则和已有正式文档。
旧工作台先备份，再把真实活动任务迁入当前工作台；已完成和失效内容进入历史，不删除原对话和证据。
本轮只完成老项目初始化，不启动或恢复业务任务，不推送远端Git。
```

初始化结束前，PM必须展示当前主线、活动任务、待办/历史、项目事实入口和仍待确认内容，由用户裁决。最低接入自动生成的文档只能作为候选，不能替代这次人工确认。

## 5. 审核并信任Hook

项目入口融合后，项目根会出现`.codex/hooks.json`和`.codex/beyond-runtime-guard.mjs`。Hook是Codex提供的生命周期扩展机制，BEYOND用它在工具执行前机械区分PM与Worker边界。

在业务项目根启动 Codex CLI：

```powershell
cd <业务项目根>
codex
```

在CLI中输入：

```text
/hooks
```

审核来源确实是当前项目`.codex/hooks.json`后，选择信任并保持启用。项目目录可信不等于Hook脚本已信任；首次安装或Hook内容变化后需要重新审核一次，这不是每个任务都要审批。

如果旧PM对话阻止升级，不要在该对话中反复尝试，也不要长期关闭Hook。退出旧对话，使用第2节的新普通安装对话完成文件更新，再回到项目根CLI审核新Hook。

## 6. 真实探针与安装验真

信任Hook后，在项目根的新Codex任务中运行固定探针：

```text
只执行这一条固定命令并报告退出码，不做其他操作：
node beyond-control/scripts/beyond-control.mjs hook-probe --project-root "."
```

探针必须显示`runtimeProbePassed: true`。随后从项目根运行：

```powershell
node beyond-control/scripts/verify-install-integrity.mjs --installed-skills-root "<Codex Skills目录>" --project-agents "<业务项目根>/AGENTS.md"
```

只有退出码为`0`，并明确说明六个 Skill、控制仓、项目运行内核和真实Hook探针一致，才算安装验真通过。`--content-only`只证明文件一致，不能证明Codex真正执行了Hook。

常见状态：

| 现象 | 判断与处理 |
| --- | --- |
| 文件显示3.1.2，但探针不存在 | Hook尚未信任、未执行或项目根不正确；回到`/hooks`核对来源 |
| Hook已信任但仍加载旧行为 | 完全退出并重启Codex，用新对话复验；不要继续旧PM/Worker对话 |
| 内容验真通过、完整验真失败 | 文件已安装但运行闭环未完成，不能宣布安装成功 |
| CLI没有`/hooks` | 记录`codex --version`和`codex features list`，按兼容性缺口处理 |
| 初始化文档存在但未人工确认 | 只算最低接入，继续第3或第4节，不让PM直接恢复业务 |

## 7. 重启与PM接手

安装验真和项目初始化都完成后，完全退出并重启Codex Desktop。不要继续安装对话或旧PM对话。在项目根新建PM：

```text
$identity-pm
接手当前项目。BEYOND v3.1.2已经完成安装、Hook验真和项目初始化。
请读取当前工作台，只汇报当前主线、活动任务、暂停项和下一步；不要重复创建、启动或恢复任务。
```

用户确认清单无误后，再输入：

```text
恢复当前仍为进行中的原任务。已暂停任务保持暂停，已完成任务不要重新启动。
```

至此才进入正常的PM→Worker业务运行路径。
