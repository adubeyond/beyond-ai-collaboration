# 故障恢复、证据与失败交付

## 何时读取

运行异常、日志排障、服务恢复、回滚、发布失败、环境阻塞归因或详细事故/失败交付出现时完整读取。普通本地预检不进入本文件。

## 判断与分层

依次明确环境、变更、版本基线、证据、风险、回滚和裁决。任何会改变恢复安全性的关键项不清时停在门禁，不执行高风险动作；不使用固定缺项数量代替风险判断。

判断问题属于模板、配置、运行、发布还是恢复层；模板字段齐备不能外推为真实环境可发布，局部服务恢复不能写成整体恢复。

## 回滚与失败阶段

回滚必须同时具备明确锚点、恢复步骤、恢复成功验证和失败交付能力。缺关键项不能说“可安全发布”。

区分发布前检查失败、发布过程失败、发布后验证失败和回滚失败；每阶段保留当前版本/制品、已执行动作、关键输出、服务/数据状态、可恢复入口和下一安全动作。

处置顺序是`停止扩散 → 保存现场和影响范围 → 恢复服务或回滚 → 复验业务与数据 → 收口残留 → 复盘改进`。已经局部发布时必须保存节点、实例或区域的版本分布、流量状态、已执行迁移和外部副作用；这些事实未明前不得继续扩大批次或把局部恢复写成整体恢复。

故障排查先缩小范围，优先执行最能区分当前分支的一个安全实验。环境、配置、服务和任务自有资源问题只有在运维写入边界与恢复授权内才可最小修正并复验；产品实现、设计、测试资产或业务契约问题把证据返回原Worker，由它切换对应方法，当前Worker不得借运维方法或恢复名义修改业务实现。结果与用户、PM 或旧记录冲突时指出事实冲突，不用“再试一次”掩盖环境、权限或回滚缺口。恢复、回滚或重试涉及用户保留检查点时，先交付当前状态和下一动作，等待确认。

## 阻塞归因

把阻塞归为环境缺失、权限缺失、配置缺失、证据缺失、回滚缺失或事实冲突。无法区分时先`不能继续`，提出一个能区分分支的最小调查动作。

优先使用项目已有运行、健康、日志、监控、恢复和回滚入口。命令输出只保留结论与关键证据；环境变更后，只有任务拥有准确路径写入授权时才更新对应项目事实、发布记录或生产运行记录，否则交付建议位置和未写原因。

## 证据与详细输出

- 一手强证据：本轮真实发布前检查、发布输出、健康检查、日志、监控或回滚结果，可支撑对应真实环境结论。
- 一手弱证据：模板、配置、目标文件或索引定点核查，只支撑模板层/阶段性判断。
- 二手证据：口头摘要、转述或旧记录，不能升格为真实发布或恢复通过。

无法取得当前轮证据时说明当前还能确认的范围、最小关键缺口和退回层级。详细失败包按需包含失败阶段、实际版本、完成动作、验证结果、残留风险、回滚状态、证据入口和最小裁决，不强制固定格式。一次事故的时间线、现场和结果写入任务主面或任务契约登记的唯一生产/事故记录；可跨事故复用的稳定检查、恢复步骤、环境或架构事实才按授权归入运行手册、环境事实或架构事实，不能把单次事故流水堆成稳定大手册。运维方法不直接宣称 PM 工作台已经消费结果，也不自行创建长日志文件；正式任务由当前Worker按授权写入准确入口，直接请求由当前基础智能体交付，未授权时保留在当前交付中。
