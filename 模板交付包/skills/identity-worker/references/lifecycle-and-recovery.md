# 异常生命周期与恢复

正式任务出现阻塞领取、取消、暂停恢复、重复实例、来源或路由冲突、事件投递失败、`red`或终态后返工时读取。直接用户任务只在取消、暂停或恢复需要核对现场时读取对应段落。普通任务正常执行和普通终态不读取本文件。

## 1. 先守住真实控制关系

业务任务、执行实例和 PM 已消费状态是三种事实。任务已经取消、暂停或完成，不自动证明实例已经停止；实例已经结束，也不自动证明 PM 已经采纳结果。

正式控制只认任务 ID、版本、执行回合、唯一工作区和平台实际来源。缺少这些事实、来源无法归属或已有其他实例仍在控制任务时，不自造标识、不接管任务，也不创建替代实例掩盖冲突。普通聊天、内部助手或协作实例不能因为看到了任务内容就变成正式任务控制实例。

本文件处理异常，不降低主文件的接单门。阻塞领取、恢复、红灯裁决或返工只能确认谁可以继续，不能替任务补造业务结果、边界、验收、当前放行段、用户检查点、禁止动作或分项授权；主文件接单核验未闭合前仍不得产生副作用。

## 2. 阻塞领取与恢复

平台新建任务的非阻塞创建回执已经完成登记，不再发送`claimed/started`。只有来源不明、用户或平台直接恢复、重复实例、共享写入尚未隔离，或者任务包明确要求登记后才能行动时，才使用阻塞领取：

1. 核对任务身份、当前版本与执行回合、项目与工作区、当前控制实例、共享边界、包装实际注入的`source_thread_id`、普通事件聚合入口和 PM 紧急目标；同时确认主文件接单门已经给出当前放行段、检查点、禁止动作与分项授权。
2. 能证明当前实例是唯一合法候选时，向实际来源发送一次`claimed`或`resumed`，暂停新增动作；平台支持等待时只做一次平台有界等待，等待登记结果。这不是终态，也不产生写入权。
3. 收到登记通过后重新核对当前版本的接单门；仍然闭合才沿原任务继续，不补发`started`，不重新接手项目或扫描全仓。登记通过只确认控制实例，不授权任何缺失动作。
4. 有界等待结束仍无结果，或平台不能保持等待时，保持业务状态不变，记录实际来源、已发送控制事件、等待结果和未获登记事实；停止新增副作用，给当前任务一次真实答复后结束本次等待。平台仍保留实例时记为`等待事件`，只结束当前等待回合；平台不能保留时只说明实例运行现实和恢复条件，不冒充`已关闭`或`失联`。后续外部输入必须先核对登记结果，不重复发送同一领取事件，也不自行轮询或抢占。
5. 身份、来源或控制权不能闭合时，只停止受影响动作并把真实冲突发给 PM；没有可回源目标时直接说明缺口，不冒充已经登记。

发现已有有效实例时保持现场，不并行接管。平台能够回到原实例时由真实控制路径恢复；不能确认原实例已经失效和完成移交时，不建立新执行回合。

正式任务控制实例无消息、等待超出预期、消息发送失败或另一个实例无法联系原实例，都不能让 Worker 宣布原正式实例`失联`。Worker不能判定自己失联；新进入或恢复的实例只保存当前现场，停止可能重叠的写入，并请求 PM、平台观察器或用户从控制面触发一次有界正式控制实例失联核对。没有外部核对结论和工作区移交时，不把“看起来没响应”解释成替补授权。当前Worker自己控制的局部助手失效时，仍由原Worker按[协作与返工作业包](collaboration-and-rework.md)核验、关闭或登记助手失联并建立获授权替补；这不产生新的正式任务控制实例。

## 3. 取消、暂停与重新执行

取消必须来自用户或 PM 的真实控制。收到取消后停止新增动作，保护现场并核对已经发生的文件、Git、服务、环境、数据、生产和费用现实；取消不等于回滚，任何清理或恢复仍需单独授权。

正式任务发送一次`cancelled`停止确认，带上任务身份、实际来源、停止位置、实例状态、现场和已经发生的副作用。只有确实停止并安全释放时才把实例写成`已关闭`；仍在停止、无法确认或已经失联时如实说明。直接用户任务没有 PM 控制目标时直接向用户说明停止现实，不制造生命周期事件。已经释放的实例不为补取消确认重新唤醒。

暂停只来自用户或PM的真实控制，或者任务契约已经预先定义且确实跨越当前执行回合的观察/等待窗口；Worker不能为方便、等待普通结果或释放资源自行制造暂停。暂停时停止会继续产生副作用的动作并安全保留现场。跨回合观察/等待还必须先在任务主面或获授权的正式记录中持久化候选状态、已经观察的时长与事实、下一时间或事件触发、责任入口、证据位置、失败升级和已有回滚授权；缺一项时只交付当前缺口，不能用`paused`掩盖无人负责的等待。

正式任务满足上述条件后发送一次`paused`并释放当前执行回合；直接用户任务只向用户交付暂停现实、下一触发和恢复条件，不制造任务终态。恢复或退回是新的外部输入。用户在同一已登记正式任务线程直接恢复时，若线程、任务主面、唯一工作区和最后终态能够证明没有其他控制实例或共享写入冲突，该线程可以沿用任务 ID、递增执行回合并重新完成主文件接单核验；`resumed`持久化后进入聚合知情，不等待 PM批准。来源不明、从另一线程或实例恢复、原实例失联、重复实例、工作区或共享写入不能唯一确认时，才由 PM或平台阻塞控制路径登记新执行回合，Worker不能自行抢占。直接用户任务沿用当前对话已经确认的目标，并重新核对用户当前授权与检查点。各恢复路径都只刷新授权、代码、Git、服务、环境和数据等可能变化的事实，不无故重建稳定目标。

终态已经成功发送后，原执行回合不可恢复。正式任务返工保留原证据并建立新执行回合：同一已登记正式任务线程收到用户直接返工指令且不存在控制冲突时，可以按上一段非阻塞路径递增回合；其他情况由 PM或平台阻塞控制路径登记。任何路径都不能修改原终态、复用原事件 ID或让旧回合继续。

## 4. 红灯不是终态

`red`只用于需要 PM 裁决的控制、资源、任务边界或共享冲突。发送前核对受影响范围和一手现实；停止可能扩大问题的动作并保护现场，不受影响且仍在当前授权检查点内的安全路径可以继续。

`red`送达后，业务任务仍未完成，当前实例按现实保持`执行中`或`等待事件`，不能仅因消息送达而释放。PM 的实际裁决没有改变业务结果、明确不做、边界、验收、授权、检查点、共享契约、其他任务或主线，且当前实例仍有效时，重新核对裁决与接单门后沿原版本、原执行回合继续。裁决改变任一受控项时，必须先由 PM更新任务版本、授权与检查点，并明确原有效实例接收新版本，或者沿用任务 ID建立新执行回合；Worker不能把红灯回复直接解释成扩权。实例已经失联、关闭或完成明确移交时，只能走新回合。平台无法保持等待时如实报告实例现实和恢复条件，不把资源限制写成任务已经失败。

## 5. 事件冲突与投递失败

事件 ID 与正文一一对应。只有同一事实、同一正文的传输失败重试才能复用事件 ID；事件成功送达后不可撤回或修订。同一 ID 出现不同正文、版本倒退、序号或状态矛盾、来源无法归属、双控制实例或共享写入冲突时，停止自动覆盖和受影响动作，把冲突与一手现实交给 PM；不受影响且安全的授权路径可以继续。

正式事件只归属于任务包装实际注入的来源，不能把祖先、历史或其他任务的 thread ID 当作回源目标。普通进展、阶段消息和任务内变化优先写入平台非唤醒事件队列、任务主面或任务契约指定的持久收件位置，由PM多任务聚合消费。平台只有唤醒消息而没有非唤醒收件能力时，Worker不逐条发送这些普通事件；保留完整事件，由PM下一次有界批量读取取得，不要求高频轮询。立即裁决事件使用平台定向任务消息能力唤醒来源PM。

`paused / failed / candidate_completed / completed`是每执行回合唯一终态回源信号，不归入普通聚合收件箱。收口前只做一次最小工具发现；若冻结为`定向终态消息`且发现`send_message_to_thread`或等价定向任务消息能力，向包装真实注入的`source_thread_id`发送唯一终态，成功后立即给本任务最终答复并释放，不等待消费回执。冻结为`平台完成观察器`时，完整终态保留在正式任务最终结果并由已建立观察器送达；冻结为`明确人工消费`时，完整终态必须保存在任务契约登记的正式任务最终结果或持久终态入口，带上消费责任、读取触发和消费游标/幂等依据后释放。任何模式都不自行建立高频轮询，也不因当前工具变化擅自改换冻结模式。

定向终态发送失败时保留同一事件 ID、完全相同的正文、证据、实际来源和现场；最终答复明确未送达对象与原因后释放，不改发另一状态，不伪造 PM 已收到、已消费或已裁决。`red`投递失败时保持受影响动作停止，并在当前实例可持续时保留等待状态。投递失败不能抹掉已经发生的业务结果。

普通知情事件包括：任务内契约或设计版本变化、同一已登记正式任务线程的非阻塞`resumed`、资源释放和用户直接任务指令的本地生效摘要。它们必须先持久化完整正文，再进入聚合收件箱，不要求PM逐条即时回执。立即裁决事件包括：阻塞`claimed/resumed`、`cancelled`、`red/shared_conflict`、双控制实例、共享写入或契约冲突、用户指令影响其他任务或主线、生产安全和不可逆风险；取消直接改变主线和依赖，必须立即进入 PM。紧急事件可顺带携带同批尚未消费的普通事件摘要，避免随后再次唤醒。

## 6. 收口前核对

发送`paused / cancelled / candidate_completed / completed / failed`前，只核对支撑本次状态变化的事实：业务状态与实例状态是否分开，任务身份、版本、回合和来源是否真实，用户直接指令及其生效范围是否已记录，当前设计/契约路径、任务版本和正文锚点/摘要是否可读且一致，验收与一手证据是否对应，用户检查点或保留决定是否已经按契约解除，Git、服务、环境、数据和发布表述是否符合现场，需要写回的正式入口是否已经按授权更新或明确未更新。

一个执行回合只发送一个收口事件：`paused / cancelled / candidate_completed / completed / failed`。发送成功后立即给出最终答复并释放，不等待消费回执；证据不足就限定结论，不用聊天结论冒充正式状态。`red`、`claimed`和`resumed`是控制事件，可以发生在最终收口之前，不占用这个唯一收口事件。
