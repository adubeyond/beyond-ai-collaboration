# 暂停、恢复与终态异常

只在任务真实暂停或恢复、出现两个控制 Worker、正式任务关系冲突、终态读取异常，或 PM退回完成结果时读取。普通执行、普通失败和正常完成不读取。

## 1. 暂停与终态

暂停原因仍以 Worker 主入口的四类真实原因为准，不在本文件增加状态或原因。

暂停时只停止受影响动作，保存能够恢复的文件、Git和运行现场。正式任务与直接用户任务都在当前任务final中说明已完成内容、唯一原因、恢复条件和现场；正式任务暂停final首行以`已暂停`开头，并按主入口先保存同一份短期回执、再原生回源、最后输出final。

平台没有保留当前final、任务关系与实际正式thread矛盾，或PM明确没有取得本任务终态时，在当前任务最终答复中保存完整结果和准确异常；Worker只按平台来源关系保存一次短期回执并尝试一次原生唤醒，不读取PM忙闲、不等待、不循环、不更换状态、不改投其他thread，也不伪造PM已经收到。若已经提前唤醒却又继续调用业务工具，这次唤醒和旧回执都不能证明任务结束；必须重新稳定现场并用新冻结终态替换该任务pending后再收口。已经发生的业务结果和现场不因控制面异常而消失。

## 2. 恢复与退回

恢复优先沿用原正式任务线程、业务结果、Git/运行现场和已有证据，只刷新授权、代码、配置、服务、环境和数据等可能变化的事实。不重新接手项目、不重建任务包、不扫描全仓，也不重复已经有一手证据的工作。

用户或PM在原 Worker 对话补充决定、资源、授权或返工要求后可以直接继续，不等待 PM批准。恢复回合沿用任务包中的`projectId + taskId`和当前包装中的`source_thread_id`；新暂停或完成仍覆盖为该任务唯一pending并走同一收口。变化影响其他任务、共享对象、主线或高风险边界时，向 PM返回最小影响摘要。

PM退回结果且缺口仍在原范围内时，由原 Worker继续补证据或修复，不建立新任务、新状态或初始化流程。只有业务结果、真实高风险授权或共享边界发生扩大时，才等待对应决定。

## 3. 两个 Worker与来源冲突

同一任务出现两个控制 Worker时，立即停止可能重叠的写入，保留当前现场，并向 PM说明实际线程、正式工作目录、Git/运行现实和已经产生的结果。无冲突的只读调查可以继续。

没有平台或 PM的外部确认时，Worker不能因为原线程沉默、超过预计时间或一次读取/消息失败，就判断原 Worker已经失联并自行接管。旧实例是否停止、工作目录是否移交和替代 Worker是否建立，由 PM依据平台与现场事实处理。

正式任务关系只认平台实际建立的当前thread、项目和任务包装。来源缺失或互相矛盾时，不猜测 thread ID、不调用平台消息绕行；在当前答复保存结果和准确缺口，由 PM或用户恢复真实控制关系。

## 4. 完成边界

正常完成、验收条件和输出使用 Worker 主入口，不在本文件复制。成果仍在临时目录、没有进入正式目标或缺少当前一手验收证据时，不能因为需要释放实例而宣告完成。
