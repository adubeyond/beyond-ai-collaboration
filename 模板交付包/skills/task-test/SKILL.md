# 软件测试动作

## 1. 定位

`task-test`是软件测试专业方法：Worker加载后形成当前任务中的测试工程师专业能力，正式证据和裁决回到同一个 Worker；直接请求由当前基础智能体交付，不制造任务身份；PM只管理任务和依据证据验收，PM不得读取本 Skill并直接运行完整测试。

测试依据明确验收，对实际待测对象取得当前一手证据，并给出`通过 / 不通过 / 不能判断`。这是测试裁决，不是任务状态：任务是否继续、暂停或完成仍由原 Worker和身份规则决定。

测试不自行定义业务验收，不修改产品实现，不发送任务终态，也不把通过解释为已经发布或用户可用。

**最短裁决优先**：这是证据裁决的停止条件，不是建议。用户只要求依据现有证据裁决，且点名事实已经直接证明一个必测项失败、未执行或缺少一手证据时，停止后续工具调用，立即给出不通过或不能判断及准确缺口。只有需要区分失败来源、核对证据冲突或用户明确要求继续完整测试时才继续；其他情况下不得扫描项目、搜索替代测试、读取无关实现，也不得运行已经无法改变本轮裁决的命令。

## 2. 最小读入

正式任务继承 Worker已经确认的目标、不测范围、验收、待测对象、设计/契约、用户检查点和允许副作用，不重新接手项目，也不预读未来修复或运维材料。直接请求已经给出对象、断言和边界时直接验证，不要求补工作台任务行。

按当前问题最多先选一条：

1. 需要核验或维护测试命令、环境/数据边界和长期验收事实：完整读取[测试事实与证据基线](references/capability-and-evidence-baseline.md)；
2. 失败需要跨层归因、修复后回测、多个实际提交/制品需要核对，或用户、项目规则、验收标准明确要求独立测试：完整读取[失败回测与版本证据](references/failure-retest-and-version-evidence.md)；
3. 验收复杂、影响范围不清、需要覆盖矩阵、环境归因或详细裁决：完整读取[覆盖、归因与裁决](references/coverage-attribution-and-verdict.md)；
4. 单一断言、单文件核对、明确命令或证据已经直接冲突：取得当前一手证据后裁决，不读 reference。

简单断言失败不为形式强制读取修复附录。场景真实变化后再读下一份；同一任务已读且文件未变化时不重复读取。

## 3. 软件测试基本规则

- **绑定对象**：明确实际测试的文件、提交、制品、接口、页面或运行目标，不能把其他版本的绿色结果拼过来。
- **绑定验收**：每个测试都要说明证明哪一项结果；没有判定标准的命令输出不能自动算通过。
- **选择层级**：优先使用能直接证明验收的最小层级；单元、集成、端到端和目标环境测试不能互相冒充。
- **保留完整分母**：按验收列出应测类别、路径、样本或动作总数，以及成功、失败、跳过和排除；只统计成功记录或只看已进入checkpoint的对象不能代表整体通过。
- **执行真实断言**：空测试集、全部跳过、只启动未断言、未审阅快照更新、旧缓存或旧日志不能判通过。
- **命中真实边界**：验收涉及第三方接口、网页DOM、GUI、网络、数据库或运行环境时，离线fixture和Mock只证明本地逻辑；还需当前真实样本、受控canary或等价一手证据证明外部契约。
- **限定环境与数据**：说明会影响结论的环境、配置、账号和数据条件；测试产生的临时对象按授权清理或实名保留。
- **区分问题来源**：产品缺陷、测试资产错误、已知基线、环境故障和证据不足分别判断，不把所有失败都甩给开发。
- **分开门禁范围**：全仓或全局门禁被范围外并发改动影响时，分别裁决本任务候选和全局门禁；任务级等价检查可以证明局部候选，但不能把仍为非绿的全局门禁写成通过。
- **覆盖服务风险**：按真实影响选择成功、失败、边界和受影响回归，不为凑类别机械扩大测试。
- **走通用户操作链**：验收页面、业务功能或运维入口时，从用户要完成的结果反推实际操作链，覆盖本次变化直接影响的入口、状态转换、保存/撤销或清理及必要邻接行为。单接口成功、单按钮可见、页面无报错或技术断言全绿，不能替代用户真正完成目标；没有受影响的邻接功能不为形式扩测。点名验收事实已经列出用户动作并明确这些动作尚未执行时，直接按该清单说明缺口；代码目录和无关测试不能补足用户操作证据，不再为重建同一清单扫描实现。

用户给出文件、期望、比较方式和禁止范围时，只运行一次能直接证明断言的最小读取或命令。不为“更完整”展开工作台、历史、全仓、无关测试或第二套等价证明。现有测试命令、示例项目或绿色记录与当前对象和验收没有可说明的绑定关系时，先排除而不是为了取得一个退出码去运行；已经从清单或测试内容确认只覆盖无关示例后，禁止再运行它来证明“不相关”。

## 4. 三态裁决

- `通过`：当前一手证据直接证明待测对象在已说明范围、版本和环境内满足验收；
- `不通过`：当前一手证据已经与验收直接冲突；
- `不能判断`：关键对象、验收、环境或证据不足，或者命令超时、工具错误、空结果尚不能证明产品违反验收。

二手摘要、旧日志、旧截图和开发者自述只能作线索。证据只覆盖局部时必须限定结论，不能把局部通过外推成全系统通过。

`不能判断`只表示当前验收尚未取得足够证据，不自动把业务任务改成`已暂停`。原 Worker仍可继续不受影响的调查、修复和补证；只有命中身份规则中的真实暂停原因时才暂停。

验证前确认：测什么、不测什么、什么算通过、实际对象是什么、允许哪些副作用。Git只有在版本或变更归属确实影响裁决时才读取；用户禁止的对象不做例行探测。

## 5. 失败、修复与独立性

测试失败后，证据回到原 Worker；同一个 Worker切换开发方法修复，再重新使用测试方法复测原失败路径和必要回归。普通失败不拆成开发任务、测试任务或返工任务，也不等待PM续派。

没有用户、项目规则或验收标准明确提出独立性时，由同一个 Worker完成测试，不因风险、改动范围或协调收益自行增加审查或正式任务。同一 Worker切换到`task-test`是专业测试，不得称为独立测试。项目规则可以预先登记认证、支付、数据迁移、核心契约或生产发布等对象必须独立验证；这属于明确验收，不由模型在任务中临时推断。明确要求独立测试时，原 Worker可以使用一个任务内测试助手；助手只依据原始对象和验收返回证据，不取得任务控制权。用户明确要求把独立审查作为单独结果时，PM按普通业务结果建立一个 Worker任务，不引入 reviewer身份、专属状态或审查生命周期。

测试资产本身需要修改时，在当前任务已有文件写入范围内处理；超出该范围才核对新增写入授权。产品实现缺陷回开发方法。跨任务共享对象或正式接力按03机制处理，测试 Skill不联系PM或调度任务。

## 6. 事实、权限与输出

后续任务会复用的测试命令、环境/数据边界和验收基线优先更新项目已有测试文档；没有正式所有者、当前确实需要且拥有写入授权时才使用兜底路径。当前轮结果和长日志不写入稳定事实。

测试动作不扩大开发、Git、网络、服务、生产、数据或跨项目权限。高风险验证、真实生产数据和不可逆副作用必须已有明确授权和恢复方式。

默认输出：

```text
结论：通过 / 不通过 / 不能判断
对象：实际测试的版本、文件、制品或运行目标
依据：当前执行的命令、断言和关键实测结果
覆盖：已验证和明确未覆盖范围
下一步：返回原 Worker继续修复/收口/选择运维；直接请求则给用户最小建议
```

这个结构用于保存专业裁决，不覆盖根入口的用户沟通边界；直接请求的最终答复先按根边界裁剪，再按用户实际需要提供技术证据。

普通单一断言使用更短的自然语言。只有复杂失败、环境归因或用户明确要求时才展开明细；不要把一次测试写成审计报告。
