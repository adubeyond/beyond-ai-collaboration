# 覆盖、归因与裁决

## 何时读取

验收包含多条链路、影响范围不清、需要覆盖矩阵、证据不足、环境故障归因或详细失败/不能判断报告时完整读取。单一明确断言不进入本文件。

## 专业判断

依次明确目标、变化、覆盖、证据、风险和裁决。任一缺口已经使当前验收无法判定时给`不能判断`并指出最小补齐条件；不影响当前裁决的未知项只进入未覆盖风险，不用模糊鼓励代替结论。

先判断当前最需要证伪的风险属于业务结果、设计、实现、契约、联调、兼容、回归、测试设施还是环境，再选择能观察它的最低充分测试层级；不要默认一开始就跑全量命令，也不要因低层测试更快就用它替代跨边界证据。

每个验收项先写成`给定条件 → 动作 → 可观察结果`，明确什么结果算对、什么反例会推翻结论。判定标准优先来自用户可观察结果、正式验收、业务规则和边界契约；实现分支、内部调用顺序和开发自述只能帮助定位，不能反向定义正确性。

## 覆盖矩阵

复杂验收按需记录`验收/风险 → 路径与变体 → 判定标准 → 测试层级 → 环境与数据 → 实测证据 → 当前裁决`。矩阵是防止遗漏和夸大结论的判断工具，不要求固定表格，也不把每个格子机械组合成用例。

矩阵先逐必验项给三态，再合成总裁决：任一必验项有直接反证时整体`不通过`；没有失败但仍有必验项证据不足时整体`不能判断`；只有全部必验项通过且没有关键未覆盖项时整体`通过`。失败与未覆盖可以同时存在，不能因已有失败就隐藏尚未执行范围，也不能用部分通过稀释必验项失败。

按真实影响选择主成功、空态、失败、边界输入和受影响回归。涉及前后端契约、多执行线交接、状态机、鉴权、并发写入、重试、批处理、迁移、发布对象或危险命令门禁时，再补契约一致性、接力回写、权限隔离、状态转换、幂等/部分失败、兼容和风险门禁。用户可见界面根据实际风险补键盘操作、可访问性、响应式、浏览器/设备、加载/错误/空态和关键视觉检查；不涉及的维度不为形式完整强行加入。

“只测成功路径不算闭环”适用于真实功能或缺陷验收，不适用于题面本身只有一个原子断言的只读核对。覆盖必须服务验收，不为凑类别增加无证明力的动作。

覆盖率、用例数和“全绿”只能说明对应测试集合的执行情况。除非正式门禁定义了算法、阈值、排除项并且本轮实际测量，否则不能用行覆盖、抽样结果或单个环境宣布“全面覆盖”。参数、角色、区域、浏览器、运行时或数据规模只执行了部分组合时，明确已测代表和未测风险。

## 测试层级、替身与独立性

优先复用项目正式入口，并选择能直接观察风险的层级：

- 纯规则和局部转换可由单元或属性测试证明；模块边界、序列化、数据库和协议需要契约或集成证据。
- 真实用户主链路、浏览器交互、多服务接力和部署制品行为需要相应端到端、联调或目标环境验证；不能用被 Mock 的局部测试替代。
- 性能、安全、数据一致性、迁移、恢复和生产行为必须使用与结论匹配的专门方法、数据规模、环境和授权。

使用 Mock、桩、虚拟时钟、假数据或模拟服务时，说明被隔离边界、替身契约来源和它不能证明什么。替身与真实契约无法交叉核对、核心行为被替掉或断言只绑定内部实现时，该证据不能支撑对应业务验收。

任务要求独立测试时，独立测试助手必须从验收和原始制品建立自己的判定路径，不接收开发者的期望结论，不只重复开发自测命令。它可以复用正式测试资产，但至少独立核对判定标准、待测版本和关键证据；结果只返回原 Worker。

## 证据质量

- 一手强证据：当前轮真实命令、测试、日志、页面、接口响应或与版本直接绑定的快照，可直接支撑对应验收。
- 一手弱证据：定点文件核查、结构化人工检查或正式索引交叉核对，可给阶段性判断但要写未覆盖风险。
- 二手证据：用户、PM、执行者摘要或旧记录，只能作线索，不能单独判通过。

“一手”不自动等于“强”：输出必须能证明测试确实执行、对象和版本正确、判定标准有效、环境和数据足以代表当前结论，并且通过或失败的原因可解释。空测试集、被跳过用例、只启动未断言、无审阅快照更新、缓存命中或旧制品执行，即使退出码为零也不能判通过。

验证命令失败但没有取得可解释断言或直接反证时，只能说明本轮未完成，结论为`不能判断`。只有当前待测结果的一手证据与验收直接冲突才是`不通过`。命令全部成功但覆盖或判定标准不足时，同样只能限定范围或给`不能判断`，不能用绿色输出填补关键证据缺口。

超时、卡死、日志停止增长、进程被杀或外部中断本身只证明测试执行没有正常闭合。详细证据应保留最后有效进展、已运行断言、进程/服务/队列状态、关键日志入口、停止动作和环境残留；只有这些证据同时直接证明产品违反验收时才判`不通过`，否则判`不能判断`并给一个信息增益最高的补齐动作。

## 缺陷归因

把问题归为业务/设计缺口、实现缺陷、契约漂移、测试资产缺陷、测试数据污染、Flaky/竞态、已有基线、证据缺口或环境阻塞；不要替任何一方强行找借口，也不要把所有问题都甩给开发。

归因必须来自能区分分支的一手事实。例如用同条件对照区分本轮回归与基线，用最小真实边界实验区分产品缺陷与错误 Mock，用干净数据或隔离环境区分状态污染，用多次带差异记录的执行定位不稳定来源。尚不能区分时给`不能判断`，只列下一项信息增益最高且在授权内的最小实验；取得结果后重新裁决，不用固定重试次数、随意增大超时或换环境直到通过。

优先使用项目已有测试、构建、lint 或联调入口。无法运行时记录原因、替代证据和未覆盖风险；多项目联调记录来源、目标、接收状态和一手联调证据。

## 详细裁决

裁决同时给出结论、问题层级和建议流向：

- `通过`：把限定到对象、版本、环境和覆盖范围的证据交原 Worker；是否收口或选择已授权运维方法继续服从原授权和用户检查点。
- `不通过`：把直接冲突、复现条件和问题层级交原 Worker，由它决定切开发修复、切设计补契约或按控制关系处理环境/协同问题。
- `不能判断`：指出缺少的唯一关键证据/环境与最小补齐动作。

详细裁决按需说明待测对象和稳定版本锚点、正式验收/设计/契约路径与版本、验收与不测范围、测试层级、环境/数据/关键变体、已执行与未执行路径、逐项三态和测试总裁决、实测结果、证据位置、基线或设施问题、清理/保留结果、残留风险和建议流向。每一项结论都应能追到对应证据，不得只给“已测、全绿、基本通过、覆盖充分”等空标签。

当前轮证据只写任务授权的任务入口或证据位置；需要当前工作台控制摘要时由 PM 消费后更新。没有相应写入授权时只交付证据和未写原因，长日志也不得为方便另建记录文件。测试 Action和独立测试助手不发送任务终态、不直接要求 PM采纳，也不因三态裁决改变任务契约或用户检查点。
