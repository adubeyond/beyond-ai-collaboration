# 修复回测、候选集成与交接

## 何时读取

当前已出现可复现失败、需要开发修复回测、多个隔离候选、唯一集成、跨实例移交或高风险专项时完整读取。普通单一断言不进入本文件。

## 失败与修复回测

测试动作负责当前裁决和证据，原 Worker 始终管理修复循环：

1. 当前测试动作取得能定位待测版本、环境、数据和断言的失败证据，判断更接近业务/设计、实现、契约、测试资产、基线、Flaky还是环境问题，并返回原 Worker。
2. 测试 Action和独立测试助手不改变正式验收、任务状态、检查点或写入范围，不启动开发实例，也不请 PM 代派。
3. 边界内实现缺陷由原 Worker 切回开发方法，或按既有授权启动一个写入边界明确的开发助手；测试方法不得直接修改产品实现。
4. 修复后，原 Worker 核对新待测版本、可用 diff或变更清单、自测结果和实际影响，再选择测试方法。
5. 没有独立性要求时由同一 Worker 复测；任务要求独立测试时，把新版本交回当前唯一独立测试助手。复测原失败路径和必要受影响回归后，证据再次返回原 Worker，由它决定下一动作。

测试阶段本身不要求新建实例。只有正式验收要求独立性，或独立证据的收益高于协调成本且原 Worker按协作规则获准时，才使用一个局部独立测试助手。助手默认复用到本轮独立测试闭环结束；失效时由原 Worker先关闭或登记失联，再建立一个可定位替补，任何时点只能有一个助手承担当前独立测试责任。不得新建平行测试任务、开发任务或“返工任务”；修复线自测不能替代任务要求的独立测试。

业务契约语义、真实权限、高风险操作或用户保留的修复上限需要改变时，测试动作把事实返回原 Worker。只影响当前任务且需要用户决定时，由 Worker在当前正式任务对话直接取得决定；资源、实例、跨任务优先级、共享所有权、写入边界重分配、主线或安全影响由 Worker交 PM协调，测试动作不直接联系用户或 PM。有效任务版本、授权、验收及其正文锚点更新后，仍由原 Worker决定继续测试、修复或停止。

修复与回测服从用户约定检查点。用户要求每轮修复后查看、一次只验证一个缺陷或本轮回测后先确认时，当前测试结果返回原 Worker后到达检查点；Worker交付当前证据并停止，不直接开始下一轮修复或扩大覆盖。

## 测试资产缺陷与不稳定失败

先保持产品待测版本不变，取得能够区分产品、测试资产、数据污染、Flaky和环境的最小证据。不得把“重跑通过”直接归因为产品已修复，也不得在没有对照时把失败都归为测试问题。

- 测试代码、fixture、Mock、快照、测试配置或脚本本身错误时，记录错误判定依据、受影响用例和它过去产生的假阳性或假阴性风险。只有测试资产准确路径获得写入授权时，测试动作才能修正；修改后既要证明测试设施恢复有效，也要在未改产品候选上重新运行目标断言。
- 测试资产写入未授权、问题涉及公共测试契约或修改会影响其他任务时，只把证据和建议改点返回原 Worker；测试 Action和独立测试助手不借“修测试”扩大写入或绕过共享所有权。
- Flaky调查记录每次待测版本、环境、数据、次序、时长和实际差异，优先控制时间、随机、并发、网络、缓存和共享状态。固定等待、无限重试、提高重试次数或单纯扩大超时不能作为修复证据。
- 超时或卡死调查先保留最后进展、进程/服务/队列状态和环境残留，再由原 Worker按授权决定终止、清理、调整观察或补环境；不得让独立测试助手无限等待，也不得清理非本轮创建或归属不明的对象。
- 项目已有正式隔离或 quarantine 机制时，只能按其授权和退出条件使用，并明确被隔离风险和负责人；隔离用例不等于产品通过，也不能静默从验收门禁消失。项目没有正式机制时不自行发明。
- 修复原失败后出现新的失败时，先判断它是受影响回归、隐藏依赖、测试污染还是独立基线，不因原缺陷已修复就忽略，也不自动把所有新失败都归给当前变更。

## 候选与唯一集成

同一业务结果拆成多个隔离候选时：

- 每个候选的证据绑定其唯一版本、工作区、配置和制品，不把不同候选的绿色结果拼成一个并不存在的“组合通过”。
- 候选任务只负责原失败路径、定向测试、受影响回归，以及证明候选可集成所需的构建、契约或静态检查；候选通过不能证明最终集成结果通过。
- 唯一集成任务在其授权包含相应范围时负责核对实际合并后的版本、跨候选契约、共享测试资产冲突、必要全量或发布级回归，并在最终候选提交或制品上完成已授权的发布前验证。
- 涉及安全、数据一致性、迁移、鉴权或其他高风险面时，不得降低安全、数据一致性、迁移或鉴权专项验证强度。
- 只有影响范围无法可靠界定、候选修改全局共享基础或项目正式门禁明确要求时，候选才追加全量测试，并记录重复全量的必要理由。

当前任务契约点名`候选 / 唯一集成 / 单任务`责任和最终发布门禁。缺少该字段时，原 Worker按实际变更范围补齐当前测试责任；涉及跨任务所有权、共享边界或发布授权时按既有控制关系取得决定，不把“测试越多”直接等同于证据越强。

## 交接与收口

跨实例交接只传原业务任务和版本、原 Worker、独立性要求、最小测试包、待测版本、原始制品、当前失败、已执行与未执行范围、正式证据位置和关闭条件，不传开发者预设结论或整段聊天。接收者先核对对象与证据是否匹配；无法匹配时给`不能判断`，不得沿用原结论。

正式任务的测试结论只回原 Worker，由它根据原授权、用户检查点和当前证据决定继续修复、收口或选择运维方法；直接、清晰的用户测试请求由当前智能体直接向用户交付，不制造 Worker或 PM关系。已预授权运维路径、当前检查点允许继续且用户没有保留验收时，测试通过才可能进入发布前检查；未授权生产时不得把“测试通过”解释为允许发布。终态、生命周期和 PM 事件由 Worker与身份 Skill负责，测试动作和独立测试助手不另造控制事件、不直接向用户或PM交付任务状态。
