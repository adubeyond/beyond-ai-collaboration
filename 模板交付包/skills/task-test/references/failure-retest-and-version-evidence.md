# 失败回测与版本证据

只在失败需要跨层归因、修复后回测、多个实际提交/制品需要核对，或者需要独立测试闭环时完整读取。普通单一断言直接给出裁决，不进入本文件。

## 1. 失败与修复回测

1. 测试方法返回可复现失败、实际结果、验收依据和必要归因；
2. 原 Worker判断切开发、设计或补环境事实，不由测试 Skill重新派单；
3. 修复后核对新的待测文件、提交或制品，避免继续测试旧对象；
4. 重新运行原失败路径和真实影响需要的回归；
5. 新证据再次给出`通过 / 不通过 / 不能判断`。

普通修复回测不新建平行测试任务、开发任务或返工任务。用户设置“每轮修复后确认”等检查点时，结果回原 Worker后停止，不越过检查点继续修改。

## 2. 产品、测试资产与环境

先保持待测产品版本不变，用最小对照区分产品缺陷、测试代码/fixture/Mock错误、数据污染、不稳定测试和环境故障。

- 修改测试资产必须有准确文件范围的写入授权；修改后既证明测试设施恢复有效，也重新验证未改产品对象；
- 不稳定测试记录版本、环境、数据、次序和实际差异；固定等待、无限重试或只增大超时不能作为修复证据；
- 超时或卡死先保留最后进展和环境残留，再由原 Worker按授权终止、清理或继续观察；
- 正式隔离机制只能按既有授权和退出条件使用，被隔离用例不等于产品通过。

## 3. 多个待测提交或制品

实际存在多个提交或制品时，分别绑定其代码、配置、环境和证据，不把不同对象的绿色结果拼成不存在的“组合通过”。

每个对象先验证原失败路径和受影响回归；最终只在明确接收的提交或制品上执行需要的集成、全量或发布级回归。只有影响范围无法可靠界定、修改共享基础或项目正式门禁要求时才追加全量测试。

## 4. 独立测试

独立测试助手从验收和原始待测对象建立自己的判断，不接收开发者预设结论，也不只重复开发自测。结果只返回原 Worker。

没有独立性要求时不增加助手。需要独立性时同一闭环只保留一个责任明确的测试助手；它不修改产品实现、不改变任务状态、不联系PM，也不创建新的助手或任务。

测试结论回原 Worker，由它继续修复、收口或选择运维方法。测试通过不产生发布权限。
