# 需求确认、设计文档与实施衔接

用于新业务任务开工前确认、正式设计文档、重大设计变更和反复无进展诊断。已批准设计内的普通细化不重复加载，不把每个编码、测试步骤当成新的业务任务。按是否改变已批准的业务范围、公开契约、验收、权限或关键技术路线判断，不按按钮、字段或代码量判断；恢复已有明确预期的缺陷修复沿原授权继续。

## 0. 讨论与确认

PM先核对当前相关资料与实现，带着业务理解、推荐做法和取舍与老板讨论；直接请求由当前对话承接。每轮聚焦必要决定，讨论次数由内容决定，不凑轮数，也不把可调查的技术细节交给老板填问卷。确认前只在授权内调查、写设计；需要实验则先说明并取得实验范围授权，不能借实验开发正式功能。

需求说明（PRD）回答用户、完整流程、范围与不做事项、数据来源、权限、异常及可观察验收；技术设计回答复用与改动位置、模块/接口/数据、技术栈和中间件选择及理由、失败处理、验证与交付。沿用已有技术栈也写明依据，不要求每次重新选型。性能要求说明目标值、负载、测量条件及确认来源；未知值先给建议或调查，不虚构承诺。只展开当前任务相关内容，不补整套项目模板。

最终提请开发确认前按第5节完成独立模型审查与意见核实，展示本轮方案、重要取舍及剩余未决项；中间讨论和展示草案不以审查完成为前提。确认须对应需求/设计的路径、章节、修订和实现范围，并保留可追溯的用户原话或消息入口；时间或提交号可标识修订，不为此新增状态系统。用户对刚展示且范围明确的方案说“可以，开始开发”可以构成批准，不强求固定句式；沉默、审查通过、旧方案批准或孤立的“继续”不能自动批准不同方案。若材料未变，用户已明确确认并授权开发，不重复索要同一批准。老板明确免除讨论或审查时记录其指定的适用范围与条件；本次例外不自行泛化为长期默认，明确的跨任务授权也不逐任务重问。

在用户确认后，原Worker连续实施、测试及已授权交付；PM不逐步骤续批。草案阶段已获开发批准但默认审查尚未完成时，先说明并沿已有授权补完审查；方案未变不重问，实质改案才确认受影响部分，不能把“开始开发”默认为免审查。用户只批准设计时仍不开发。确认是业务内容检查点，不增加任务状态、回执或唤醒规则。

## 1. 唯一活动设计文档

已获准落盘的业务需求与设计不能只留在聊天、工作台摘要或任务卡中。已有有效的项目/子项目文档入口和事实索引时直接复用；入口缺失或冲突时，读取当前项目根`AGENTS.md`映射的项目文档入口，定位本结果相关资料。然后确定：

```text
已有正式设计入口或唯一新路径
文档服务的模块、业务结果和消费者
需求与技术设计各自的正文/章节及相互引用
谁负责在实施期间更新
内容被替代或不再适用后的入口与历史处理
```

优先复用项目已有设计、架构或契约文档。没有承载者且任务拥有写入授权时才新建；不得使用“最终版、最新版、修订版”等平行文件制造多个真值。

任务与工程文档分别维护：任务保留本轮目标、范围、验收、动作与反馈，引用模块需求/设计的适用修订和章节，不复制正文；同一适用范围内的设计只保留一个正式所有者，可由需求、设计文件或既有文档的不同章节组成，并由一个入口串起。模块文档可服务多个任务，一个任务也可引用多个模块。设计文档所在目录只承载设计正文及其直接附件，不作为后续开发、测试、发布或运行证据的通用工作区；这些证据回到当前任务或项目已有的对应所有者。

## 2. 设计正文

围绕同一个完整业务结果，把业务规格、技术设计和验收例子接起来；这是内容的组织方式，不要求三份文档、固定表格或一页一个任务。已有正文明确时链接对应章节，只补本次缺口。

- **业务规格**：先说用户要得到什么、当前行为和明确不做，再沿实际操作或调用流程写清输入、输出、规则与异常。有界面时展开影响结果的字段、选项来源与可选值、默认值、组合关系、排序及状态保留；动态选项说明产生规则，不抄一份易过期的全集。无界面的服务或脚本围绕调用者、处理规则和业务副作用展开，不套页面格式。
- **技术设计**：逐项说明上述业务行为由哪些现有模块、接口和数据承接，哪些已具备、哪些需要改；保留主链路、模块职责、读写方向、共享对象、字段语义、状态、错误、兼容、实现位置、依赖与推荐顺序。业务要求与现有接口不一致时，提出对应改动或明确的过渡取舍，不让执行者自行降低目标，也不把旧技术描述一律保留。
- **验收例子**：给出具体前置条件、操作或输入、预期结果及相关反例，说明测试入口与判定依据；既检验用户完成目标，也检验必要的接口、数据和兼容约束。性能沿用已确认的指标与测量条件，不以“页面可见”“接口成功”代替业务通过。发布、观察和回退路径按实际涉及范围保留，或说明本次为何不涉及。

“符合Demo”“沿原规则”可以指向已有依据，但不能代替本轮仍未说清的关键口径。先核对决定当前方案的资料与实现，区分已确认目标、Demo表现、当前实现和候选；提取到的临时默认值、模拟数据或旧行为不自动成为目标。冲突只核对受影响项；已有明确决定时沿原决定处理，不因Demo或旧实现不同而重新索要确认；确需改变已定方案或尚未决定的业务取舍才沿第0节讨论，不为填满模板全项目调查。

业务描述保留在产品或模块正文，字段类型、接口参数等详细定义引用唯一契约，不复制第二套定义。有界面且已有原型时，用少量能区分业务理解的真实或脱敏样例对照操作流程；例如一个报价主体包含多家公司时，列表、详情、统计是否仍按同一主体计数。原型暴露的规则缺口回到需求正文核实，已确认规则反过来修正原型与契约；视觉可用不代表真实数据链路已交付。不因此强制新增原型、UI角色或任务。需要示例时，从当前项目根`AGENTS.md`映射的控制仓读取`docs/AI编程协同机制/模板/产品设计与契约基线模板.md`的“页面内容与字段责任”一节；用户Skill目录不是项目控制仓。仍需决定的取舍、风险和未知项如实保留，不用凑齐章节冒充设计完成。

实施切片按可验证结果拆，不按设计、开发、测试角色拆，也不机械切成固定时长。在已有阶段方案或设计正文中，把本阶段结果连回整体目标，并保留仍未覆盖的目标；任务仅承接本次获准范围，不因整体目标更大而自行扩项：

```text
整体目标与本阶段结果 / 涉及位置 / 前置依赖 / 实现要点 / 验证方式 / 完成条件 / 尚未覆盖范围
```

## 3. 与实施连接

需求和技术设计已确认且原任务已授权开发时，同一个 Worker切换到开发方法继续，不建立设计交接任务，不等待PM续派。执行者开始前实际读取任务所指当前正文与必要直接依赖，不能只读派单摘要；修订不匹配时仅核实受影响差异。

不改变业务、公开契约、验收或权限的实现细节，由原Worker在授权内更新对应正文后继续；涉及业务范围、字段语义、外部接口、权限、验收或关键技术路线变化，PM先核实影响并取得用户对受影响部分的确认，其他不冲突工作继续。旧批准不能覆盖新范围，不能靠把文档改成错误实现来消除失败。

PM维护需求、取舍与确认来源，执行者随实现更新技术设计、契约和必要实施记录；限于已授权文档范围，共享正文保持明确写入者。同一文件当次只由一个写入者维护：PM将获准设计交给Worker后不并写，其他人的修订交当前写入者合入；不靠分章节掩盖同文件冲突。保留已确认目标、已定方案和当前实现的区别，记录实质变化的原因及代码/验证入口，不逐命令写日志或另建强制总结。每项交付对照当前获准验收，未满足项如实保留，不用局部完成替代业务结果。

设计结束时只提供一个可消费入口：正式文档路径与相关章节/修订、本阶段获准结果及尚未覆盖范围、决定实现或验收的样例与唯一契约入口、仍会阻断实现的未决项。接口有生产方与消费方时点明各自维护或消费哪份原文，不另抄字段表。原 Worker继续实施时直接使用该入口；PM或另一个正式任务消费时只传这份最小摘要，不复制设计正文；资料读取与更新沿项目工程资料指南处理。跨任务关系按03机制处理，设计 Skill不创建任务、不分配Worker，也不承担消息中继。

## 4. 历史回收

任务完成、取消或被替代，不等于模块需求与技术设计失效。仍有效的目标、契约、架构和已定但未实施方案保持原位；即使当前没有执行任务，也继续作为后续工作的依据。

任务结束时把过程材料中的稳定结论写回原所有者，只回收不再活动的任务过程与临时材料。工程正文确已被替代或不再适用时，再记录替代关系、修正当前索引和直接引用，并按已有授权处理历史；没有移动授权就在原位注明历史性质。不为归档另建总结、复制正文或批量搬目录。

移动、删除和合并仍服从用户授权，不能借归档丢弃尚未验收的设计或有效契约。

## 5. 多模型审查与无进展诊断

新业务方案默认由主设计者加一个不同模型的审查者讨论；重大分歧或复杂关键问题再加第三个，不固定所有任务跑三份。审查者先独立阅读用户原话、适用的原始资料、事实与未知项、候选方案和约束，不只接收主模型结论；指出哪些关键业务内容仍需执行者猜、哪些与依据冲突、哪些技术衔接或验收不能支撑目标，返回具体问题、依据、影响、最小调整与验证办法。PM核对原始证据并融合，业务取舍仍由老板决定，不以票数定真伪。不提供凭据、无关业务数据或整个私有仓库。

同一问题连续两轮有针对性的修复仍失败，且没有新的有效证据时，停止重复原猜测的盲改，进入异模型诊断；关键假设被证据推翻时可提前进入，有新定位证据时不机械凑次数或停工。原执行者提供预期/实际、最小复现、已试方法及结果、版本/约束和未知项；协助者只读分析，由原执行者选取能区分原因的验证，再实施并回测。出现新证据或尚未解决的重要分歧才续审，不无限互评。权限、环境或必需业务决定缺失不能靠换模型绕过。

审查/诊断是原任务内辅助，不创建新的正式任务或源码写入者，也不自动改变任务状态。复用已获授权且可用的模型入口；CLI调用与结果处理按项目根映射的`04-CLI目标协作机制.md`，不另写通知、等待或回调流程。核对显式请求的模型标识，不能把不同CLI或指向同一模型的简写别名算成异模型；分别记录请求与返回报告，不能据此保证网关背后的真实身份。汇报说明身份核实边界；缺少返回标识时只称已请求该模型，不称已证实异模型审查。模型选择服从当前策略、用户锁定与预算，不修改模型矩阵或全局配置。

模型不可用时如实记录审查未完成，继续允许的调查和方案整理，不伪称已审查，也不静默回退成同一模型；必要时仅请老板决定替代模型或明确审查豁免范围，不冻结无关任务。没有外部模型条件的项目仍可使用BEYOND，由用户明确选择单模型路径并按第0节记录适用范围，不为它安装CLI、索要已存在的凭据或越过权限。
