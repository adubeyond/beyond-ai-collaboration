# 架构、取舍与P0作业包

仅在原 Worker 已经选择设计方法，且当前属于标准/重大架构、新系统、主链路重构、多项目边界、数据迁移、P0止血或真实技术取舍时完整读取本文件。本文件只产出架构判断、取舍和可执行设计，不建立任务身份，不改变用户检查点、任务授权或生产控制关系。

## 设计规模

- 标准设计：用于新功能、跨模块、跨执行线或真实技术取舍。先调查现状，再比较会改变决策的方案，说明推荐理由、迁移成本、风险和可逆性。
- 重大设计：用于新系统、主链路重构、多项目边界、数据迁移或高风险架构变化。首轮先确认一个首要业务目标或不可接受结果；尚未确认时只形成`继续设计`和一个会改变方向的最小决定项，不倾倒完整架构或技术清单。直接用户请求由当前智能体询问用户；正式任务把决定项返回原 Worker，由 Worker按既有控制关系处理。

复杂项目按`主链路 → 能力 → 模块 → 当前执行切片`逐层拆解。总设计保持稳定，阶段设计滚动细化；不按人员方便随意切块，也不把所有问题扩成总架构重做。

## 架构判断顺序

1. 明确首要业务目标、现有系统基线和不可接受结果。
2. 画出用户/外部系统、输入、状态变化、输出和责任主体组成的主链路，明确系统与信任边界。
3. 划定模块职责、依赖与读写方向、数据所有者、生产者、消费者和拍板人。
4. 写明关键数据不变量、状态转换、原子/并发边界以及部分失败后的真实状态。
5. 冻结当前阶段必需的接口、字段、状态、错误、事件、文件或命令契约，并确认唯一正式位置和适用版本。
6. 根据当前风险给出可判定的安全、隐私、可靠性、性能/容量、资源、可观测性、兼容性和恢复约束；没有依据的量化目标保留为待核对，不能编造。
7. 比较真实方案并选择最小可逆路径；明确迁移、兼容窗口、回滚锚点、验证范围和旧路径退出条件。
8. 把每个进入范围的设计项映射到事实来源、受影响实现和可观察验收，形成开发能够直接消费的最小设计输入。

遵守专业取舍：顺现有结构、主链优先、边界先于复用、简单优先、可验证优先、只预留已经看得见的扩展点。职责未稳定前不抽公共层；没有当前证据时不新增基础设施。

设计机制必须与失败模型相匹配：非幂等副作用不能靠无界重试恢复；跨系统操作不能用一个本地事务名称掩盖部分成功；异步链路要说明超时、取消、重复消息、积压和恢复；缓存要说明权威数据、失效和一致性边界；性能方案要说明目标规模、瓶颈证据、容量上限和降级行为。当前设计未涉及这些机制时不强行加入，但一旦使用就必须闭合其成立条件与失败现实。

## P0止血

P0缺陷先设计一个可回滚止血片：

```text
当前用户主链路：
最小改动边界：
验证入口：
回滚锚点：
根因治理后续：
```

历史清理、迁移、批量治理和新基础设施默认不能成为主链恢复的前置条件；只有一手证据证明不可分时才并入P0。止血片不得静默改变正式契约、扩大生产权限或把临时实现冒充长期架构；必须写明临时机制的触发、观测、回滚和退出条件。设计完成后把止血边界、验证入口、回滚锚点、风险和仍需决定项返回原 Worker；由 Worker在当前检查点和分项授权内选择开发或运维方法，设计 Action不得自行实施、发布或宣布主链已经恢复。

## 方案收敛

只比较业务效果、复杂度、迁移成本、风险、可逆性等会改变决定的维度。没有实质差异时直接给推荐方案，不凑选项。可以采用可逆默认值时标成假设并写验证点；真正需要业务取舍时只形成一个最小决定项。直接用户请求由当前智能体询问用户后继续；正式任务返回原 Worker，由 Worker取得有效决定并更新当前任务理解后，设计方法才沿原任务继续。
