# 架构、取舍与P0作业包

仅在标准/重大架构、新系统、主链路重构、多项目边界、数据迁移、P0止血或真实技术取舍时完整读取本文件。

## 设计规模

- 标准设计：用于新功能、跨模块、共享契约或真实技术取舍。先调查现状，再比较会改变决策的方案，说明推荐理由、迁移成本、风险和可逆性。
- 重大设计：用于新系统、主链路重构、多项目边界、数据迁移或高风险架构变化。首轮先确认一个首要业务目标或不可接受结果；尚未确认时只说明仍需收敛，并提出一个方向问题，不倾倒完整架构或技术清单。

复杂项目按`主链路 → 能力 → 模块 → 当前实施切片`逐层拆解。总设计保持稳定，阶段设计滚动细化；不按人员方便随意切块，也不把所有问题扩成总架构重做。

## 架构判断顺序

1. 明确首要业务目标、现有系统基线和不可接受结果。
2. 画出输入、状态变化、输出和责任主体组成的主链路。
3. 划定模块职责、读写方向、生产者、消费者和拍板人。
4. 冻结当前阶段必需的接口、字段、状态、错误、事件、文件或命令契约。
5. 覆盖当前规模需要的失败恢复、一致性、权限、性能和可观测性。
6. 比较真实方案并选择最小可逆路径；明确迁移、回滚和验收。

最终用业务语言说明推荐理由，并给出实现、测试和发布/回退路径；不涉及发布时明确写不涉及。

遵守专业取舍：顺现有结构、主链优先、边界先于复用、简单优先、可验证优先、只预留已经看得见的扩展点。职责未稳定前不抽公共层；没有当前证据时不新增基础设施。

## P0止血

P0缺陷先切出可回滚止血片：

```text
当前用户主链路：
最小改动边界：
验证入口：
回滚锚点：
根因治理后续：
```

历史清理、迁移、批量治理和新基础设施默认不能成为主链恢复的前置条件；只有一手证据证明不可分时才并入P0。止血片不得静默改变正式契约、扩大生产权限或把临时实现冒充长期架构。

## 方案收敛

只比较业务效果、复杂度、迁移成本、风险、可逆性等会改变决定的维度。没有实质差异时直接给推荐方案，不凑选项。可以采用可逆默认值时标成假设并写验证点；真正需要业务取舍时只问一个问题，回答后沿原设计继续。
