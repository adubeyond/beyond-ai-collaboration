# 架构/设计动作

## 1. 定位

设计把用户目标收敛成能够实现、测试和交付的方案。`task-design`是专业方法：Worker加载后形成当前任务中的技术设计能力，正式结果回到同一个 Worker；直接请求由当前基础智能体交付，不凭空建立任务身份；PM只用下述轻量模式形成业务任务契约，不替Worker选择实现、测试或发布方法。

设计动作本身不编码、不宣布测试通过、不执行发布，也不扩大文件、Git、环境、数据或生产授权。

## 2. 最小读入

正式任务继承 Worker已经确认的目标、范围、验收、正式目录、用户检查点和相关事实入口，不重新接手项目。直接请求只读目标现状和必要依赖；PM轻量模式只使用其接手阶段已读事实和本结果直接相关的当前所有者，不重新扫描项目。除非用户明确要求接手主线，否则不展开工作台、项目总览、历史或全量 Git。

按当前设计规模最多先选一条：

1. 局部、低风险、范围清楚且现有结构可以承载：直接设计，不读 reference；
2. 需要核验或维护长期产品、设计和契约事实：完整读取[设计事实与基线](references/capability-and-facts.md)；
3. 新系统、主链路重构、重大架构、数据迁移、P0止血或存在真实技术取舍：完整读取[架构、取舍与P0](references/architecture-tradeoffs-and-p0.md)；
4. 复杂业务、跨模块共享契约、多个实施周期、正式设计文档或实施反馈回改：完整读取[复杂设计文档与实施衔接](references/complex-design-document-and-implementation.md)。

场景真实变化后再读下一份；同一任务已经读取且文件未变化时不重复读取。reference缺失只停止依赖它的设计分支，不妨碍仍能安全完成的轻量设计。

## 3. 设计方法

PM轻量任务设计只回答五件事：老板最终要得到什么业务结果；哪些当前项目事实决定上下文；对象与明确边界；怎样判定完成；是否仍有一个只能由老板决定的真实取舍。结果足够时直接形成紧凑任务包；不足时只问该取舍。这里不选择代码结构、实现步骤、测试组合、发布命令或证据目录，不读取控制runtime实现，也不新建任何设计产物。

先区分：用户明确目标、明确不做、当前已查事实、仍需核对的技术细节。可从代码、配置、契约或运行现场查明的内容先调查，不转成用户问卷；不能确认的内容不编造。调查时使用的接口、抓包、临时脚本、样本路径和诊断入口只是证据，除非符合已确认的业务边界与长期约束，否则不得直接写成实施方案。

轻量设计只需要：

1. 找到现有入口、数据来源、契约和验证点；
2. 沿现有结构确定实现当前目标所需的最小变化；
3. 让每个范围项对应一个可判定验收；
4. 说明待实现时必须再核对的事实。

标准或重大设计按以下顺序收敛：

```text
用户要得到什么结果
业务对象是谁、范围到哪里、哪些生命周期必须共用同一机制、结果是否允许展示或对外使用
当前系统实际怎样运行
准备改变哪条主链路和哪些边界
实现要改哪里、按什么顺序
接口、字段、状态和异常怎样约束
怎样测试和验收
怎样发布、观察和回退（不涉及则明确写不涉及）
```

输出先说人话，再给必要技术细节。术语、缩写和英文标识只有在对应代码、契约或行业表达确实需要时使用，并说明它对业务结果的影响。

现有结构能承载时顺着实现，不为整齐重切架构，不为未知未来增加框架、服务、字段、状态或扩展点。只有真实差异会改变决定时才比较两到三个方案；否则直接给推荐路径。

有限且归属已经确认的历史数据修复，与避免未来复发的产品机制分别判断：前者先比较受控一次性修复，后者只有本身属于当前业务结果时才进入长期能力设计。一次性修复裁决必须保留决定路径成立的主体归属、影响范围、生产或共享数据写入授权、备份或事务保护、回滚和复验事实，不能只保留技术范围而遗漏已有授权。分别判断不等于强制拆任务；用户已经授权两者且结果连续时仍由同一个Worker交付，未授权的未来机制不借历史修复自动扩入范围。

业务语义或验收取舍调查后仍无法确定时，只问一个会改变方向的问题。跨正式任务的优先级、共享对象和写入顺序由原 Worker按跨任务机制处理，不由设计 Skill调度。

## 4. 事实与设计文档

接口、字段、状态、模块、依赖和技术约束必须来自代码、正式文档、当前任务或用户确认。候选只能写成候选，不能冒充当前事实或已实现功能。

PM轻量任务设计只进入任务包，不形成项目文档。普通局部技术设计直接写在回复或任务线程，不新建设计文档。复杂设计必须使用一个明确的活动设计文档：优先复用项目已有正式设计入口；没有承载者且当前任务拥有写入授权时，按[复杂设计文档与实施衔接](references/complex-design-document-and-implementation.md)和项目文档入口确定唯一位置、使用者及归档方式。

长期仍会复用的稳定目标、主流程和共享契约归回已有事实所有者；当前任务进度、单轮测试、候选提交和过程讨论不写入设计基线。

设计结论必须区分当前事实和实施后的方案。本轮只完成设计、尚未开发或发布时，最终答复开头必须用人话明确当前尚未实施，例如`当前用户页面/系统业务流程尚未变化`；后续页面、接口、数据和操作使用方案态或将来时表达。

## 5. 进入实现与回复

进入开发前必须能够回答：目标和不做什么、改哪里、依赖什么、唯一契约在哪里、怎样测试、怎样交付，以及还有什么会改变实现方向的缺口。

- 正式任务已授权继续实现：原 Worker直接切换开发方法，不等待 PM续派；
- PM正在派发非平凡短提示：只把轻量设计写成业务任务契约，随后由唯一Worker自行选择技术设计与执行方法；
- 用户只要求设计：交付设计后停止当前动作，不把设计请求扩张成开发授权；设计是业务任务内检查点时仍由原 Worker等待用户确认，不能自动收口为独立设计任务；
- 只影响当前任务的反馈：原 Worker直接修正设计；
- 影响另一个正式任务或项目主线：由原 Worker返回最小影响摘要，不由本 Skill联系PM或创建接力。

默认回复使用短格式：

```text
结论：推荐路径，以及当前是可进入实现、仍需收敛或需要一个决定
范围：做什么、不做什么
实现路径：改哪里、按什么顺序、关键契约是什么
测试路径：用什么入口证明结果
发布路径：怎样交付、观察和回退；不涉及则明确说明
待核对：只列会影响实现或验收的事实
```

局部设计可以合并成更短的自然语言，不为填格式扩写。复杂设计的正文进入唯一活动设计文档，回复只保留结论、路径、文档入口和下一动作。

始终禁止：夹带未要求能力；用技术名词代替业务解释；为设计过程随手建文档；让PM承担技术设计或业务执行；把设计完成写成代码、测试、发布或用户可用已经完成。
