# 架构/设计动作

## 定位与不可推断边界

设计把目标收敛成可实现、可协同、可验收的方案。它是 PM 或执行者调用的动作技能，不改变原身份、任务 ID或任务控制权；当前设计足以约束实现且授权包含开发时，任务控制实例直接进入开发，不等待 PM续派。

先逐字提取用户明确的目标、限制和明确不做。不得用“常规设计”“体验完整”或未来扩展为理由增加用户动作、业务定义或产品范围：

- 用户只要求查看时，不增加新建、编辑、删除、详情或跳转。
- 不自行定义未给出的字段、状态枚举、默认值、排序、文案或数据结构。
- 不自行增加视觉风格、颜色、端适配、基础设施或“以后方便”的扩展点。

用户说`只展示 / 能看就行 / 先简单做`时直接走轻量设计，不追问是否需要编辑或扩展。缺少可调查的字段取值、数据来源或样式事实时，标记为实施前从代码或正式契约核对，不现场编造，也不转问用户。

## 输入分类与按需读取

由任务控制实例调用时继承任务运行上下文，只读取当前设计初始化包、点名目标、必要事实和验收入口；不重新执行项目接手链。用户直接提出清晰设计请求时，遵守根`AGENTS.md`后只读目标现状和必要依赖，不自动展开工作台、项目总览、历史或全量 Git。只有用户明确要求接手、从当前主线领取设计，或目标必须依赖工作台才能确定时，才走通用项目读入链。

按以下条件路由：

1. 局部、低风险、范围清楚且现有结构可承载：走轻量设计快路径，不读取reference。
2. 动作初始化包显示设计能力`未初始化/需刷新`，或需要建立/刷新产品设计与契约基线：完整读取[设计能力与事实作业包](references/capability-and-facts.md)。
3. 新系统、主链路重构、重大架构、多项目边界、数据迁移、P0止血或存在真实技术取舍：完整读取[架构、取舍与P0作业包](references/architecture-tradeoffs-and-p0.md)。
4. 跨执行线契约、完整阶段设计、实施拆解、接力、设计归位或实施反馈回改：完整读取[契约、交付与接力作业包](references/contracts-delivery-and-handoff.md)。

初始判断最多读取一份reference；场景真实切换后再读下一份。触发后必须完整读取，同一任务中已读且文件未变化时直接复用。reference缺失时只停止依赖它的设计分支；核心仍能处理普通轻量设计，不能猜规则、扩大范围或放行尚未闭合的实现。

## 轻量设计快路径

当前请求是局部、低风险且目标边界明确时，只做以下步骤：

1. 把输入分成`明确目标 / 明确不做 / 已查事实 / 待核对事实`。
2. 定点定位现有入口、数据来源、契约和验证点；能确认承载位置后立即停止读取，不展开历史、未来动作或无关模块。
3. 沿现有结构冻结当前目标必需的最小行为和契约。未知细节不阻塞实现时保留为实施前核对，不凑字段、方案或扩展点。
4. 让每个范围项对应一个可判定验收；没有事实来源的范围和验收直接排除。
5. 输出`结论、明确范围、待核对事实、验收、下一步`。不展示完整架构、长字段表、实施拆解或内部检查清单。

若题面使用“现有页面/接口/流程”但没有精确入口，只做一次定点检索定位事实；仍找不到时把唯一缺口写入待核对事实。可调查事实不得转问用户，待核对事实不影响最小设计时不得阻塞交棒。

## 一般设计判断

先判断当前是总设计、阶段设计、契约修正还是局部修复，再按风险选择轻量、标准或重大设计。设计顺序保持：业务目标 → 主链路 → 模块/读写边界 → 当前实现必需契约 → 当前范围异常 → 验收与落地顺序。

先解决当前主要矛盾：契约不清先定契约，职责混乱先定边界，跨线失真先定唯一共享契约。现有结构能承载时顺着实现；不为整齐重切架构，不为未知未来引入框架、服务或复杂状态机。

只有存在会改变决策的真实取舍时才比较`2–3`个方案；没有实质差异时直接给推荐方案。业务语义、用户偏好或验收取舍调查后仍无法确定时，只问用户一个会改变方向的问题；资源、实例、跨任务优先级和契约影响范围交 PM。

## 事实、能力与安全默认

接口、字段、状态、模块、依赖和技术约束必须来自现有代码、正式文档、当前任务或用户确认。候选只能标为候选，不能冒充正式事实、冻结成契约或据此宣布开工。

出现设计能力初始化缺口时，先读取对应作业包；事实未闭合时不得冻结候选设计或放行开发。设计基线已可用且没有命中刷新触发时直接引用正式入口，只刷新本次目标、受影响契约和验收，不重复展开全项目设计。

设计动作不得扩大文件、Git、环境、生产、数据、不可逆或外部费用授权。需要正式写回时只写任务授权的唯一设计/契约位置；没有写入授权时交最小设计结果，不自行新建方案、审查或协作文档。

## 放行、自检与回复

放行开发前必须闭合：目标和边界、唯一正式设计与契约、验收、写回位置，以及当前涉及的共享对象和拍板关系。能在任务内调查补齐的继续设计；只有目标、写入边界、契约变更权或重大取舍无法在当前授权内决定时才红灯。

交棒前内联检查：目标—范围—契约—验收是否对应；事实与候选是否分开；是否夹带未要求能力；开发是否知道改哪里、依赖什么、怎么验证。关键缺口未闭合时保持`继续设计`，不能用`待定`或“类似现有实现”冒充完成。

设计结论必须先区分当前事实与方案实施后的状态。本轮只完成设计、尚未开发或发布时，最终答复第一句必须明确`当前用户页面/系统业务流程尚未变化`，后续页面、接口、数据和操作一律用方案态或将来时表达；不得用“方案已冻结”让老板误以为功能已经可用。

默认输出：

```text
结论：设计已冻结并自动进入下一动作 / 继续设计 / 红灯升级
方案：当前目标、边界、结构和必要契约
验收：如何证明成立
风险：只列影响放行的风险
下一步：最小动作和接收方
```

轻量设计优先使用五项短格式；用户要求简单时不展示方案比较或长清单。纯讨论、假设场景或Skill测试没有正式落点时，不生成形式化回写草案。

始终禁止：在设计动作中直接编码；替 PM改主线；替测试或运维伪造结论；让不同执行线各自猜契约；在关键缺口未闭合时放行开发；为设计过程随手新建文档。
