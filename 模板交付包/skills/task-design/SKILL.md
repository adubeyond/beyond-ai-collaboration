# 架构/设计动作

## 身份与边界

设计把目标收敛成可实现、可协同、可验收的方案。它是 Worker 在当前任务内选择的专业方法，或基础智能体处理直接、清晰设计请求时采用的方法，不建立新智能体，不改变身份、任务 ID、控制权或授权。在本方法内，PM 只编译、派发或协调任务，不能替 Worker 完成业务设计；跨任务、共享对象、主线、资源、安全和收口仍由 PM 按身份职责处理。正式任务先由 Worker 完成接单核验，再在当前放行段内进入设计。

以用户明确的目标、限制和不做范围为边界，不因“常规做法”“体验完整”或未来扩展增加功能、字段、状态、风格、基础设施或用户动作。可从现场查明的事实先调查；不知道的技术现实标为待核对，不编造，也不把可调查问题转问用户。

## 最小读入与路由

由 Worker 调用时，继承已核验的任务目标、验收、检查点、分项授权、事实入口和回源关系，只补当前设计需要的事实，不重跑接手链。直接设计请求只读目标现状和必要依赖；除非用户要求接手或目标依赖当前主线，否则不展开工作台、项目总览、历史或全量 Git。

这些专业附录同时适用于正式任务和直接请求。正式任务按文中的Worker关系执行；直接请求由当前智能体承担询问、交付和后续动作。不存在的PM、助手或任务关系不补造。

按当前主要矛盾选择路径：

1. 局部、低风险、范围清楚且现有结构可承载：走轻量路径，不读 reference。
2. 必需事实未知、正式入口缺失、证据过期，或要建立、核验、刷新产品设计与契约基线：读[设计能力与事实作业包](references/capability-and-facts.md)。
3. 新系统、主链路重构、重大架构、多项目边界、数据迁移、P0止血或真实技术取舍：读[架构、取舍与P0作业包](references/architecture-tradeoffs-and-p0.md)。
4. 跨执行线契约、完整阶段设计、实施拆解、接力、设计归位或实施反馈回改：完整读取[契约、交付与接力作业包](references/contracts-delivery-and-handoff.md)，再按该作业包的交付门禁完整读取[项目文档入口](../../docs/AI编程协同机制/00-模板入口.md)，取得路径、版本、活动期和历史回收的唯一规则。

初始最多读取一份 reference；场景真实切换后再读下一份。触发后完整读取，同一任务中文件未变化则复用。reference 缺失时只停止依赖它的分支，不猜规则或错误放行。

需要跨模块、执行线或检查周期消费，涉及共享契约、迁移、权限、关键状态流程，或用户要求正式设计文档时，第4项必定命中。复杂设计不能只留在聊天、工作台摘要或任务卡中；未完整读到项目文档入口、未确定唯一活动路径、当前版本、写入状态、消费者和计划归档位置时，不得写“设计完成”或交给开发、测试消费。路径、活动期和归档规则仍只由项目文档入口拥有，第4项只负责设计内容、交付和接力方法。

## 轻量设计

局部、低风险且边界明确时：

1. 分清`明确目标 / 明确不做 / 已查事实 / 待核对事实`。
2. 定点定位现有入口、数据来源、契约和验证点，达到最小充分事实后停止读取。
3. 沿现有结构确定最小行为与契约，不凑字段、方案或扩展点。
4. 让每个范围项对应可判定验收；需要进入开发时，再给出实现落点、依据和验证入口。

轻量结果用几句话说清结论、范围、待核对事实、实现落点和验收，不展开完整架构、长表格或内部清单。题面提到“现有页面/接口/流程”却未给入口时，先做最小定点检索；仍找不到才记录唯一缺口。

## 设计方法与表达

先判断是总设计、阶段设计、契约修正还是局部修复，再按`业务目标 → 主链路 → 模块与读写边界 → 必需契约 → 当前异常 → 验收与落地顺序`收敛。契约不清先定契约，职责混乱先定边界，跨线失真先定唯一共享契约。现有结构能承载时顺着实现，不为整齐重切架构，不为未知未来增加复杂度。

只有真实取舍会改变决定时才比较方案；没有实质差异就直接推荐。标准或复杂设计先用普通中文让用户看懂：

1. **做成什么**：完成后的用户结果和明确不做。
2. **实现路径**：改哪些部分、先后依赖和每步作用。
3. **测试路径**：怎样证明主流程、失败、边界和旧功能仍正确。
4. **发布路径**：怎样进入目标环境、检查和回退；本任务不含发布时说明边界。

技术名词、英文、接口名和命令只在必要时保留，并先解释其与用户结果的关系。以上都是计划，不能写成已经开发、测试、发布或可供用户使用；尚未实施时必须明确说明当前用户页面/系统业务流程尚未变化。设计阶段默认复用已有代码和测试证据；除非设计取舍确实依赖当前运行行为且已有执行授权，不运行测试、构建或发布命令。

聊天交付最多使用六个短段：`当前现实 / 设计锚点 / 做成什么 / 实现—测试—发布路径 / 明确不做 / 决定项`，总计不超过1200个中文字符；短段内只写用户裁决需要的内容，不再展开第二份“模块边界、状态、数据契约、开发切片、测试表、回滚步骤、归档步骤”。复杂设计的锚点必须包含`唯一活动路径 / 当前版本 / 是否已写入 / 当前消费者 / 计划归档位置`。模块字段、状态枚举、接口表、事件名和完整执行附录只写进获授权的唯一正式设计文档；没有写入授权时只给建议落点，并原样说明`尚未持久化，不能作为正式实施依据`，不把整份技术正文倾倒到聊天。

## 开发就绪与接力

每个范围项应能追溯为`用户目标或有效决策 → 一手事实与约束 → 设计选择 → 可观察验收`。按当前变化检查真正命中的架构、业务状态、安全、数据与并发、外部失败、资源与容量、兼容迁移和正式消费入口；不相关项不填表，无依据的质量数字不编造。

交给开发判断前，至少闭合：

- 唯一实现依据及适用版本，或本轮可直接消费的设计结果；
- 目标模块、入口或文件类型，可复用能力及明确不改对象；
- 当前范围的用户行为、输入输出、状态、不变量、失败、权限和兼容边界；
- 必要的依赖顺序、迁移/回滚、配置、文档、跨线关系和验证入口；
- 编码前必须闭合的决定项与实施时定点核对的事实。

轻量设计可以内联；复杂设计必须指向唯一正式文档，并说明当前版本、是否已写入、当前消费者和计划归档位置。设计完整只表示开发输入足够，不产生开发授权，也不解除用户检查点。

## 事实、回流与停止

接口、字段、状态、模块、依赖和技术约束必须来自可核验证据；候选不能冒充事实或正式契约。只有会改变目标、边界、正式契约或验收的缺口阻止冻结和开发判断，其他未知项作为实施前核对。

开发证据可以推翻设计，但不能静默偏离。局部实现差异不改变用户行为、契约、职责、数据所有权、质量目标和验收时，正式任务由原 Worker 在任务内处理，直接请求由当前智能体在现有授权内处理；改变其中任一项时，停止受影响实现并切回设计，先更新获授权的唯一正式入口及版本，再恢复开发。

目标、契约变更权或重大取舍无法在当前授权内决定时，只形成一个最小决定项。直接请求由当前智能体询问用户；正式任务返回原 Worker，由 Worker 在当前任务内取得用户决定，只有跨任务、共享对象、主线、资源或安全影响才交 PM。

## 返回

正式任务向原 Worker 返回当前结论、范围、事实与候选、唯一设计/契约入口及版本、实现落点、验收、明确不做、残留风险和决定项；直接请求由当前智能体把同一内容交付用户，不制造任务回源。返回或交付前确认开发能够判断依据哪个版本、改哪里、复用什么、守住什么、怎样验证；关键缺口未闭合时保持继续设计。

用户约定“只审设计”“一次一个文件”或“设计完先看”时，到检查点立即停止。设计动作不直接编码，不修改任务控制或 PM 主线，不扩大文件、Git、环境、生产和数据权限，不替开发、测试或运维宣布结果，也不为过程随手新建文档。
