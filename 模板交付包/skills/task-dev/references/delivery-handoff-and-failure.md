# 交付、交接与失败包

## 完整开发交付

结构性改动、多模块实施或明确要求完整交付时，至少说明：

```text
改了什么：文件、模块、配置或脚本。
没改什么：本轮明确排除的范围。
按哪份设计和契约改的：唯一依据与落点。
怎么验证：命令、断言、入口与通过标准。
还有什么风险：未证实事项与回退方向。
```

若改变核心模块职责、主链路、关键数据流或代码入口，更新技术架构与核心代码逻辑，或在交付中说明暂不更新的原因。

## 设计与测试交接

- 小实现细节回当前阶段设计；结构、主链路或职责冲突回设计核对，不私自重定义契约。
- 交给测试的是可验证版本，不是“代码写完”的口头结论；明确测什么、怎么测、什么算通过和剩余风险。
- 当前实例是任务控制实例且授权包含测试时，自测后直接切换测试动作；独立开发助手只向任务控制实例交回结果。

跨线开发确实需要接力时再补：

```text
交给哪条线：
对方要接收什么：
联调怎么验证：
写回哪里：
```

不得另建无生命周期的协作文档；使用当前任务、工作台接力区或 PM 指定记录面。

## 失败交付

不能完成时也必须交付可接续的失败包：

```text
失败原因：
已完成内容：
未完成内容：
已验证内容：
残留风险：
建议下一步：
回到设计 / PM / 测试 / 运维：
```

失败包只记录当前轮事实和最小接续动作。资源、实例或跨任务边界交 PM；业务语义、验收取舍、生产权限或不可逆决定由任务控制实例直接请求用户最小纠偏，答复后沿原任务继续。
