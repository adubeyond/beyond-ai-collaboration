# 实现、调试与修复循环

## 适用范围

只在新增高回归行为、缺陷修复、构建/测试失败、根因排查，或任务控制实例需要开发修复助手时读取。

## 实现与证据

- 新增行为、核心逻辑或高风险缺陷优先定位或补一个能稳定失败的测试，确认失败由目标问题造成，再做最小实现并确认转绿。
- 文档、纯配置、一次性迁移或无法自动化的改动，先定义可观察结果，再用构建、静态检查、定点核查或人工复验替代，并说明未覆盖风险。
- 项目已有失败项必须与本轮新增失败分开；旧失败不能算通过，也不能冒充本轮缺陷。

## 根因循环

1. 稳定复现并记录实际现象和最小条件。
2. 沿输入、状态变化与调用链定位最早偏差点。
3. 一次只验证一个根因假设，先取证再做最小修复。
4. 重跑原失败路径和受影响回归；整理代码后再跑关键验证。

禁止连续堆叠多个猜测性修复后统一测试。无法定位时交付当前证据、已排除项和下一条最有价值的验证动作，不用“可能是环境问题”提前结束。

普通构建失败、测试失败和实现调整是原任务内黄灯，由任务控制实例连续修复。需要改变契约、越过写入边界、取得真实权限、执行高风险操作或达到修复上限才形成红灯。

## 开发修复助手

修复助手必须从任务控制实例取得原任务 ID、失败证据、写入边界、交付物、验证入口和关闭条件，沿用原任务 ID，只处理对应失败范围。

完成后把 diff、当前轮自测、残留风险和正式写回位置返回任务控制实例；由任务控制实例把新版本交回原测试实例复测。开发助手不控制 tester、不改变任务状态、不自行启动测试或运维，也不向 PM 做普通修复中继。

若实际启动者是测试实例、回报要求绕过任务控制实例，或控制关系无法核实，写入前报告控制权冲突。资源、实例和跨任务冲突交 PM；业务契约、验收偏好、权限或高风险决定由任务控制实例按授权直接找用户裁决。
