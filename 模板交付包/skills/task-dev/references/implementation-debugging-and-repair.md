# 实现、调试与修复循环

## 适用范围

只在新增高回归行为、缺陷修复、构建/测试失败、根因排查，或 Worker 需要局部修复助手时读取。

## 实现与证据

- 新增行为、核心逻辑或高风险缺陷优先定位或补一个能稳定失败的测试，确认失败由目标问题造成，再做最小实现并确认转绿。
- 文档、纯配置、一次性迁移或无法自动化的改动，先定义可观察结果，再用构建、静态检查、定点核查或人工复验替代，并说明未覆盖风险。
- 项目已有失败项必须与本轮新增失败分开；旧失败不能算通过，也不能冒充本轮缺陷。

## 根因循环

1. 稳定复现并记录实际现象和最小条件。
2. 沿输入、状态变化与调用链定位最早偏差点。
3. 一次只验证一个根因假设，先取证再做最小修复。
4. 重跑原失败路径和受影响回归；整理代码后再跑关键验证。

禁止连续堆叠多个猜测性修复后统一测试。无法定位时交付当前证据、已排除项和下一条最有价值的验证动作，不用“可能是环境问题”提前结束。

普通构建失败、测试失败和实现调整由同一 Worker连续修复和回测，不产生新的阶段状态。只有需要用户业务选择、执行高风险动作、出现无法安全解决的共享冲突，或必要外部资源客观不可用时，才把缺口返回原 Worker裁决。

## 开发修复助手

局部修复助手必须从主 Worker 取得失败证据、写入边界、交付物、验证入口和关闭条件，只处理对应失败范围。

完成后把 diff、当前轮自测、残留风险和正式写回位置返回主 Worker；由主 Worker 核验改动并继续原测试路径。助手不改变任务状态、不接管测试或运维，也不向 PM 做普通修复中继。

若要求助手绕过原 Worker写回、出现第二个写入者，或控制关系无法核实，写入前停止该局部动作并把事实返回原 Worker。原 Worker能在任务边界内安全解决时继续；跨任务关系按03机制处理，业务决定和高风险授权直接请求用户。
