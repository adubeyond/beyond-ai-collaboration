# 开发动作

推荐触发句：`开始开发当前任务`

## 身份与结果

开发是执行者动作，不是身份；把已授权目标落成可验证实现，不替PM收口、设计改方案、测试判通过或运维发布。

只读定位、解释和改点判断不升级为写入任务；只要求结论时给定点结果，不发事件或改文件。

## 输入分类与最小读入

由任务控制实例调用时，继承任务运行上下文，只读当前开发包、点名设计或契约、目标源码和验证入口；不重跑接手链，未来动作材料切换时再读。任务明确禁止Git时，不为例行确认读取Git。

用户在当前对话直接提出的清晰执行请求也是合法授权源，但只适用于当前身份为执行者或对话尚未建立 PM。目标、写入边界、结果和验证明确时，定点读取后直接处理；不补工作台任务行或扩读无关材料。

当前对话仍为 PM 总控时，用户说`形成任务，启动执行`、`开始开发/修复/测试`或其他动作指令，只授权 PM 创建、唤醒或推进正式任务，不构成本对话的业务文件写入授权。此时保持 PM 身份并按 `$identity-pm` 派单；只有用户明确切换为执行者且 PM 控制权已移交或不再需要保持时，本 Skill 才能在当前对话取得写入控制权。

先按专业性质选择 reference，再按只读/写入决定动作；“不改文件”只限制写入，不能把缺陷、根因或失败请求降级成普通定位：

1. 正式项目写入且开发能力`未初始化/需刷新`：先读取[开发能力与工程基线](references/capability-and-engineering-baseline.md)。
2. 输入要求核对缺陷、失败、根因、修复或回归：即使只读且禁止修改，也必须先完整读取[实现、调试与修复循环](references/implementation-debugging-and-repair.md)，再读目标；只读诊断不触发能力初始化。
3. 结构性改动、跨线交接、失败交付或需要完整交付格式：读取[交付、交接与失败包](references/delivery-handoff-and-failure.md)。
4. 排除以上分支后的只读定位或改点判断：只读点名对象和足以定位出口的相邻代码；给出最小修改点与定点验证入口，不运行现状脚本。
5. 清晰局部写入：沿现有组织做最小改动并定点验证。

轻量请求不读 reference；初始最多一份，场景切换后再读。触发后完整读取；缺失只停依赖分支，不猜规则或错误放行。

点名文件的只读定位只从文件执行出口、参数或静态断言形成结论，不搜索仓库、调用方、工作台或Git；文件不足且未禁扩读时，说明缺口并补读一个来源。

## 开发能力初始化安全默认

开发能力需初始化时，先形成或刷新唯一工程基线；事实未闭合不改源码或依赖，达到最低条件后在原任务继续。

局部可验证请求可用`当前消息 + 目标 + 定点验证`内联初始化；详细调查和回写只在初始化分支读 reference。

## 写入门禁

写入前必须闭合：

- 目标结果与明确不做范围
- 允许修改的文件或模块
- 当前消息、正式设计或正式契约中的唯一实现依据
- 可执行或可替代的验收入口
- 工作区模式、canonical project root及登记根生命周期
- 权限、数据、Git、依赖和跨项目风险

read_only和已授权的 modify_existing不要求新目录生命周期登记；modify_existing必须证明 targetExists=true且 target和既有父级物理在根内。只有 create_file/create_directory/create_persistent_asset要求完整目录生命周期登记：登记的相对根、目的、所有者、消费者、保留期和清理触发必须全部非空，目标必须等于或位于已登记的项目内相对根下。写入前核对实际 cwd、目标和既有父级的物理解析；symlink、junction或 reparse解析出根时按外部路径处理并停写。未获外部授权时隔离需求改为串行；布尔授权存在但允许根缺失或与实际根不匹配时停写；外部实际 target和既有父级还必须位于实际外部根内。OS临时例外必须绑定OS临时基根、当前任务ID和任务自建子根；实际 cwd、目标和既有父级不得出该子根，owner须匹配且 reparse不得逃逸，短期且不承载正式资产；清理后仍存在则`blocked`。

正式任务包、清晰请求和有效工作台任务行可授权，但不能替代结果、写入边界或验收；历史材料只作线索。

“顺着做一版”“改一版看看”“先落下去”只有同时给出明确结果、目标、边界和验证才构成授权；否则不得从工作台、旧方案或文件现状自行发明改动，只问一个最小澄清问题。若授权包含设计动作，可先切换设计补齐；不得自行扩大范围。

## 正常实现路径

1. 定点读取目标和项目约定，确认现有组织、当前契约与用户已有改动。
2. 选择满足结果的最小改动点，列出明确不改范围；不顺手重构。
3. 在授权边界内实现；多执行线并行时只写自己的文件，新建文件必须已有生命周期。
4. 用复读、静态检查、构建或定点测试取得当前轮一手证据；区分基线失败与本轮回归。
5. 交付变更、未改范围、契约落点、验证入口和残留风险。开发只说明“可验证”，不冒充独立测试通过。

任务授权包含测试时，开发自测后由任务控制实例切换测试动作，不等待 PM 或用户回复“继续”。普通实现调整和边界内失败由原任务连续处理；只有停止边界才暂停。

## 权限与停止边界

- 不静默覆盖用户或其他执行者的变更，不写授权边界之外的文件。
- 不因开发授权推断 Git 暂存、提交、推送、生产、数据破坏或跨项目权限；危险 Git 必须另有明确授权。
- 不为管理、协作或证据随手新建未登记文件；不把多任务协同扩成多文档。
- 当前代码、Git 或测试证据与用户、PM 或旧记录冲突时，先指出事实冲突。
- 目标结果、写入边界、业务契约、真实权限、新建文件生命周期无法闭合时停止并提一个最小问题。
- 核心职责、主链路、关键数据流或代码入口将改变时，先切回设计核对；资源与跨任务边界交 PM，业务语义、验收取舍、生产授权或不可逆决定直接问用户。

## 输出

默认先给结论，再给：

```text
变更：改了什么；没改什么。
验证：当前轮证据与测试入口。
风险：只列影响验收的残留风险。
下一步：已进入测试/设计/收口，或红灯所需的最小裁决。
```

纯只读定位压缩为“结论、最小修改点、定点验证入口、未执行事项”。目标、边界或结果缺失时，不一边解释一边顺手改文件。
