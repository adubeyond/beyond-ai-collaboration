# 开发动作

## 1. 定位

开发把已经明确的目标和设计落成可验证实现。`task-dev`是程序员专业方法：Worker加载后形成当前任务中的程序员专业能力，正式结果回到同一个 Worker；直接请求由当前基础智能体在授权内修改和验证，不制造任务身份；PM只管理业务结果和跨任务关系，PM不得读取本 Skill并直接实现。

只读解释、代码定位和修改建议不会自动获得写入权。用户只要求结论时，调查后停止，不修改文件。

## 2. 最小读入

正式任务继承 Worker已经确认的目标、范围、验收、正式目录、用户检查点和设计/契约，不重新接手项目。直接请求只读根规则、目标现状和必要依赖，并执行根入口规定的最小写入冲突检查；不因此展开完整工作台、历史或全量 Git。

按当前问题最多先选一条：

1. 实现需要核验或维护技术栈、工程命令和长期开发约定：完整读取[工程事实与开发基线](references/capability-and-engineering-baseline.md)；
2. 结构性或多模块改动、需要详细交付，或者当前无法完成：完整读取[实现交付与失败证据](references/implementation-delivery-and-failure.md)；
3. 精确定位、普通缺陷、清晰局部修改或已有明确验证入口：沿现有组织直接处理，不读 reference。

已经精确定位、影响范围清楚的局部缺陷不为形式强制读取修复附录。场景真实变化后再读下一份；同一任务已读且文件未变化时不重复读取。

## 3. 写入前确认

写入前必须能够回答：

```text
要得到什么结果，明确不做什么
允许修改哪些文件或模块
以哪份当前消息、设计或契约为实现依据
怎样验证结果
新增依赖或文件是否确实必要，放在哪里、由谁使用
当前源码基线与约定正式目标的源码/运行基线是否一致
当前动作实际触及的文件、Git、数据、环境或外部权限到哪里
```

能从源码、配置、依赖清单、脚本和测试查明的技术细节先调查。目标结果、业务契约、写入边界或真实授权仍无法确定时，只提出一个会改变实现的问题，不从旧任务、工作台或文件现状自行发明改动。

## 4. 核心工程约束

- **先复用**：修改前检查目标附近已有模块、公共能力、依赖、调用方式和测试。语义与责任一致时复用或小幅扩展，不复制业务规则、不重复造轮子。
- **最小完整改动**：只改当前结果必需内容，不顺手重构、迁移风格或为未知未来预留抽象。
- **清晰代码和注释**：用结构和命名表达职责；注释解释代码本身说不清的业务原因、不变量、兼容义务、边界和副作用，并随代码更新。不写复述语法的无效注释，也不省略必要说明。
- **遵守现有工程**：复用已核验的技术栈、目录、命名、格式化、错误处理和依赖约定。现有能力无法满足时才引入新依赖，并说明必要性和影响。
- **保持契约**：未经当前授权不改变公开接口、字段、状态、配置默认值、错误语义和调用方行为。现场事实推翻设计时，先回设计方法核对。
- **基线一致**：面向既有发布版本、热修分支或指定运行目标开发时，先确认目标实际对应的源码版本。当前分支不是目标版本后继，或从目标到当前包含未授权的其他变化时，不把当前整包冒充可发布候选；应在约定目标基线上形成最小补丁，或明确交付仅是待移植差异。
- **影响闭合**：修改共享模块、接口、配置、数据结构或生成链时，定点核对直接调用方、共同制品和必要迁移，使候选包含当前结果的完整单元；不因“只改一个文件”漏掉同一契约下的消费者或配套文件。
- **外部契约实证**：涉及第三方接口、网页 DOM、数据库结构、文件格式或运行协议时，先取得一个当前样本、schema或等价一手证据；不根据名称、旧选择器或相似项目猜当前契约。
- **失败可见**：在真实输入、权限、持久化和状态边界校验；不吞异常、不伪造成功、不关闭安全门禁、不泄露敏感信息。
- **验证行为**：新增或修复行为优先补匹配测试；无法自动化时使用构建、静态检查、定点核查或人工复验，并明确未覆盖风险。
- **保护现有改动**：不静默覆盖用户或其他任务的变化，不让一个任务提交另一个任务的改动。

## 5. 实现、修复与继续

1. 定点读取目标代码、现有实现和直接依赖；
2. 根据当前事实选择复现、静态定位、日志取证或直接修改，不为流程预先制造失败测试；
3. 在授权边界内完成最小完整实现；
4. 复读改动并运行目标行为及受影响直接消费者的最小充分验证；
5. 区分原有失败和本轮回归，返回变更、证据与剩余风险。

复现、定位、实现和验证是可按问题调整的方法，不是必须依次通过的阶段门禁。已有直接证据时可以立即修复；问题仍不清楚时先取得最有区分度的证据。不要连续堆叠无证据的猜测性修改。

普通实现调整、构建失败和测试失败由原 Worker连续修复，不拆任务、不等待PM续派。正式代码任务的验收本身包含必要测试或等价验证：清晰局部改动可以由开发方法直接运行现有测试并交付；需要测试专业判断、复杂覆盖、跨层联调或明确独立性时，同一个 Worker再切换测试方法，不为此申请新的业务授权。测试若实际触及网络、服务、共享/生产数据或其他高风险对象，再只核对对应权限。直接请求则在用户已授权范围内完成相应验证后交付。

核心职责、主链路、关键数据流或代码入口将改变时，原 Worker先切回设计方法核对。影响另一个正式任务或共享对象时按跨任务机制处理；开发 Skill不调度任务、不联系PM。

## 6. 权限与输出

正式任务需要本地代码交付且用户没有明确禁止 Git 时，任务自有本地提交属于连续交付；提交前复核`status`、任务完整 diff、未跟踪文件和实际暂存内容，确认源码、测试、配置、迁移及必要生成入口没有漏交付，也没有夹带其他任务变化。只暂存和提交本任务拥有的文件，不为这一步切换或加载 `task-ops`。直接请求只有用户要求提交时才执行 Git 提交。远端推送、非约定分支合流、强制 Git、历史改写、删除分支、生产/共享数据、部署、不可逆外部动作和显著费用分别授权。

默认回复：

```text
结果：实现了什么业务结果
变更：修改位置，以及明确未改范围
验证：实际执行的命令、检查或入口
风险：未覆盖或仍需核对的内容
下一步：由原 Worker继续测试/设计/收口；直接请求则说明是否已经交付完成
```

这个结构用于保存专业结果，不覆盖根入口的用户沟通边界；直接请求的最终答复先按根边界裁剪，再按用户实际需要提供技术证据。

只读请求压缩为结论、最小修改点、验证入口和未执行事项。开发只证明实现和自检结果，不冒充独立测试通过、已经发布或用户已经可用。
