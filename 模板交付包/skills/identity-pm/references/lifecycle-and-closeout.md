# 异常生命周期与收口作业包

本作业包是 PM 处理控制异常、恢复执行和依据证据收口的生命周期之“术”。只有 `SKILL.md` 已经把当前输入判定为阻塞领取、暂停恢复、重复或乱序事件、旧版本、来源或实例冲突、`red`、`shared_conflict`、`cancelled`停止确认、证据不足、返工或复杂收口时才完整读取。平台创建回执已经正常登记、普通通知和证据闭合的普通终态使用 PM 主文件快路径，不读取本文件。

本文件不创建第二套派发或协同协议。需要新建正式任务时使用[复杂任务编译、派发与事实补足作业包](dispatch-and-init.md)；共享对象的所有权、隔离、顺序和合流使用[多任务协同与独立审查作业包](coordination-and-review.md)。

## 1. 生命周期真值与事件信封

始终分开三种事实：

1. **业务状态**：`待排期 / 可执行 / 进行中 / 已暂停 / 候选完成 / 已完成 / 已取消 / 阻塞`。
2. **实例状态**：`待领取 / 执行中 / 等待事件 / 待回收 / 已关闭 / 失联`。
3. **PM 已消费控制快照**：PM 最后已经核验并用于主线判断的状态，不冒充任务现场实时状态。

`验证中`只是当前动作，`待补证据`只是证据条件，都不是第三套业务状态或实例状态。事件是改变控制认识的输入，不因送达自动覆盖正式状态；PM 消费后才更新控制快照。

事件 ID 使用`<任务 ID>:<任务版本>:<执行回合>:<序号>`。事件至少包含：

```text
任务 ID / 任务版本 / 执行回合 / 序号与事件类型 / 发生时间
实际来源任务定位 / 业务状态 / 实例状态
用户直接指令：无 / 原意锚点、已生效变化与影响范围
授权、契约或共享对象变化
正式设计/契约：无 / 路径、版本、正文锚点、变化摘要与受影响消费者
完成与剩余 / 一手证据 / 正式写回
Git、服务、环境、数据与发布现实
下一步 / 需要谁裁决什么
```

实际来源以平台事件信封为准；能取得时同时登记真实`threadId + hostId`，不能取得的字段保持未知，不复制 PM、祖先或历史任务标识冒充来源。

事件 ID 与正文一一对应。同一事件传输失败只能用原 ID 和完全相同的事件事实重试；已消费事件不重复改状态、启动实例或收口。同一 ID 出现不同正文时登记事件冲突，不把后到正文解释成修订。

旧版本事件不能覆盖当前版本的契约、状态、控制实例或授权，但旧实例已经造成的文件、Git、服务、环境、数据或生产变化仍是客观现实。先保护现场和受影响对象，再定点核对并决定保留、回退、隔离或另建获授权任务；需要产生副作用的处置仍须取得对应的准确授权。不得用“旧版本只作证据”忽略真实副作用。

用户在正式任务对话中的直接指令不需要PM重新批准。PM消费时核对它是否只影响当前任务，还是进一步影响共享契约、其他任务、主线、资源或安全：任务内变化更新控制快照并进入批量知情；跨任务变化立即协调受影响任务。PM可以基于事实向用户提出风险或冲突，但不能让Worker等待PM复述用户已经明确的决定。

事件收件箱是逻辑队列，不默认新建一份共享写文档。完整正文保存在平台事件、任务主面和正式设计/契约中；当前工作台只保存每个任务最后已消费事件、当前设计版本和未消费最高严重度。普通进展、阶段消息和任务内变化按项目的一次聚合窗口或PM下一次空闲回合成批消费，不逐条唤醒 PM；紧急事件到达时顺带消费已经排队的普通事件。`paused / failed / candidate_completed / completed`是每执行回合唯一收口信号，不属于普通聚合事件：按任务冻结的`定向终态消息 / 平台完成观察器 / 明确人工消费`模式到达 PM。平台完成观察器可以监视终态；人工消费只从任务契约登记的正式任务最终结果或持久终态入口读取，并按已登记责任、触发和游标/幂等依据消费，不使用高频轮询。

## 2. 阻塞领取、暂停与恢复

来源不明、从另一线程或实例恢复、原实例失联、重复实例、共享写入未隔离，或者任务包明确要求登记后才能动作时，使用阻塞`claimed / resumed`。用户在同一已登记正式任务线程直接恢复、且线程、任务主面、唯一工作区和最后终态能够证明没有控制冲突时，不进入本阻塞登记；Worker递增回合并把`resumed`持久化为聚合知情事件，PM后续按游标消费：

1. 先用 PM 当前控制快照核对任务 ID、版本、回合、序号、平台实际来源、项目与工作区、已登记实例和共享写入边界。
2. 当前快照不足以判断时，只定点读取任务主面、最后已消费事件或平台正式登记；不扫描项目、不重载完整任务包、不推演后续事件。
3. 字段完整、来源与待领取任务一致且没有控制或工作区冲突时，登记唯一任务控制实例，并通过平台实际可用的任务消息能力向事件真实来源只返回一次`登记通过`。
4. 字段缺失、来源不可归属、旧实例仍在执行或存在双实例、工作区及共享写入冲突时，返回`拒绝领取`或`待补证据`，保持原业务状态，停止可能扩大冲突的动作，不启动内部助手冒充正式实例。
5. 平台没有可用的定向消息能力时，记录未返回的对象、原因和待发送裁决，不向用户回复冒充任务已经收到，也不把登记缺口改写成业务失败。

阻塞领取只解决控制实例能否开始，不重新决定业务目标、任务契约或授权。登记结果已经返回后不补发无控制变化的确认消息。

正式任务控制实例的`失联`需要外部控制证据，不是沉默、固定超时或一次消息失败的别名。只有平台生命周期/完成观察器，或因用户查询、依赖等待、恢复、取消及未返回的阻塞领取而被触发的活动PM，才能发起一次有界正式控制实例失联核对；Worker不能判定自己失联，PM不为发现失联持续轮询。核对只读取已登记实例的实时平台状态、最后有效事件、任务主面和实际工作区/运行资源，不扫描无关项目。Worker控制的局部助手不是正式任务控制实例；其失效、关闭和替补由原Worker按协作作业包核验，不把助手失效升级成PM对正式Worker的失联裁决。

只有以下事实同时成立时才登记`失联`：

1. 已登记控制目标被平台明确报告为异常终止、已不存在、不可恢复，或实际运行载体已经消失且不能再按原实例定位；暂时无新消息、超过预计时长、一次读取/等待/消息失败或PM尚未消费终态都不充分。
2. 没有与当前任务、版本和执行回合匹配的有效终态或正式控制移交；已经正常终态或移交的实例按对应状态处理，不改记失联。
3. 核对证据带实际来源、发生时间、平台或运行事实和最后可验证副作用。只能确认“无法判断是否仍在运行”时，业务状态保持不变，把`待补证据`作为证据条件，并停止可能与旧实例重叠的写入或共享动作。

确认失联后先保护旧现场、工作区和共享对象，登记最后已知文件、Git、服务、环境、数据和生产现实。只有平台或实际运行证据证明旧实例不能继续产生副作用，并且唯一工作区已经隔离、关闭或明确移交时，才能沿用业务任务ID、递增执行回合并登记一个替补控制实例；新回合重新核对当前契约、授权、易变事实和未完成动作，不复用旧事件ID或把旧实例未执行的授权当成已经发生。无法证明旧实例停止或工作区唯一性时保持控制冲突，只允许不重叠的安全调查，不创建并发替补。

活动PM不能证明自己已经失联。PM控制入口失效时，只能由平台或用户从控制面外部恢复或建立替代PM；接管前必须核对原PM不再拥有活动写控制、当前工作台、最后已消费事件和未决任务。Worker、Action Skill或协作实例都不能因PM无响应而晋升为PM或改写项目控制真值。

暂停时停止会继续产生副作用的动作，安全保留现场和已取得证据，业务状态记为`已暂停`，实例按现实记为`等待事件`或释放后的`已关闭`。恢复只刷新任务主面当前结论、最后事件以及 Git、服务、环境、数据、授权等易变事实；目标、边界、验收和稳定入口未变时不重新规划、不扫全项目、不重建任务包、不重复提问。

用户或平台直接打开执行对话，不自动产生第二个控制实例。已登记实例仍在运行时回到原实例；已暂停或终态后的同一已登记正式任务线程收到用户直接恢复/返工指令、且能证明唯一工作区和无控制冲突时，由该线程建立新执行回合，不等待 PM审批。来自另一线程、原实例失联或无法证明唯一性的恢复先走本节阻塞登记。失联本身不授权创建替代实例，先核对唯一工作区、平台实例状态和最后一手现实；不倒填不存在的历史事件。

## 3. 异常事件、取消与共享冲突

- `red`：先验证事件身份和受影响边界，保留现场并停止相关动作；授权内不受影响的安全路径可以继续。PM 只补足决定继续、调整、退回、取消或请求用户裁决所需的最小事实。
- `shared_conflict`：本文件只验证事件、保护共享对象、阻止冲突写入并更新受影响任务状态；随后转入协同作业包裁决所有权、兼容、隔离、顺序或唯一合流。协同裁决形成后再回本文件恢复、返工或收口。
- `yellow / shared_notice`：本身不是阻塞；可以合并进下一控制事件或终态。后续证据形成真实冲突时生成新的`shared_conflict`，不改写旧事件含义。
- 重复事件：返回已有消费事实或保持静默，不重复改变业务状态。
- 乱序或序号跳跃：不猜缺失步骤；核对最后已消费序号、发送端证据和现实副作用，只补当前裁决必需的缺口。
- 来源、双状态或双实例冲突：把`待补证据`记为证据条件，停止自动覆盖；不能用内部助手、另一段自然语言或新任务掩盖控制冲突。

平台回源失败时保留原事件 ID、实际来源和待核对缺口；不要求来源任务更换事件 ID，不长期轮询，也不因普通事件生成无业务价值的性能报告。

用户明确取消，或者 PM 在当前控制权限内确认任务已经失去主线价值且无需继续投入时，业务状态记为`已取消`。实例仍在运行时，通过已登记的真实控制路径通知它停止新增动作并安全保留现场；无法确认已经停止时，实例状态保持`执行中`或按现实记为`失联`，同时保护共享对象，不把业务取消冒充实例已经关闭。记录已经发生的文件、Git、服务、环境、数据、生产和费用现实；实例安全释放后才记为`已关闭`。取消不等于回滚，任何删除、恢复、停服、数据修复、退款或其他副作用仍需单独授权。已经释放的实例不为补一条取消事件而重新唤醒；取消作为新的外部控制事实登记。

PM 收到`cancelled`时，把它视为 Worker 对取消控制的停止确认，不把它当成 Worker 自行作出的取消决定、任务完成证据或回滚证明。先按第 1 节核对任务身份、版本、回合、序号和实际来源，再核对取消来自用户或 PM 的真实控制、实例停止位置、现场保留和已经发生的副作用；来源或现实无法对应时保持`待补证据`，不覆盖当前控制快照。确认取消有效后业务状态保持或更新为`已取消`；只有一手证据证明实例已经停止并安全释放时才把实例记为`已关闭`，否则按现实保持`执行中 / 等待事件 / 失联`并继续保护受影响对象。同一`cancelled`按事件 ID 幂等消费，不重复改状态、触发回滚或形成第二次收口。

## 4. 终态核对与裁决映射

每个执行回合只消费一个`paused / failed / candidate_completed / completed`收口信号。定向终态消息可以唤醒包装实际来源，平台完成观察器可以在任务结束时交付终态；两者都未建立时只能从契约冻结的正式任务最终结果或持久终态入口人工消费。首次创建后的有界等待只证明任务启动，不能作为终态已监听或已送达的证据。终态消息成功投递只证明到达来源，不证明 PM 已消费或裁决。

复杂`paused / candidate_completed / completed / failed`进入收口前，只核对支撑当前结论的最小充分事实：

- 实际来源是否对应已登记的`threadId + hostId`或平台事件信封，任务版本和执行回合是否一致。
- 任务主面、实例登记、最后事件和 PM 已消费快照能否互相解释。
- 业务结果、明确不做、验收和用户保留决定是否由匹配的一手证据支持。
- 最终消息是否把候选、代码完成、本地测试或待发布冒充已经采纳、已经上线或用户可用。
- Git、服务、进程、环境、数据、生产和发布现实是否与事件表述一致。
- 事件点名的契约、任务主面、事实文件、发布记录和证据是否按准确路径授权写回；未点名范围不扩张核对。
- 当前结果是否仍推动主要矛盾，是否破坏共享契约、依赖任务或目标主线。

证据不足时只形成限定结论、退回或阻塞，不把未知解释成通过，也不让已经释放的实例长期等待。终态成功投递后是不可变事实；返工沿用任务 ID，增加执行回合并生成新事件 ID，不要求原实例撤回终态、修订同一事件或继续原执行回合。

生产交付额外核对任务起始基线、授权目标主线、当前生产实际版本、未归并生产补丁、可执行回滚入口和验证对象生命周期。生产成功不等于目标主线已经包含；无法解释的生产差异不得宣告完成。

裁决只使用`采纳 / 限定采纳 / 退回 / 阻塞`，并映射到真实状态和下一动作：

- **采纳**：采纳范围已经满足正式结果和对应验收；业务状态记为`已完成`，已释放实例记为`已关闭`，再按授权写回主线和稳定事实。
- **限定采纳**：明确采纳什么、不采纳或尚未证明什么。未采纳部分已经由有权决定者移出本任务或转成独立结果时，本任务可以记为`已完成`；原任务必需结果仍未满足且尚未决定后续时保持`候选完成`，决定继续后按排期与执行现实转成`待排期 / 可执行 / 进行中`并进入新执行回合，不得用“部分通过”冒充完整完成。
- **退回**：原终态和证据保持不变，旧实例保持`已关闭`；契约未变且继续获授权时沿用任务 ID 增加执行回合，尚未排期时业务状态记为`待排期`，可以立即执行时记为`可执行`。
- **阻塞**：业务状态记为`阻塞`；仍需保留现场的活动实例记为`等待事件`，已经释放的实例记为`已关闭`。只说明最小缺口、已完成部分和解除阻塞所需的实际决定或资源。

取消是主线路线决定，不是证据采纳结论，按第 3 节处理。`completed`事件也不能迫使 PM 采纳与主线、正式验收或现实不一致的结果。

## 5. 证据、用户决定与收口回复

一手证据包括真实命令与测试、运行结果、日志、截图、接口响应、Git 差异、环境或外部记录，以及用户对实际使用结果的直接反馈和有权作出的业务决定。证据强度必须匹配结论：样例通过不等于真实业务完成，结构通过不等于语义通过，本地通过不等于已经发布，生产可用也不自动证明目标主线已包含代码。

用户可以明确保留任何会影响真实结果的验收、体验偏好、业务语义、生产数据、不可逆操作、费用或重大取舍。PM 先调查可调查事实并提出专业异议，但不能用自动、PM 裁决或机器证据越过用户保留决定；用户未保留且任务已经预授权的低风险机器验收，可以按任务契约自动收口。

PM 面向用户的收口回复遵守主文件，不套固定四行骨架，也不倾倒内部状态。按当前任务实际涉及的内容，用用户能理解的语言说明：

- 当前真实结果、用户现在能不能使用，以及采纳、未采纳或未知的范围。
- 实现入口和关键链路；证据已经点名文件、模块、接口或流程时直接说明。
- 实际测试方法、对象、结果、覆盖与未覆盖范围。
- 是否已经交付或发布、真实使用入口、尚缺的授权或条件。
- 会影响使用、验收或主线的剩余风险、下一动作和必须由谁决定的事项。

不适用的内容不强行补齐，未知项不编造。先说现实结果，再说实现、验证和发布事实，最后给必要下一步；不得只回复“候选完成、红灯、已收口、进入下一阶段”。

## 6. 裁决后的主线衔接与回收

收口不是按设计、开发、测试、运维阶段机械过门。PM 根据已采纳结果、未完成现实、依赖变化和新的主要矛盾，决定：

- 原契约未变且需要重做：同一任务进入新执行回合。
- 出现可独立排期和验收的新业务结果：通过派发作业包建立新任务。

- 只缺外部决定、权限或资源：保持阻塞并提出一个最小裁决。
- 结果已经闭合：更新主线、释放实例并停止制造记账回合。

任务状态、主线、项目事实和证据只写入各自唯一正式入口。目标位置必须存在并具有准确路径写入授权；未获授权时在当前回复保留建议写回内容、证据来源和未写原因，不把 PM 控制权解释成写权限。

实例已经完成写回且没有下一动作时释放。普通收口不发送纯消费回执，不为记录“已看到”唤醒已经结束的任务；只有真实控制变化、返工、恢复或新授权才产生下一事件或执行回合。
