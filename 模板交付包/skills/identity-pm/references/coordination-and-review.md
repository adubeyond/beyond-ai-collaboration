# 多任务协同与独立审查作业包

本作业包是 PM 组织多个正式任务、保护共享对象并取得独立审查证据的协同之“术”。只有 `SKILL.md` 已经路由到本文件时才完整读取；单一任务普通派单、普通事件和任务内普通修复不读取。

PM 与执行者共同使用的术语、共享对象、接力、事件分级和冲突恢复接口，以[多智能体共享运行协议](../../../docs/AI编程协同机制/机制/03-多智能体协同机制.md)为唯一来源。本作业包只规定 PM 如何应用这些接口进行调度、审查和收口，不建立第二套公共协议。

## 1. 适用边界与协同产物

适用于多个正式任务、跨线接力、共享契约或写入、依赖与合流、内部助手、独立审查、资源冲突或批量事件汇流。

不要为了展示分工而协同。只有多个任务能够独立验收，或者协作能取得单一实例难以获得的独立证据、隔离能力或明显时间收益，并且收益高于创建、传递、等待、核验和回收成本时，才增加任务或助手；否则由一个任务控制实例连续完成。

输出必须能说明：

1. 多个任务共同依据什么，哪些内容不能各自解释。
2. 哪些任务可以并行，哪些必须等待、串行或交给唯一合流任务。
3. 每个任务的真实实例、工作区、边界、依赖、证据和当前状态。
4. 内部助手或独立审查由谁控制，结果返回哪里。
5. 多任务结果怎样影响项目主线、用户使用和下一关键动作。

本文件不创建第二套任务派发、生命周期、平台权限或 Worker 执行协议。单个任务契约和非阻塞创建使用[复杂任务编译、派发与事实补足作业包](dispatch-and-init.md)；异常状态与终态使用[异常生命周期与收口作业包](lifecycle-and-closeout.md)。

## 2. 权威来源与跨任务不变量

两个以上任务共享接口、字段、枚举、数据范围、业务规则、文件、环境或生产对象时，创建受影响任务前先形成短权威来源清单：

```text
来源路径或外部记录 ID / 版本或哈希 / 适用范围
正式所有者 / 最后核验与证据 / 冲突时优先级
```

只从权威来源提取多个任务共同消费的不变量：

- 接口、路由、字段、枚举和数据范围。
- 必须保持的兼容行为和验收口径。
- 共享禁止修改对象、唯一写入者和唯一合流责任。
- 依赖版本、输入制品、验证入口和生效顺序。

每个候选任务包引用同一来源和版本。创建前对同名不变量做精确比较；一致才放行。存在冲突时只暂停受影响任务，回到正式所有者核对并修正任务包，独立任务继续。不得复制完整设计形成第二份真值，也不得等到执行中再用`shared_conflict`补救可在派单前发现的冲突。

## 3. 依赖、共享对象与并发

PM 为当前实际任务维护最小协同关系：

```text
任务身份与业务结果 / 正式任务或排队标识 / 项目与工作区
读写边界 / 依赖与被依赖任务 / 共享对象及所有者
允许并行条件 / 等待或串行条件 / 唯一合流责任与验收
```

不设置固定并发数，按现实冲突控制：

- 业务结果可以独立验收、读写边界分离、共享不变量一致且资源可隔离时可以并行。
- 同一文件、worktree、数据库或表、服务、端口、测试账号、环境、生产对象或外部额度不能隔离时，串行或指定唯一合流任务。
- 存在全局红灯、双控制实例、工作区所有权冲突或共享契约冲突时，只停止受影响任务。
- 一个慢任务不得阻塞没有依赖和共享冲突的其他任务。
- 普通通知积压不暂停授权内运行的任务；只有真实依赖或资源冲突形成等待。

## 4. 任务创建结果与事件汇流

每个任务经过第 2—3 节门禁后，回到派发作业包第 6 节分别建立或恢复；协同门禁已经通过，不重复转回本文件。本文件只聚合平台实际结果：

- 真实`threadId + hostId`表示可由线程能力定位的正式任务。
- `clientThreadId`只表示 worktree仍在准备，不得冒充真实任务或传给要求 thread ID的工具。
- 创建失败和创建结果不明分别记录；结果不明先定点核对，不重复创建。

多个正式任务是事件生产者，活动 PM 是唯一控制事件消费者。唯一消费者和单写者只说明控制责任，不产生当前工作台或其他路径的写入授权。

每条事件按`任务 ID + 任务版本 + 执行回合 + 事件序号 + 实际来源 thread ID`分组，不依赖到达顺序、消息相邻位置或自然语言上下文猜归属。任务正文没有自报真实实例时，以平台创建结果或事件实际信封为准；不为补一个身份字段向任务发送没有控制变化的消息。

事件汇流采用四种处理方式：

1. **不唤醒**：命令级进展、普通调查、同一任务内动作切换、局部设计/实现调整和可恢复测试失败，只留在任务主面。
2. **聚合知情**：不影响其他任务的任务/设计版本变化、同一已登记正式任务线程的非阻塞`resumed`、资源释放和用户直接指令本地生效摘要，进入PM事件收件箱；按一个有界聚合窗口、PM下一次空闲回合或多任务等待快照批量消费。
3. **终态回源**：`paused / failed / candidate_completed / completed`是每执行回合唯一终态，不进入普通聚合收件箱；按任务冻结的`定向终态消息 / 平台完成观察器 / 明确人工消费`模式到达来源PM。到达不等于已经消费、裁决或采纳，Worker不等待消费回执。
4. **立即裁决**：阻塞`claimed/resumed`、`cancelled`、`red/shared_conflict`、双控制实例、共享契约/写入冲突、用户指令影响其他任务或主线、资源重分配以及生产安全/不可逆风险，立即唤醒PM。取消直接改变主线和依赖。一次紧急唤醒同时吸收已排队普通事件，避免紧接着再次回调。

平台支持多任务等待或批量快照时，PM一次监控多个已登记正式任务，只取各任务相对消费游标的新事件；不得为每个任务建立一个长期等待回合。平台没有非唤醒收件能力时，普通事件留在任务主面供有界批量读取，Worker不能退回逐条唤醒PM的旧路径。终态投递始终服从任务冻结模式，不因普通事件收件能力变化而降级成普通聚合事件。

同批已到达事件按以下顺序处理：

1. 共享对象、全局红灯、`shared_conflict`和双控制实例冲突。
2. 各任务的阻塞领取或恢复裁决。
3. 只影响单个任务的实际裁决。
4. ready、queued、黄灯和共享通知等普通知情事实，以及已经按冻结模式到达的暂停或终态。
5. 恢复 PM 原本的主线判断或用户回复。

不得把一个任务的证据、授权、事件序号、平台标识或回源目标带入另一个任务。事件可以聚合消费，每项裁决仍必须带任务身份和实际来源。

PM每批按`立即裁决 → 跨任务影响 → 需要决定的候选、失败或暂停 → 其他已到达终态 → 知情更新`排序，只读取事件点名的差异和正式锚点，一次更新控制快照和消费游标。缺字段、文档不可读、版本/正文锚点不一致时标记待补证据，不用摘要猜正文；无需裁决的任务不回发纯确认。

## 5. 业务授权、平台能力与资源门禁

每个任务分别核对业务授权、平台当前实际能力和资源条件。PM当前实例可写、某个任务拥有更高运行权限或项目存在默认配置，都不能证明其他任务具有相同能力，也不能扩大文件、Git、环境、服务、生产、数据、费用或不可逆授权。

本文件不硬编码平台配置路径、权限值、审批模式或沙箱枚举，不自动修改持久权限，也不自动创建权限探针任务或写删探针文件。

确需持久权限变更、运行能力探针或临时文件时，必须把准确目标、用途、使用者、保留或回收、验证和副作用分别写入业务授权；再通过派发作业包建立获授权的正式任务。权限或资源不足时只停止受影响任务，保留现场并说明最小缺口；独立任务继续。

## 6. 正式任务、内部助手与实例回收

正式任务按可独立验收的业务结果建立，不按设计、开发、测试、运维阶段拆分。同一任务控制实例连续切换动作、处理普通失败并回测，PM不逐阶段路由。

内部助手只在正式任务已经存在、任务授权允许协作，且局部目标、输入、读写边界、输出去向、实例预算和回收条件明确时启动。它可以承担定点调查、独立测试、审查或局部实现，但必须直接返回原任务控制实例；不能改变业务结果、正式契约、授权或任务状态，不能成为业务任务控制实例或直接收口。

内部助手默认只允许一层，不能继续创建或指挥新的助手。原任务确实需要新增实例时，由原任务控制实例重新说明新增收益、隔离边界、实例预算、结果去向和回收条件；PM只处理需要重分配的资源与跨任务冲突，不用放宽派生层级掩盖任务过大、边界不清或原实例失效。

平台限制导致只有 PM能代为启动助手时，原任务控制实例提交完整资源请求；PM只完成获授权的资源动作，助手仍直接返回原任务控制实例。无法直接返回、隔离不成立或资源未经授权时形成资源红灯，不让 PM成为过程消息中继。

实例结果已经写回且没有下一步时释放。平台要求 PM执行关闭时，只处理一次回收动作，不参与任务内修复和回测。

## 7. 跨线接力与写回

跨线接力至少说明：

```text
发起任务 / 接收任务 / 当前事实 / 输入制品
共享对象与正式所有者 / 读写边界 / 目标动作
验证入口 / 证据位置 / 接收结果 / 关闭条件
```

共享契约只有一个正式所有者。其他任务引用所有者和版本，只记录必要差异，不复制第二份独立真值。接力改变业务目标、任务边界、共享契约或生产授权时回到 PM或用户裁决；普通技术协同留在任务控制实例之间。

当前工作台已获准确路径写入授权时，PM可以写入会影响主线、多个任务或下一步的接力结果；未获授权时只在正式事件和用户回复中保留当前事实、建议写回内容及未写原因，不因“PM是单写者”推导权限。

## 8. 独立审查

先决定审查的控制形态：

- 只为原任务提供局部、独立证据时，使用获授权的任务内审查助手，结果返回原任务控制实例。
- 审查结果可以独立验收、独立排期，或用户需要直接进入纠偏时，使用派发作业包建立正式审查任务。
- 低风险改动已经由匹配结论的机器证据闭合时，不强制创建审查实例。

审查只接收最小输入：

```text
任务目标与正式要求 / 待审 diff、提交或文件范围
当前测试与一手证据 / 已知风险
输出：按优先级说明发现、证据、影响和建议
```

不得把完整聊天历史、PM预判或期望答案交给审查者。审查者依据正式契约、目标现实和一手证据独立判断，缺背景时定点补充。

审查结论必须分开回答两件事：一是结果是否符合当前任务、边界与验收，是否漏做、越界或擅自扩张；二是实现、测试、配置或文档本身是否可靠，证据是否足以支持结论。第一项通过不能替代质量验证，第二项优秀也不能让超出任务的结果自动进入主线。

审查意见是待核验输入，不是自动授权或完成结论。接收方核对现实、兼容义务、调用关系和原验收，再区分阻断缺陷、范围内修复和超范围建议；证据不成立时说明理由，新增能力或扩大边界时回 PM或用户。

## 9. PM 回复、负载与回收

PM向用户说明多任务对整体结果的影响，而不是倾倒状态和日志。回复按实际情况交代：当前共同目标、哪些任务在推进、依赖和共享对象、并行或等待原因、冲突与证据、对用户使用或交付的影响、下一关键动作，以及必须由用户决定的事项。

PM默认保持可用，不长期执行源码扫描、实现、调试、完整测试、部署等待或长证据整理。执行实例只回传结论、一手证据、对其他任务和主线的影响、需要裁决事项和下一步建议。

回收由任务或阶段结束、事实失效、入口被旧过程挤占或实例无下一步触发，不按行数机械触发。只有目标位置存在且已获准确写入授权时才执行回收；当前入口保留当前结论、必要证据路径和下一步，长日志与旧过程进入获授权的证据区、生产记录或历史位置。
