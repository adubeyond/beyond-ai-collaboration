# 多任务协同与审查作业包

只在 `SKILL.md` 已判定当前输入同时涉及多个正式任务、跨线接力、共享写入/工作区、内部助手、独立审查、资源预算或批量事件汇流时完整读取本文件。单一任务普通派单与普通事件不读取。

## 1. 多任务事件汇流

多个正式任务线程是事件生产者，PM 正式线程是唯一控制事件消费者和总工作台单写者。平台线程消息只传输控制关系或正式真值；业务调查、调试日志、普通进展和任务内纠偏留在各任务对话。

每条消息先按`任务 ID + 任务版本 + 执行回合 + 事件序号 + 来源 thread ID`解析信封并分组。不得依赖到达顺序、消息相邻位置或自然语言上下文猜归属；字段不完整或来源冲突的事件不自动覆盖状态。

创建回执返回的子任务 thread ID由 PM直接登记：`creation receipt thread_id = PM registration`。worker未在事件正文自报自身 ID时可写明由终态平台信封登记，即`worker body may defer to terminal envelope`；PM按实际信封来源消费即可。不得仅为让 worker在事件正文填写精确 ID而向子任务补发身份消息：`no identity-supplement message for event body`；只有授权、边界、契约或裁决确有变化时才发送新的控制消息。

同批已到达事件按以下顺序处理，不等待延迟窗口：

1. 共享对象、全局红灯、`shared_conflict`和双控制实例冲突。
2. 各任务的阻塞领取登记；分别回到对应来源 thread ID。
3. 只影响单任务的实际裁决事件。
4. 创建回执登记、兼容启动、黄灯、共享通知、暂停和终态等不需要实际裁决的事实。
5. 恢复 PM 原本的规划或用户回复。

不得把一个任务的证据、授权、事件序号或回源目标带入另一个任务。多任务事件可以聚合消费，但每项裁决仍必须带任务键和来源。

## 2. 背压与并发门禁

不设置固定并发数，按现实冲突控制：

- 存在未处理的全局红灯、共享契约冲突、双控制实例或工作区所有权冲突时，不创建新的冲突任务。
- 多任务写入边界、worktree、共享契约或生产对象不能隔离时，改为串行或指定唯一合流任务。
- 普通通知积压不暂停授权内运行的任务；PM 批量登记后再启动更多任务。
- 同一事件传输失败只用原 ID重试；worker 不轮询 PM。
- 只有实际依赖关系或共享冲突形成队头阻塞；一个慢任务不得阻塞其他独立任务的派单和收口。

### 2.1 批量权限准备

批量派单前先做一次权限基线门禁，业务授权与 Codex 运行时权限分别核对。PM 当前对话能写文件，不能证明新正式任务会继承相同权限；先核对可信项目、项目级 `.codex/config.toml`、当前平台创建能力和一个新任务的最小写入探针。

当平台`create_thread`没有权限参数、且新线程不会继承 PM 当前权限时，不得批量创建一组等待人工切换权限的任务。先在批量外解决一次项目级默认权限：低风险任务优先使用满足写入边界的受限权限；确需完全访问时，只有取得用户对项目级持久 Full Access 的明确授权，才由获授权的配置动作在可信项目设置`default_permissions = ":danger-full-access"`，并且不得同时设置`sandbox_mode`或`[sandbox_workspace_write]`。没有这项授权时只允许单个试点任务等待人工切换，不宣布批量就绪。

项目默认权限变更后先创建一个可回收的最小正式任务，验证其能读取并用标准`apply_patch`修改、复读和删除自身获准的临时探针，再放行其他写任务。探针通过只证明运行时权限可用，不扩大文件、Git、网络、服务器、生产或数据授权；这些仍按各任务包分别限制。

项目默认权限只保证之后按该项目设置创建的新任务，不证明已存在的正式 thread 或已经开始的执行回合会刷新。恢复旧任务前先确认该 thread 已切换到目标权限，并从新的执行回合继续；不得在旧回合中靠连续`允许一次`迁移权限。发现旧回合仍按`on-request/workspace-write`运行时，只停止新增审批请求并保留现场，不重建业务任务、不更换 worktree、不丢弃 diff；同一 thread 的新回合继承新设置后继续。

## 3. 任务、实例与内部助手

任务按可独立验收的业务结果建立，不按设计、开发、测试、运维阶段拆分。同一任务控制实例在内部切换动作；普通失败回到开发后交原测试证据面回测，不由 PM逐段路由。

并行前确认任务可独立验收、写入边界分离、共享契约唯一、依赖和合流人明确。不能分离时串行。

协作子智能体只在正式任务已经存在、局部目标、输入、写入边界、输出去向和回收条件明确且实例预算允许时启动。它只能承担只读调查、独立测试、审查或局部实现，结果直接回正式任务控制实例；不能成为业务任务控制实例、改变授权、直接收口或把 PM变成日常消息中继。

平台只有 PM能代启动且任务硬性要求隔离时，任务控制实例提交一次完整资源请求；PM只做一次资源启动。助手仍直接回任务控制实例，后续修复接力和回测不经 PM。无法直接回报或隔离仍不成立时形成资源红灯。

实例结果写回且没有下一步时默认释放。平台要求 PM操作关闭时，只消费一次回收事件，不参与过程路由。

## 4. 跨线接力

跨线事项进入当前工作台接力面，至少包含发起方、接收方、当前事实、共享对象、目标动作、接收状态、证据位置和关闭条件。只有发起没有接收方回写不算闭环。

共享契约只能有一个正式所有者。其他任务引用所有者和版本，记录必要差异，不复制第二份独立真值。接力改变业务目标、写入边界或生产授权时回到 PM/用户裁决；普通技术协同留在任务实例之间。

## 5. 独立审查

核心链路、共享契约、高风险数据和发布变更分别检查任务符合度与结果质量；低风险改动可凭机器证据自动收口，不强制创建审查实例。

安排独立审查时只交最小审查包：

```text
任务目标与正式要求
待审 diff / 提交 / 文件范围
当前轮测试与一手证据
已知风险
输出契约：按优先级列发现、证据、影响和建议
```

不得把完整聊天历史、PM预判或期望答案直接交给审查实例。审查者以代码、正式契约和一手证据独立判断，缺背景时定点补充。

接收意见时把它当待核验输入，不当自动授权。核对代码现实、兼容义务、调用关系和原验收范围，再区分阻断缺陷、范围内修复和超范围建议；证据不成立时技术性反驳，新增能力或扩大边界时回 PM/用户。

## 6. PM 负载与回收

PM 默认保持可用，不长期执行源码全量扫描、实现、调试、完整测试、部署等待或长证据整理。执行实例只向 PM发送结论、一手证据、需要裁决事项和下一步建议，不倾倒过程日志。

回收由任务/阶段结束、事实失效、入口被旧过程挤占或实例无下一步触发，不按行数机械触发。回收后当前入口只保留当前结论、必要证据路径和下一步；长日志与旧过程进入证据区、生产记录或历史回收。
