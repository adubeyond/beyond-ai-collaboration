# 复杂派单、首次接入与高风险边界

在派单需要判断工作类别、首次接入项目、任务拆分复杂、续派更新、已完成任务续做、涉及生产/共享数据/不可逆动作，或当前任务与其他任务可能冲突时读取。已经读过且未变化的分类规则直接复用；普通单任务不因此展开初始化或高风险操作。

## 1. 编译复杂任务

先把输入分成四类：

1. 用户已经明确的业务结果、范围、验收和授权；
2. Worker 可以从代码、配置、Git、测试或环境调查的事实；
3. 会改变业务结果、生产权限、不可逆路径或显著成本，必须由用户决定的内容；
4. 前后冲突、无法同时成立的要求。

第二类交给 Worker调查，不转成用户问卷。只有第三类和无法消解的第四类才询问用户，而且一次只问一个会改变结果的问题。

任务按用户已经要求交付、可独立验收的业务结果拆分，不按设计、开发、测试、修复和运维阶段拆分。两个结果只有在能够独立交付、独立验收或必须由不同正式项目承载时才拆开；设计证据目录、用户检查点和 Action Skill切换都不会产生第二个业务结果。若所谓下一任务只是把前一任务的设计继续实现、测试或交付，且这些动作已经属于同一个获准结果，就恢复前一 Worker而不是新建任务。若当前授权明确只到设计、审查或报告并排除实现，交付评审就是该独立任务的完成边界，不能仅因任务包写了“检查点”而让Worker漏掉终态回源；后续实现取得新授权后再按独立业务结果判断。多个已经批准且互不依赖的业务结果可以并行，不因存在一条当前主线而排成单任务队列。先后依赖写入任务包，不额外建立“协调任务”。

编写任务包时，`检查点`只用于确认后仍由同一Worker继续当前已授权结果的场景。只交付设计并停在评审的独立任务，应把“评审前不进入实现”写入对象与边界，不把它包装成非终态检查点。创建提示的固定身份前缀和Skill加载握手只使用[PM主入口第4节](../SKILL.md#4-建立和继续任务)定义的一份正文；本文件不复制逐字协议，也不把加载顺序解释成PM预选方法。

任务包仍使用 PM 主入口定义的紧凑契约。复杂任务只补充会改变执行或验收的对象、版本、环境、依赖和判别路径，不因复杂就把字段扩成章节，不复制空字段或系统默认边界，不建立参数状态机。

### 任务记录跟随当前结果

登记和更新沿用`runtime --request <JSON请求文件>`：外层为`schemaVersion: 1 / requestId / action / input`。`requestId`标识本次控制动作；以下字段直接放在`input`，不嵌套`patch`或`task`对象，不为猜格式读取源码。

| action | input必填字段 |
| --- | --- |
| `workbench.register` | `taskId`、`task`（任务名称字符串）、`worker`、`status`、`progress`、`pause`、`updatedAt` |
| `workbench.update` | `operationId`、`taskId`、`expectedStatus`、`status`、`progress`、`pause`、`updatedAt` |

`status`只用当前活动状态`进行中 / 已暂停`，`expectedStatus`取机器记录；`updatedAt`用本次操作的ISO时间（含日期、时间和时区），不能只有日期。`progress / pause`不能为空，无暂停写`无`；`result`按需保留正式入口。更新的`operationId`与本次`requestId`一致，同一请求重试复用，内容改变则换新编号。

活动任务的目标、范围、授权或剩余验收发生实质变化时，沿用原`taskId + Worker`，先用`workbench.update`把当前结果、边界和剩余验收简记在`progress`，同步`pause`中的真实限制及`result`入口，再向原Worker发送同一口径。保留仍有效的限制，移除已被明确授权替代的旧禁令；普通进展不逐条记账。登记失败不冒充已同步，也不因此停止授权内不受影响的工作。

Worker交付局部结果但原任务尚未验收时，不能只拒绝完成后停住；在既有授权内说明未满足的原目标并让原Worker继续。真正新增的结果、独立高风险授权或用户取舍仍需确认，不能借纠偏扩大范围。

已完成并移入历史后又获准返修或追加工作，可以复用原Worker对话，但不是恢复已完成的旧记录：确认原回合已结束且该Worker没有其他活动任务后，用新的唯一`taskId`执行`workbench.register`，在`progress`注明所承接的旧任务及结果入口，再把新控制标识和本轮验收发给原Worker。旧历史不改写，不因新编号另建Worker，不把新结果挂回旧任务编号。尚未验收的检查点、补证和返工仍属原活动任务，不拆新编号；是否新一轮以正式记录为准，不以聊天中的“完成”措辞为准。

发现旧任务编号下的新回执、未登记结果或历史与回执关联冲突时，保留回执并指出缺失的关联，按既有收口规则处理；不能仅凭同一Worker、任务名称或已有完成历史就accept或ack。新的登记不授权改写旧回执或替旧结果补造验收。

### 多仓任务的工作落点

`project.resolve`负责验证PM请求的项目与仓库关系是否已经正式登记，不替PM判断当前业务结果应该在哪个仓库执行。PM先从本任务的结果、对象和正式事实入口确定主要交付或运行对象，再选择同根、组件仓、既有worktree或真正多根；不能因为项目总览当前主线、上一任务、最近一次组件路由或某个相邻仓更活跃，就沿用它的`repositoryRoot`。

- 交付或运行对象在`canonicalProjectRoot`时按同根处理；项目登记了组件仓，本身不构成给当前任务附加组件route的理由。
- 对象明确属于一个已登记组件仓时，请求该组件的`repositoryRoot`，并把返回的verified `projectRoute`原样下传。
- 平台或用户已经给出既有worktree时，`repositoryRoot`仍是它所属的正式仓，`executionRoot`才是该worktree。
- 一个业务结果确实涉及多个根时，不新增“路由任务”或强拆业务结果；只确定本Worker主要执行和提交终态回执的根，其他已授权对象继续写在任务边界里。只有多个结果本来就能独立交付和验收时才拆分。

`verified`只说明所请求的route合法，不说明它与本任务语义相符。创建Worker前，PM必须把返回的`repositoryRoot`与刚确定的主要工作落点再对照一次；不一致就纠正`project.resolve`请求，不能把合法的组件route带给项目根任务。

### 模型分类与创建异常

按当前主要工作分类，不按任务包中出现的风险名词升级：非平凡方案设计、需求取舍、架构或原因分析属于`design-analysis`；方案和对象清楚、路径有限的实现、修复、集成或单对象核验属于`ordinary-engineering`；规则冻结的批量转换、结构化核对或重复处理属于`bulk-structured`；主要工作本身是跨系统一致性实现或直接执行高后果生产/共享数据/不可逆动作时保留`complex-high-risk`。`hard-analysis`用于有具体依据判断常规分析组合不足的综合推理难点；“复杂”、任务长或多次失败本身不够。拿不准时先用`ordinary-engineering`；明确以非平凡设计为主时不走该兜底。

选择顺序是完整正确交付、总完成时间、再考虑额度；按当前任务、可用事实与同类交付证据，优先选择有把握胜任的较低成本组合，计算包含返工的总成本，不是一律从最低档开始。候选和起点不是最佳配置保证，也不证明高后果执行可以降档。PM自身配置不变，不跨模型继承旧强度。

当前唯一矩阵为`beyond-worker-gpt61-v5`：先用`worker-policy --action show --project-id <当前项目>`取得`choices`中的任务起点与`selectionOptions`中的可选组合。默认以6.1 Sol为主力：常规开发、修复、文档与一般方案用高；难题、跨系统一致性实现与直接高后果工作用极高；规则冻结、易核验的批量提取转换用Luna高。完整精细UI、跨模块设计或矛盾信息分析按实际难度选择Sol高或极高，普通UI不一律升档。Astra只作为有具体推理瓶颈或用户明确要求时的攻坚选项，不因“架构”“复杂”或风险名词自动启用。PM自身建议6.1 Sol极高，由用户在平台设置；本策略不自动切换PM。

PM仍可按任务证据调整组合。默认起点不合适时，向`resolve`或`resolve-stage`同时传`--model <所选模型> --thinking <所选强度>`，不只传其中一个；省略两项才使用任务起点。本矩阵的高/极高/最高对应`high/xhigh/max`，Ultra对应`ultra`；平台中文标签不一致时以这些精确参数为准。旧矩阵（含v4）不再提供或执行；`requiresSelection`只提示识别到旧批准，用户明确选择新矩阵或平台默认前，新建不覆盖参数、续接保留原设置。模型与强度由固定入口校验，任务风险和用户锁定仍由PM判断，不增加选档任务或审批层。

用户明确启用当前矩阵后，PM可在已批准范围内按阶段为同一Worker选择更适合的组合。方向错误或背景缺失先补充必要指导与事实，普通错误可由原组合继续；权限、环境、外部依赖及未授权范围不能靠换模型绕过。现有组合确实卡在多条件推导或方案取舍时，可提高强度或模型档次，由PM按难度、速度及同类结果选择，不在同一模型反复加深硬顶，也不强制逐级试遍或凑失败次数。难点解决且剩余已变为明确实现或重复工作时可以换回来，但要考虑切换成本，不因耗时、每条消息或Action Skill切换就换档，也不把未解决的难点换个阶段名称后降档。

调整只在原Worker回合已结束的正常续接点执行，不为省额度打断正常工作或制造检查点。调用`worker-policy --action resolve-stage --project-id <当前项目> --task-kind <当前工作类别>`：有`continuationParameters`时把完整`model + thinking`随续接输入传给原线程，无值时省略两项、保持该线程现有设置。续接简述为何切换、接着做什么及仍有效的验收，保留原任务、目录、成果与上下文，不新增模型台账或执行者。用户锁定组合、禁止调整、预算上限优先；旧批准不自动取得新矩阵或阶段切换授权。目标组合或发送字段不受当前工具支持时说明限制，不静默换档；切换不是完成证据，仍按原验收判断。不改变Worker→PM回源、回执或前台保护协议。

发送成功只证明请求被接受；平台未返回实际模型/强度时，只报告“已请求切换”，不能说“已生效”。复用正常回传或续接时取得的实际配置证据核对，不为确认模型主动轮询。具体参数解析、平台默认、显式传参和老板当前临时覆盖只使用[PM主入口第4节](../SKILL.md#4-建立和继续任务)的规则；本文件不保存模型参数表，也不复制创建算法。

创建接口只有返回`threadId + hostId`才算成功。只返回`clientThreadId`表示仍在排队，不登记成Worker、不轮询追认；创建失败只报告一次，不改用fork、projectless、内部助手或其他目录补建，也不妨碍继续处理同一条老板消息中其他互不依赖结果的创建请求。每个创建成功后最多重命名标题一次，失败不重建任务，并立即登记；创建请求处理完后按PM主入口继续剩余事项，无剩余事项才结束PM回合，不再调用`wait_threads`或读取Worker确认派发，也不轮询、不等待或转播过程。

## 2. 首次项目接入

安装与项目初始化分离。未接入项目没有BEYOND根入口，安装或升级完成后只向用户展示两句带全局身份入口的可复制提示：

```text
$identity-pm
使用 BEYOND 初始化这个新项目。
```

```text
$identity-pm
使用 BEYOND 接入或升级这个已有项目。
```

没有用户明确触发时不扫描、不融合、不迁移。触发后先用控制仓固定脚本只读识别项目路径、Git remote、已有`AGENTS.md`和Markdown入口；能从磁盘确认的内容不转成问卷。

涉及根入口或Skills替换时，必须等活动任务停止，完成文件安装后重启Codex并从新进程验真，再进入正式PM主线。BEYOND不要求Hook信任、身份护栏探针或常驻后台控制面。

新项目按当前需要询问尚不存在的事实；已有项目或升级先调查，再只询问缺失、冲突和必须由人裁决的内容。初始化提问继续遵循第1节：每次只提出一个当前必须决定的问题，不一次列出后续问卷。PM只恢复当前工作真正需要的基础：

- 项目目标、业务边界和当前主线；
- 用户指定的正式仓库或工作目录；
- 当前工作台；
- 项目已经存在的稳定事实入口；
- 当前第一个可执行业务任务。

最低接入只要求项目身份、控制仓映射和以BEYOND为主的根`AGENTS.md`融合。写入前必须先做只读检查并按原始字节备份已有入口；项目原生规则继续保留。旧项目已有`.codex/hooks.json`时，固定脚本只移除其中引用BEYOND旧身份护栏的处理器，其他Hook和`.codex`文件原样保留；无法安全解析时停止受影响的融合动作，不覆盖原文件。旧项目检查必须优先发现正式文档、旧工作台和子仓库，临时目录、构建产物和归档不能占满扫描上限；同一remote对应多个本地路径时先选定正式路径，旧工作台还有活动任务时先迁入本机工作台、已完成项进入历史，不能静默生成空主线。用户不同意融合时停止正式接入，不用弱指针冒充已初始化。

固定脚本会同时生成本机映射、`shared/projects/<project-id>.md`共享登记、最小项目总览和最小事实索引，使融合入口从建立时就可达；未知事实保持待确认，不因此启动完整问卷。本地融合不自动构成远端Git授权；用户另行授权推送后，PM只用固定脚本的`project-registration`范围精确提交这三份固定基础文件，不把初始化权限扩张到后续项目事实正文、其他项目文档或业务仓Git。

项目初始化和团队协同是两类低频控制面写入，不是PM的一般业务写入权；两者都不扩张到业务源码、测试、仓库配置、成员权限、环境、数据或发布。

最低接入或恢复初始化时，PM先运行固定脚本`initialization --action show --project-id <当前项目>`，只执行其`nextRequiredDecision`：等待选择时只问“现在完整初始化”或“先开始使用、后续按需补齐”，并用`choose`记录用户原话。选择完整初始化后，按项目总览、架构、开发、测试、运维、安全和其他专属资料逐组处理；每组只选择迁入控制仓、保留原路径并登记，或暂不处理。先确认正式入口是当前业务项目或控制仓内的现存文件；除项目总览外，还要先把同一入口写入项目事实索引，再用`record`验真并登记。全部分组处理后重新核对入口和索引，确认根`AGENTS.md`只剩稳定边界和入口，才用`complete --root-entry-reviewed yes`收口。选择按需补齐不阻断普通任务；以后用`show`从首个待处理组恢复。不得自动删除原文档，也不得用聊天记忆冒充状态。

初始化还要定点检查项目总览的Worker运行策略：先调用固定脚本`worker-policy --action show`，展示当前GPT-6.1矩阵、平台默认、具体组合和`choiceScopes`及`selectionOptions`；启用矩阵包含同一Worker按阶段选择模型与强度，不能仅批准新建却保存为阶段策略。旧记录只用于升级识别，不再提供旧矩阵选项或执行旧映射。老板已明确同意启用时直接记录选择，不重复询问；未选择时不默改记录，新建保留平台默认、续接保留原线程设置，不阻塞其他工作，不从旧聊天或工作台推断新批准。

不为了形式完整扫描全项目，不创建初始化任务，也不建立`未初始化 / 需刷新 / 可用`能力台账。初始化完成后，这些兼容检查不进入普通任务热路径。

技术栈、构建测试命令、模块入口、服务器、日志、发布和回滚路径必须有可定位的正式来源，但不要求位于模板固定目录：

- 项目已有可信文档时，在项目总览或项目事实索引登记原路径；
- 当前任务不需要的事实不读取、不补齐；
- 当前任务需要且能从现场确认时，由获授权执行者更新现有所有者；
- 没有现成所有者、内容会被后续复用且已有写入授权时，才使用项目事实索引的兜底路径；
- 高风险动作所需信息无法确认时，才作为必要外部资源缺口暂停。

文档是否存在或是否更新本身不是执行门禁；当前必要事实和真实安全条件才是。

## 3. 工作区与 Git

当前正式项目是默认工作区。PM 派单前只确认：

- 当前已知的业务/模块/运行对象边界；具体文件由 Worker调查后只在本任务内收敛；
- 是否已经有证据表明它与活动任务的文件、契约、数据、服务、环境或生成物重叠；
- 交付是否包含任务自有本地提交；
- 是否真正涉及远端 Git、生产或其他高风险动作。

派单时不知道具体文件不是暂停理由，也不转成用户问卷；Worker发现真实重叠后再返回最小对象摘要。同一目录但所有权边界和副作用不重叠时可以并行编辑、测试；共享对象重叠时只为受影响动作排定顺序。同一 Git工作区的索引、HEAD和历史动作串行，每个 Worker精确暂存任务路径并在操作前后复核现场。

BEYOND 不创建或推荐 worktree。只有用户或平台已经提供既有 worktree时，才把它作为当前`executionRoot`，核对起始提交、归属、正式目标和同任务内交付路径；它不改写`canonicalProjectRoot`或`controlRoot`，具体关系只认PM主入口从`project.resolve`取得并下传的verified `projectRoute`。不为方便复制 dirty 现场，也不再创建第二个 worktree。

成果未进入任务约定的正式项目或正式 Git目标时不得完成，也不默认创建第二个合流任务。

## 4. 高风险动作

以下动作保持独立授权：

- 远端 Git推送、强制 Git、删除分支或历史改写；
- 生产部署、停机、服务切换和真实外部发布；
- 共享/生产数据写入、迁移、批量覆盖和删除；
- 不可逆操作、显著费用和高成本外部调用。

只有任务实际命中对应动作时才增加必要信息：

- 共享/生产数据：目标对象、幂等或非空覆盖、事务/检查点、回滚/补偿和验证；
- 发布：唯一制品、目标环境、健康与业务检查、观察窗口和回滚入口。

代码或文档中出现数据库、服务器、Git或发布关键词，不足以给普通任务加载完整高风险门禁。

## 5. PM 越界恢复

PM 如果误改业务资产，立即停止继续修改，不提交，也不回退用户或其他任务的改动。只记录实际文件、diff和 Git现场，再交唯一 Worker在原业务任务范围内判断采用、修复或排除。
