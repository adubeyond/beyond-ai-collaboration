# 复杂任务编译、派发与事实补足作业包

本作业包是 PM 把法层判断转译为正式任务的复杂派单之“术”。只有 `SKILL.md` 已经路由到本文件时才完整读取；本文件不自行扩展触发条件。低风险单一只读任务走主文件快路径，不读取本文件。

## 1. 适用边界与产物

输入必须来自 PM 已形成的当前判断：用户要得到的业务结果、主要矛盾、已知事实、未知项、授权和停止边界。输出必须同时包含：

1. 可由唯一任务控制实例执行和验收的任务契约。
2. 用户已经授权派发时，已创建或已恢复的正式任务控制关系；尚未授权或平台能力不可用时，明确说明任务未派发的原因和最小后续动作。
3. Worker 能据此向用户和 PM 说明实际结果、实现、测试、交付与风险的必要输入。

本作业包不建立项目能力状态机，不产生任何文件、Git、环境、服务、生产、数据、费用或不可逆授权，不消费异常生命周期事件，也不维护跨任务协同协议。

## 2. 意图与冲突编译

把当前输入分为四类：

1. 已明确的业务结果、明确不做、验收偏好和授权。
2. 可从项目入口、代码、配置、Git、测试、环境或正式事实调查的内容。
3. 会改变业务结果、验收、生产权限、不可逆或高成本路径，必须由用户决定的内容。
4. 前后冲突、来源冲突或无法同时成立的要求。

可调查事实交任务控制实例在授权内发现、核验并按授权写回，不把技术栈、测试命令、服务器地址和发布流程整理成用户问卷。PM 可以依据已核验事实、正式设计或明确的任务内设计责任选择实现路线；不得把未经调查、未经决定的方案、阈值、轮数、并发、数据规模或灰度方式冒充既定事实。

### 2.1 重新规划

先区分`继续/优化`与`重新规划/重新设计/换方案/推倒重来`。用户明确重新规划时，旧路径、阈值和下一步失去默认决策权；旧进度只作背景证据，已生效的安全边界、不可逆限制和当前运行事实继续有效。

用户没有给出新方向时，只问一个真正决定方向的问题，语言按当前上下文组织；答复前不修改正式文档、任务状态、控制实例、主技术路径、阈值或预算，也不派单。用户已经给出方向时直接编译，不重复询问或用旧进度代替新方案。

只读取足以识别对象、安全边界和正式入口的最小事实，不展开无关历史、代码、旧任务全文或全量 Git。尽量聚合矛盾、写回和校验；出现会改变路线的新事实时重新检查，不受固定回合数限制。

### 2.2 冲突扫描

至少检查：

- `连续做到完成`是否与`某阶段结束后等待确认`冲突。
- 业务结果是否要求上线或发布，但目标环境、发布授权或回滚边界未知。
- 业务结果、明确不做、验收、读写边界、自动执行路径和终态是否互相排斥。
- 用户只表达`稳定后上线/修好后发布`时，是否把期望终态误写成生产执行授权。
- 当前依据之间是否版本、范围或优先级冲突，且冲突会改变任务结果。

缺失决定会改变结果、权限或执行路径时，只问当前最影响方向的一个问题并保留任务草案；不得带冲突启动任务。不存在方向冲突时，把可调查缺口编译为任务控制实例的发现、核验和回写责任。

### 2.3 多任务与共享契约门禁

涉及两个以上候选任务、共享契约、共享写入、跨线依赖或唯一合流责任时，本文件只形成每个候选任务的业务结果、边界、验收和事实来源草案，然后转入[多任务协同与审查作业包](coordination-and-review.md)完成跨任务不变量、隔离、顺序、比较和合流设计。跨任务规则只由该作业包维护；协同门禁通过前不创建受影响任务。

## 3. 当前任务事实缺口与就绪条件

只围绕当前任务实际会执行的动作判断：

1. 完成该动作需要的事实是否已知。
2. 已知事实是否有当前有效的正式入口和适用范围。
3. 易变事实是否足够新，是否需要在动作前复核。
4. 缺失事实能否由任务控制实例在当前读取、工具和风险边界内调查。

不运行项目能力状态机，不为完整度扫描或建设无关能力。缺口登记在已获授权的任务面或当前工作台；已核验的可复用事实按授权写入项目事实文件，跨任务稳定目标和业务决定按授权进入项目总览。动态调查过程、任务状态和实例信息不得写入项目总览或稳定事实文件。

可调查缺口由任务控制实例调查、核验并沿原任务继续。只有业务语义、验收取舍、真实权限、不可逆或高成本决定，以及调查后仍无法确定且会改变结果的事实，才交给用户决定。同一共享缺口已经有责任任务时，其他任务使用已确认部分或登记依赖，不重复调查。

标准项目事实路径由`docs/AI编程协同机制/项目事实/README.md`提供，但标准路径只决定内容归位，不产生创建授权：

- 用户或当前任务明确授权该准确路径时，任务控制实例可以创建并写入。
- 未获该路径写入授权时，任务只交付建议路径、应沉淀事实、证据来源和未写原因。
- 项目事实文件授权不包含当前工作台、项目总览、其他事实文件或 Git 写入；这些分别授权。
- 已有正式文件能承载时不新建；路径、用途、使用者、入口和保留方式不清楚时不创建。

正式派发前先闭合核心主干：

1. 业务任务 ID、版本、正文锚点/摘要、执行回合、唯一任务控制实例或待创建关系，以及唯一任务主面。
2. 业务结果、当前现实、主要矛盾、明确不做、项目、工作区和目标入口。
3. 当前放行段的事实入口、待调查缺口、读写边界、实际授权和写回责任。
4. 用户检查点、检查点前禁止动作、解除主体，以及允许自动推进、普通失败修复与回测的范围。
5. 验收、一手证据、收口主体、普通事件聚合入口、PM 紧急控制目标、终态回源模式和红灯停止条件。

任务契约以`任务版本 + 正文锚点/摘要`冻结。锚点至少覆盖业务结果、明确不做、验收、读写与授权边界、用户检查点、任务身份与工作区、正式来源和终态回源模式；锚点外的说明、排版和普通进展不改变版本，锚点内任一变化必须递增版本并把新锚点送达 Worker 后才生效。

再只对已经命中的风险追加并闭合：

- 新建文件或记录：准确路径、用途、使用者、入口、持续维护和回收方式。
- 复杂设计：唯一活动路径、版本、创建/更新授权、消费者和计划归档位置。
- Git/worktree：仓库、基线、唯一工作区、目标分支和当前动作授权。
- 数据、环境、服务、发布或生产：真实对象、授权、验证、停止和回滚/补偿边界。
- 多任务、共享对象或跨线接力：转协同作业包确定所有者、隔离、顺序和合流。
- 长时间、费用、不可逆或异常生命周期：预算、观察证据、决定者和恢复条件。

当前没有用户保留检查点时也要明确写`无用户保留检查点`，不能用字段缺失表示允许连续执行。任一关键项缺失、互相冲突或无法确定时，任务保持草案或待裁决，不创建为可执行任务；已经误创建的平台线程也只能核对和报告契约缺口，不得因为线程存在、Action Skill 已点名或某项写入获准而先产生副作用。

验收明确依赖真实账号、短信、生产写入、隔离数据库、故障注入或外部费用时，只对该资源做定点预检。资源缺失但不阻塞授权内主交付时，预先排除对应覆盖并要求终态说明；资源直接决定业务结果时才停止受影响动作。

修复上限优先由证据和风险决定：仍能取得新证据、风险未扩大且动作在边界内时继续；同一失败重复且没有新的验证动作，或下一步需要扩权、高风险、不可逆操作时停止。固定次数只来自用户或正式规则。

## 4. Git、工作区与高风险授权

本节只在当前任务已经命中对应风险时读取并编入任务；普通只读或准确边界内的可恢复文件修改不需要携带整节。

- 任务分支和 worktree 由任务控制实例维护。PM 只确定目标分支、唯一工作区归属和 Git 分项授权，不亲自操作执行资产。
- 平台自动生成 worktree 时按实际返回登记，不提前建立同分支副本；已有任务 worktree 时不重复创建。
- 只有用户或正式任务事实明确要求从现有工作树、分支或未提交现场开始时，才把该现场指定为任务 starting state；不得为方便继承聊天上下文、复用本机改动或节省初始化而擅自复制 dirty 现场。未明确要求时使用平台或项目正式基线，并把确需保留的现有差异作为外部输入、依赖或待裁决事实单独登记。
- `开始开发/测试/发布`不自动授权`git add/commit/push/merge/rebase/reset/stash`，每项按当前任务事实单独记录。
- 用户授权业务终态或期望生产发布，不自动授权远端推送、分支合流、强制 Git、生产数据修改、停机、删除或新增费用。
- 既有正式流程明确包含且当前授权覆盖的动作可以执行；具体动作尚未查明时，由任务控制实例先调查正式流程，只执行已授权部分，超出部分停止。
- 数据写入任务必须在契约中明确非空覆盖、幂等、事务或检查点，以及回滚或补偿边界。
- 服务、凭据或发布任务必须要求任务控制实例在动作前核对实际命令、服务单元、进程参数、日志、凭据来源、验证对象和可执行回滚入口。
- 业务授权与平台运行权限分别核实；平台工具可用、PM 当前实例可写或平台创建成功，都不能扩大业务授权。

## 5. 当前动作最小输入与任务契约

任务契约由`核心主干 + 已命中风险附加包`组成。只为当前实际动作提供输入，未来动作在真实切换时再读取相应 Skill 和事实：

- **共同输入**：业务结果、当前现实、主要矛盾、项目与工作区、根规则、正式任务身份、边界、授权、验收和停止条件。
- **设计**：现有需求或契约、必须保持和允许改变的内容、受影响消费者、设计验收和获授权写回位置；复杂设计再提供按[项目文档入口](../../../docs/AI编程协同机制/00-模板入口.md)登记的唯一活动文档、当前版本、消费者和计划归档位置。
- **开发**：目标模块或文件、当前基线、正式设计或任务内设计责任、构建和最小自测入口。
- **测试**：待验证主张、对象与版本、环境和数据、验证入口、判定标准、证据位置和已知未覆盖。
- **Git**：仓库、HEAD、唯一工作区、目标分支和每项 Git 动作授权。
- **运维**：目标环境、候选版本、正式脚本或运行手册、凭据来源、验证和回滚入口，以及生产、数据、停机和费用授权。
- **事实与事件**：任务主面、项目事实入口、证据与发布记录写回位置、事件身份、普通事件聚合入口、PM 紧急控制目标、终态回源模式和消费游标责任。

缺失但可调查的输入写成任务责任，不写成状态枚举；不涉及的动作不展开，也不填写占位状态。

复杂正式任务使用以下语义契约。它是模型和正式任务之间的输入协议，不是给用户复制的固定回复模板；核心主干始终存在，风险附加包只在命中时加入，相同内容可以合并：

```text
核心主干
- 任务：业务任务 ID / 版本 / 正文锚点或摘要 / 执行回合 / 唯一控制实例或待创建关系
- 结果：业务结果 / 当前现实 / 主要矛盾 / 明确不做
- 入口：项目 / 工作区 / 唯一任务主面 / 当前目标与事实入口
- 当前放行：读写边界 / 当前动作实际授权 / 待调查缺口与写回责任
- 节奏：用户检查点 / 自动推进范围 / 普通失败修复与回测 / 停止条件
- 验收：验收依据 / 一手证据 / 收口主体 / 正式写回位置
- 回源：普通事件聚合入口 / PM 紧急控制目标 / 终态回源模式

按需附加
- 新建文件：路径 / 用途 / 使用者 / 入口 / 维护与回收
- 复杂设计：活动文档 / 版本 / 授权 / 消费者 / 归档
- Git/worktree：仓库 / 基线 / 工作区 / 分支 / 当前动作授权
- 数据：对象 / 写入不变量 / 验证 / 回滚或补偿
- 环境、服务、发布、生产：目标 / 当前现实 / 凭据来源 / 验证 / 回滚 / 授权
- 多任务与共享：依赖 / 所有者 / 隔离 / 接力 / 合流
- 长时间、费用、不可逆：预算 / 观察证据 / 决定者 / 停止和恢复
- 异常生命周期：来源 / 现场 / 控制冲突 / 恢复条件
```

派发时已经知道且当前动作会使用的文件、模块、接口、命令、脚本、环境、版本和用户入口必须直接写入；未知但可调查的内容明确交给任务控制实例发现并在终态回传。未命中的附加包整段省略，不写`不涉及`，也不能为填满契约而编造。

任务主张跨多个参数、环境、分支、入口或版本时，派单前必须编译修改前判别矩阵。用户或任务包点名的每条路径都进入复现前置、停止条件和最终验收；只验证一条不能代表整项主张。授权内仍有能区分根因的安全路径时继续取证；最终结论覆盖多条路径时，修改前证据必须说明缺陷命中路径和基线对照路径。

任务授权后，唯一任务控制实例连续推进调查、设计、开发、测试、边界内修复、回测、获授权写回和收口；动作切换和普通里程碑不是等待 PM 续派点。

## 6. 正式任务创建与 Worker 交接

用户已经按 PM 主文件授权创建或恢复正式任务、且第 3—5 节闭合后，PM 才执行派发：

1. 使用项目已有业务任务编号约定；没有约定时生成稳定且可区分的业务任务 ID，并在平台创建前明确版本和执行回合。不得用平台 thread ID、内部协作实例 ID或普通文档路径替代业务任务身份。
2. 新业务的任务契约写`实例登记或领取方式=平台创建回执登记（非阻塞）；包装无冲突时不发送 claimed/started`。来源不明、直接恢复、重复实例、共享写入未隔离或控制关系冲突时不得套用该值，先转生命周期作业包完成阻塞领取或裁决。
3. 新业务调用平台正式任务创建能力，继续既有业务优先使用已登记正式任务。任务提示完整传递第 5 节契约，并只把`identity-worker`指定为任务控制身份；当前 Action Skill作为基于主要矛盾的初始建议写入契约，不与 Worker身份并列成两个控制入口。Worker先核对任务身份、当前放行段、检查点、授权和回源关系，再按当前动作需要加载对应方法：设计用`task-design`，实现或修复用`task-dev`，验证用`task-test`，Git、环境、发布或运行动作用`task-ops`；未来动作只描述自然语言路线，由同一 Worker 在真实切换且检查点允许时加载。
4. 派单前按平台真实能力冻结终态回源模式为`定向终态消息 / 平台完成观察器 / 明确人工消费`之一。定向能力可用时选择`定向终态消息`；不可用时必须真实建立平台完成观察器；两者都不可用时选择`明确人工消费`并向用户说明。人工消费还必须登记完整终态正文所在的正式任务最终结果或持久终态入口、消费责任、读取触发和消费游标/幂等依据；没有可读入口或责任者时不能把人工消费写成有效回源。只有前两种模式可以承诺自动回传，不用高频轮询冒充观察器。
5. 子任务中的 PM 紧急控制目标必须写明`以新任务包装中平台实际注入的 source_thread_id 为准`，不得硬编码当前、祖先或历史 thread ID；普通进展、阶段消息和任务内变化先进入平台任务事件、任务主面或任务授权指定的持久入口，由 PM 按游标批量消费，不逐条唤醒。`paused / failed / candidate_completed / completed`作为每执行回合唯一收口信号，不受普通聚合规则约束，按已冻结模式回源。
6. 按平台实际返回类型登记，不转换、猜测或混用不透明 ID：
   - 返回真实`threadId`时，连同实际`hostId`、项目、环境或 worktree登记为正式任务控制实例；只有真实`threadId`可以传给要求 thread ID的等待、读取或消息能力。
   - 只返回`clientThreadId`时，仅登记为 worktree准备中的排队句柄，不登记为真实任务控制实例，不把它传给要求 thread ID的工具，也不宣称任务已经开始运行；等待平台或界面完成准备后再登记真实任务。
7. 真实`threadId`就绪后，按平台要求使用线程等待能力做一次有界启动确认，只判断任务是否已经启动；这次等待不是终态监听，不得据此承诺后续终态可达。随后返回用户，不打开任务代执行，也不持续等待普通进展。排队句柄不能用于这次等待。
8. 创建调用超时、返回内容不完整或结果不明时，先按业务任务 ID、平台创建记录和项目定点核对是否已经产生任务；无法确认时登记`创建结果不明`并停止重试，不盲目重复创建。
9. PM 向用户说明业务任务 ID，以及平台实际返回的真实`threadId + hostId`或排队`clientThreadId`、实际项目和工作区、授权边界、冻结的终态回源模式、当前是准备中、运行中、需要关注、已完成还是失败，并说明用户从哪里进入任务查看和纠偏；不得只回复“已派单”，也不得把准备中写成已经开始。
10. 平台能力不存在或确认创建失败时，明确说明任务尚未创建、实际失败原因、已冻结契约和最小恢复动作；不使用内部协作实例、后台助手或文档记录冒充正式任务。
11. 已有任务的来源、版本、工作区或控制实例冲突时不重复创建，转入[异常生命周期与收口作业包](lifecycle-and-closeout.md)裁决。

本文件只负责把事件身份、证据要求、普通事件聚合入口、PM 紧急目标和停止条件编入任务。创建后的事件消费、暂停恢复、异常终态、终态不可变和返工回合由生命周期作业包维护；多个任务的共享对象、隔离、依赖和合流由协同作业包维护。

## 7. 纠偏与越界恢复

用户在正式任务对话纠正口径、验收、检查点或本任务具体动作授权后，任务控制实例先保存用户原意，区分继续有效、作废和新增内容。锚点外变化保留原任务版本；锚点内变化递增任务版本并把新正文锚点送达 Worker。变化只作用于当前任务时，Worker更新必要设计或契约、受影响验证与证据后继续，不要求用户回 PM 重复，也不等待 PM 审批或转述；完整`task_updated`事件进入普通聚合入口。

变化同时影响共享对象、其他活动任务、主线路线、资源分配或安全边界时，用户决定对当前任务仍是直接输入。Worker暂停有冲突的动作，保留不受影响部分，把用户指令锚点、实际生效范围、当前现场、设计或契约路径、版本、正文锚点、变化摘要和受影响消费者立即交给 PM；PM负责协调其他任务和控制面，不重新批准用户已经明确的决定。真实权限不足、未授权生产、不可逆风险或事实矛盾仍按红灯处理，不能用直接指令绕过。

用户在 PM 对话改变主线、任务结果或边界时，PM 先判断既有任务是否仍有价值；改变任务结果、边界或验收时更新任务版本，不用补充消息静默改写已经运行的契约。契约未变但需要重新执行，或已投递终态后需要返工时，转入生命周期作业包决定新执行回合。

PM 已越界修改执行资产时立即停手，不暂存、提交、继续实现或执行破坏性回退。只登记改动文件、候选 diff、分支或 worktree和 Git 现实，标记`待唯一任务控制实例独立验证后决定`；先明确工作区归属，再由任务实例决定采用、修复或排除。
