# 复杂派单与初始化作业包

只在 `SKILL.md` 已判定当前任务涉及复杂写入、首次项目初始化、Git/worktree、服务、数据、生产、不可逆操作、目标冲突或完整重新规划时完整读取本文件。低风险单一只读派单不得读取。

## 1. 意图编译

把用户输入分为四类：

1. 已明确的业务结果、明确不做和授权。
2. 可从项目入口、代码、配置、Git、测试或正式事实调查的内容。
3. 会改变业务结果、验收偏好、生产权限、不可逆或高成本路径，必须由用户决定的内容。
4. 前后冲突、无法同时成立的要求。

可调查事实交任务控制实例在授权内发现并回写，不把技术栈、测试命令、服务器地址和发布流程整理成用户问卷。不得发明实现方案、性能阈值、固定轮数、并发量、数据规模、灰度方式或验收指标。

### 1.1 重新规划

先区分`继续/优化`与`重新规划/重新设计/换方案/推倒重来`。用户明确要求重新规划时，旧路径、阈值和下一步失去默认决策权；旧进度只作背景证据，已生效的安全边界、不可逆限制和当前运行事实继续有效。

用户没有给出新方向时只问一个问题：`这次重新规划，您最想改变原方案的哪一点，或希望新方案首先解决什么结果？`答复前不改正式文档、任务状态、控制实例、主技术路径、阈值或预算，也不派单。用户已给方向时直接编译，不重复询问或汇报旧进度。

快速方向门禁只读足以识别对象、安全边界和正式入口的最小事实；不展开历史、代码实现、旧任务全文或全量 Git。方向补齐后在内存中一次形成任务简报，只做一次矛盾扫描、一次聚合写回和一次集中校验。

### 1.2 冲突扫描

至少检查：

- `连续做到完成`是否与`某阶段结束后等待确认`冲突。
- 业务结果是否要求上线/发布，但目标环境、发布授权来源或失败回滚边界未知。
- 业务结果、明确不做、验收、写入边界和终态是否互相排斥。
- 用户只表达`稳定后上线/修好后发布`时，是否把期望终态误写成生产执行授权。

一个缺失决定会改变业务结果或自动路径时，只问当前最影响方向的一个问题，保留任务草案；不得带冲突启动任务。没有方向冲突时，用已确认事实和`任务控制实例自行发现并回写`补齐技术入口。

### 1.3 权威事实与并行任务包

涉及两个以上候选任务、共享契约或唯一集成责任时，派单前先冻结一份短`权威来源清单`：来源路径或外部记录 ID、版本/哈希、适用范围和冲突时优先级。再从中提取`跨任务不变量`，只记录会被多个任务共同消费的路由、字段、枚举、范围、共享禁止修改对象和合流责任；不得复制整份设计到每个任务包。

每个任务包从同一清单派生。创建前对所有任务包中的同名不变量做一次`跨包精确比较`：值一致才放行；冲突时只暂停受影响任务包并回到权威来源核对，无冲突任务可继续。不能用“执行中再 shared_conflict纠正”替代派单前比较，也不能把可从正式契约、代码或配置核对的事实转问用户。

## 2. 项目能力与任务初始化

项目首次接入时，PM 只在项目总览建立稳定能力结果台账骨架，不先扫描全项目。稳定结果只用`未初始化/可用/需刷新/阻塞/不适用`；`调查中/待用户确认/待现场核验/已解锁`和唯一责任任务只进当前工作台的项目能力初始化协调表。稳定事实进项目事实文件；任务、实例和事件只进当前工作台或任务主面。

PM 先从现有台账和任务自动路径识别真正会被使用的能力，不为完整度初始化无关能力。缺口存在时：

1. 在 PM 单写协调表和原业务任务包登记`能力、稳定结果、当前初始化阶段、正式写回位置、最低解锁条件、唯一初始化责任任务`。
2. 可从项目入口、代码、配置、脚本、测试、Git、环境或既有文档发现的事实交任务控制实例调查，PM 不亲自执行，也不转成用户问卷。
3. 只有业务取舍、真实权限或调查后仍无法确定的事实进入引导式问题；问题带候选值、来源、影响和`确认 / 纠正 / 不知道，请继续调查`路径。
4. 用户答复、事实核验和能力解锁都在原任务完成；任务实例写项目事实文件和任务主面，达到当前动作最低条件后沿原任务继续，不返回 PM 等待续派，也不直接修改 PM 单写协调表。
5. 同一能力同一时刻只允许一个初始化责任任务；其他任务只消费已确认部分或登记依赖，不创建第二初始化线。PM 消费事件后更新协调行和项目总览稳定结果。

标准实际路径来自`docs/AI编程协同机制/项目事实/README.md`。对应项目事实文件尚不存在时，PM 不把内部文档创建转问用户，而是在原业务任务包和当前工作台文件创建登记表中直接写入：`允许新建文件=是 / 标准项目事实文件 / 确定路径 / 使用者 / 项目事实索引与项目总览入口 / 持续保留`。用户明确禁止文档写入、路径越出项目或要求非标准文件时才红灯；这不授权 Git暂存、提交、推送或其他文件写入。

能力已`可用`且没有命中刷新触发时，PM 只在任务包引用正式入口；`需刷新`只列当前动作相关易变事实，不要求全量重新初始化。用户确认不能替代代码、Git、测试、服务或生产现场核验。

任务进入`可执行`前确认：

1. 任务 ID、任务版本、业务状态、执行回合、唯一任务控制实例/待领取和直接 PM 控制目标明确。
2. 业务结果、明确不做、读写边界、自动路径、验收、一手证据、收口主体、黄灯与红灯去向闭合。
3. 每个实际动作都有事实入口、`不适用`或发现后回写责任；标准项目事实文件缺失时已有确定路径和创建授权。
4. 写文件、Git、环境、服务器、发布、生产数据和外部费用分别授权；未知高风险动作只到只读预检。
5. 用户在当前任务对话直接纠偏；纠正记录、唯一契约、受影响验收、任务主面和证据都有写回位置。

只有验收明确依赖真实账号、短信、生产写入、隔离数据库、故障注入或外部资费时，增加定点`高风险验收资源预检`：记录资源是否可用、验证对象生命周期和缺失时影响。资源不可用但不阻塞授权内主交付时，提前从本轮覆盖中明确排除并写入完成剖面；资源直接决定业务结果时才形成最小红灯。普通任务不做全项目资源盘点，也不把技术入口整理成用户问卷。

修复上限优先使用证据和风险停止规则：仍能取得新证据、风险未扩大且在边界内就继续；同一失败重复且没有新验证动作，或下一步需要扩权、高风险、不可逆操作时停止。只有用户或正式规则明确给出时才使用固定次数。

### 2.1 动作初始化包

按自动路径填写，不涉及的动作合并写`不适用`；初始化中的动作同时写状态、正式入口、责任和本轮刷新项：

```text
项目与规则：稳定结果/初始化阶段；根目录、AGENTS.md、项目入口；刷新项
设计：稳定结果/初始化阶段；项目事实标准路径或唯一需求/契约；刷新项
开发：稳定结果/初始化阶段；工程开发基线标准路径、目标模块、构建和自测入口；刷新项
测试：稳定结果/初始化阶段；测试与验收基线标准路径、环境/数据、基线失败和证据位置；刷新项
Git：稳定结果/初始化阶段；仓库、HEAD、工作区、目标分支及 add/commit/push/merge 分项授权；刷新项
运维：稳定结果/初始化阶段；运行环境、部署发布运行手册标准路径、验证和回滚入口；本次版本与现场刷新项
安全与凭据：稳定结果/初始化阶段；安全凭据索引标准路径、来源、使用边界和预检责任，不复制密钥；刷新项
文档与事件：稳定结果/初始化阶段；任务主面、项目事实索引、证据、发布记录和直接 PM 目标；刷新项
```

稳定事实由任务控制实例持续复用；写文件、测试和发布前只刷新相关易变事实。

## 3. Git、工作区与高风险授权

- 任务分支和 worktree 由任务控制实例维护。PM 只冻结目标分支、工作区归属和 Git 分项授权。
- 平台自动生成 worktree 时直接登记，不提前建立同分支副本；已有任务 worktree 时不重复创建。
- `开始开发/测试/发布`不自动授权`git add/commit/push/merge/rebase/reset/stash`，各项按任务事实记录。
- 用户授权业务终态或生产发布，不自动授权远端推送、分支合流、强制 Git、生产数据修改、停机、删除或新增资费。
- 既有正式流程明确包含且当前授权覆盖的动作可执行；未知具体动作写`从正式流程发现，按已授权部分执行并回写；超出部分红灯`。
- 数据写入任务增加非空覆盖、幂等、事务/检查点和回滚/补偿不变量。
- 服务、凭据或发布任务在执行前核对最终命令、服务单元、进程参数、日志、凭据来源和回滚入口。

## 4. 标准任务简报

非低风险快路径使用以下语义；允许合并同值字段，不得漏掉边界和消费者：

```text
任务 ID与业务结果：
任务版本 / 业务状态 / 执行回合 / 最后已消费事件：
任务控制实例/待领取：
业务口径与明确不做：
正式依据或本轮设计责任：
读写边界：
自动执行路径：
动作初始化包：
允许操作、环境、实例和修复上限：
验收标准与一手证据：
收口方式：自动 / PM / 用户
黄灯通知条件：
红灯停止条件及去向：
任务内纠偏与回归责任：
写回位置与直接 PM 控制目标：
```

任务主张若跨多个参数、环境、分支、入口或版本，派单时必须先把`修改前复现矩阵`编译完整：用户或任务包点名的每条判别路径，都同时进入复现前置、停止条件和最终验收。只验证其中一条路径不能代表整项主张；授权内仍有能区分根因的安全路径时属于黄灯继续取证，不得据此发送`failed/red`。最终 GREEN 覆盖多条路径时，修改前 RED 也必须明确哪条路径用于命中缺陷、哪条用于基线对照，不能只把分支完整性留到修复后验收。

PM 只按正式生命周期事件消费任务状态，不把 worker 的普通 commentary 或“准备发送终态”当成已发生事实，也不据此做阶段路由。任务包遗漏判别路径时，应优先在派单前修正；任务运行后只有收到`red/shared_conflict`、用户改变契约或正式终态证据不足时才发送控制输入。终态已经投递后，退回必须进入同一任务的新执行回合，不能要求原回合撤回、修订或覆盖终态。

稳定业务任务 ID 必须由 PM 在调用平台创建正式线程前生成并写入任务包；平台返回的 thread ID只登记实例，绝不能生成或替代业务任务 ID。任务需要首次创建标准项目事实文件时，还必须在`读写边界`或`动作初始化包`中写明前述创建授权，不能只写“自行发现并回写”。

任务授权后，任务控制实例连续推进到收口或红灯；里程碑只回写进展，不成为等待 PM 续派点。PM 不要求实例先向自己汇报再代问用户。

## 5. 纠偏与越界恢复

用户在任务对话纠正口径、验收或授权后，由任务控制实例更新纠正记录、唯一契约和受影响验收，回归后继续。只影响本任务时随终态回传；影响共享契约或其他活动任务时发送共享事件。

PM 已越界修改执行资产时立即停手，不暂存、提交、继续实现或破坏性回退。只登记改动文件、候选 diff、分支/worktree和 Git 现实，标记`待任务控制实例独立验证后采纳`；先明确唯一工作区归属，再由任务实例决定采用、修复或排除。
