# BEYOND R5-R2 多维发布验收计划

> 状态：待老板确认的测试计划，不是通过结论。
>
> 冻结对象：`BEYOND-R5-PRE-RELEASE-CANDIDATE-R2-20260822.zip`
>
> SHA-256 以候选 ZIP 同目录的`.zip.sha256`文件为唯一核对入口，不在公开计划中复制动态哈希。
>
> 冻结含义：测试期间不修改这个 ZIP。任何产品源码变化都必须生成新候选、新哈希和新轮次，不能用修复后的结果覆盖本候选失败现场。

## 1. 为什么重新规划

此前测试已经证明静态规则、固定脚本、候选完整性和一个新鲜 Worker 回传闭环，但还不足以证明整套产品稳定。主要缺口是：

1. 静态检查、CLI 隔离探针和 Codex Desktop 真机任务曾被混为同一层证据；
2. 成功路径多，忙碌、插话、重启、暂停、工具缺失、重复回调和多任务交错覆盖不足；
3. 测试偏重机制“有没有执行”，对目标完成度、最后一公里、反驳与澄清、服务器操作效率覆盖不足；
4. 新项目验证较多，老项目升级、原生规则保留、多项目身份和历史工作台迁移覆盖不足；
5. 单次通过较多，重复稳定性、顺序变化和平台更新后的兼容性覆盖不足；
6. 修复后常只重测缺陷点，没有系统验证此前稳定能力是否回退。

因此，本轮不能再用“几个案例成功 + 脚本全绿”宣布正式版通过。

## 2. 测试原则

### 2.1 四层证据分开裁决

| 层级 | 证明内容 | 不能证明 |
| --- | --- | --- |
| E0 静态与确定性脚本 | 文件一致、规则短路、固定运行时和清单正确 | 模型真会照做 |
| E1 隔离进程与测试项目 | 安装、发现、文件/Git行为和模型基础理解 | Desktop任务拓扑、回调时序 |
| E2 Codex Desktop真机 | 用户可见任务、PM/Worker、回调、插话、重启和并发 | 真实服务器与生产发布 |
| E3 受控远端与老项目灰度 | SSH、部署、回滚、旧项目迁移和真实业务链 | 所有未知项目与未来Codex版本 |

任何一层失败都不能被另一层绿色覆盖。

### 2.2 测试对象必须唯一

- 每轮记录 ZIP 哈希、候选文件清单、Codex Desktop/CLI版本、模型、推理强度、项目路径、项目编号和主机编号；
- Worker final、回调、PM验收和工作台事务分别取证，不用PM摘要代替Worker原文；
- 保留应测总数、通过、失败、不能判断、未执行和排除原因；
- 首次失败证据只读冻结，修复后建立新轮次。

### 2.3 不做组合爆炸

十个变量不做全排列，而采用主路径 + 单变量 + 成对组合：

- 请求：清晰短提示 / 清晰长提示 / 模糊提示 / 用户前提错误；
- 路由：直接请求 / PM正式任务 / 团队协作；
- Worker终态：已完成 / 已暂停 / 工具失败；
- PM状态：空闲 / 正在回答 / 用户插话 / 重启恢复；
- 并发：单Worker / 两个错开完成 / 多个近同时完成；
- 项目：全新 / 老项目 / 同机多项目；
- 动作：本地代码 / Git / SSH与发布；
- 环境：Windows本地 / Linux远端；
- 模型：平台默认 / 项目已确认矩阵；
- 证据：正常 / 缺失 / 重复 / 迟到。

## 3. 发布硬门

必须同时满足：

1. 所有 P0 用例通过，不能有“不能判断”或跳过；
2. P1 用例没有影响主线的未解决失败；
3. 同一个关键回传组合连续三轮通过，且不是重复使用同一任务记录；
4. 没有默认创建 reviewer、内部助手、worktree、Hook、长期结果信箱、额外CLI或后台进程；短期pending消费后必须删除；
5. 简单正式任务只有一次PM派单、一个Worker、一次终态收口，普通过程PM往返为0；
6. 老项目数据、原生规则、工作台和项目事实没有被候选覆盖；
7. 真实远端测试未获授权时必须明确记为未覆盖，不能由本地模拟替代；
8. DSH或其他模型独立审查只负责发现遗漏，不能替代运行证据。

### E10 效率与“顺手感”对照（P1，6组）

每组同时记录：总耗时、模型回合数、工具调用数、读取文档数、PM中途往返、暂停次数、Worker数量、老板人工干预次数、最终目标完成度。

| ID | 对照场景 | 目标 |
| --- | --- | --- |
| E10-01 | “帮我开发一个明确小功能” | 一Worker闭环，不问无关信息 |
| E10-02 | “帮我解决这个Bug”+直接证据 | 直接修复验证，不走长流程 |
| E10-03 | “帮我设计一个功能”但信息模糊 | 先问必要业务问题，不仓促实现也不发问卷 |
| E10-04 | “帮我发布一下”且事实齐全 | 一次建立生产上下文，连续执行 |
| E10-05 | 新模块 vs 最后一公里 | 后者不得重启全套设计或扩张工具链 |
| E10-06 | 短提示 vs 长提示表达同一目标 | 最终业务结果一致；长提示不导致规则污染，短提示不导致消极等待 |

硬指标：

- 简单正式任务：1次PM派单、1个Worker、0次普通过程回PM、1次终态收口；
- 默认 reviewer、辅助正式任务、worktree和持久后台对象均为0；
- 清晰请求中，不因流程额外要求老板操作；
- 模糊请求最多先问一个会改变结果的核心问题；
- 目标完成度按“结果完整、证据真实、范围克制、连续推进、沟通成本”五项评分，每项满分5，任一项低于4则不能称为顺手感通过。

## 5. 分批执行顺序

不一次性把全部测试扔给一个模型：

1. **批次A：冻结与安装**——F0 + I1；
2. **批次B：路由与单Worker**——R2；
3. **批次C：终态回传核心矩阵**——C3；
4. **批次D：开发/Git与目标完成度**——G4 + D5；
5. **批次E：远端、模型与团队**——O6 + M7 + T8；
6. **批次F：稳定性重复与效率对照**——S9 + E10；
7. **批次G：独立审查**——只审证据分母、遗漏和错误归因；
8. **批次H：灰度安装**——前七批全过后，才安装到万事通并先跑低风险canary。

每批结束只给一份裁决：`通过 / 不通过 / 不能判断`。失败后停止进入下一批，不一边修源码一边继续累计绿色结果。

## 6. 修复后的回归规则

这不是新增运行规则，只约束本次测试工程：

1. 缺陷修复后生成新候选和新哈希；
2. 先复测原失败用例；
3. 再跑它直接影响的用例组；
4. 再跑四个永久哨兵：简单直接请求、一个正式Worker、完成/暂停回传、精确Git交付；
5. 最终发布前重新跑全部P0，不继承旧候选的P0绿灯；
6. 文案、检查器或提示词本身有错时，单独归为测试资产缺陷，不能修改断言迁就产品输出。

## 7. 最终裁决口径

- `源码候选通过`：只表示E0/E1通过；
- `真机候选通过`：表示E2全部P0通过；
- `老项目灰度通过`：表示E3中老项目迁移和受控远端场景通过；
- `可以发布`：以上三项同时成立，P1没有影响主线的未决失败，并完成独立证据审查；
- `生产稳定`：只能在发布后经过约定观察期和真实项目结果证明，发布前不得提前使用这个结论。
