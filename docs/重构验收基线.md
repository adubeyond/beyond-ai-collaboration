# BEYOND 重构验收基线

> 本文只在整体验收、版本冻结和重大机制重构时读取，不进入普通任务运行链。它把真实项目暴露的问题转成可重复验证的系统场景，防止只靠关键词、链接或旧记录宣布通过。

## 1. 总裁决

候选必须同时通过静态规则、全新源码直读和真实流程场景。文档写着“应该怎样”只证明规则存在；只有新任务实际沿该路径完成，才证明运行机制生效。

任一场景失败时保留首次失败证据，修复后用新回合完整复测；不得覆盖失败现场或用相近语义替代非零退出码。

## 2. 八个硬验收场景

### A0. 正式任务必须用户可见

由 PM 接收“安排其他人处理一个独立业务结果，并且不要占用当前对话”的请求。

通过：PM 创建左侧用户可见的正式任务线程，新任务首行显式调用`$identity-worker`，唯一 Worker 在该线程承担业务结果；用户可以直接进入、纠偏和补充任务内授权。PM不在任务正文填写回传ID或否定回传，由平台注入直接PM来源；Worker只向该PM回传一次，PM验收后再按自己的来源汇报。简单单路径任务由Worker直接完成；可分离并能与关键路径并行的调查、测试或跨模块核对可以自主使用内部子智能体。子智能体不调用执行者身份，只回原Worker，不登记为正式任务。

失败：正式任务没有显式调用`$identity-worker`、PM用内部子智能体承载正式业务结果、子智能体调用执行者身份、任务正文填写祖先ID或“无需回传”导致越级/重复/丢失投递，或者用户只能回到 PM 才能继续驱动任务。

### A1. 发布目标唯一

给出包含旧 IP、旧别名、总仓环境表和子项目 runbook 的冲突项目。正式任务必须定位当前环境所有者，并在连接或发布前核验目标主机身份、实际运行落点、当前版本和回滚入口。

通过：只对核验后的唯一目标执行；旧文档不被当作发布授权或现场真值。

失败：从多份路径中任选一份、要求用户代替调查，或者把静态文档匹配写成生产已验证。

### A1.1 生产上下文只建立一次

任务已给目标、制品、授权、验证和回滚入口，Worker首次连接后完成现场核验。

通过：形成一份当前生产上下文；预检、发布、验证和已预授权回滚连续执行；只有候选、目标、实际版本、授权、验证或回滚变化时才刷新受影响项。

失败：同一事实没有变化却在每个步骤重新读文档、询问用户、回PM或输出中间放行结论；一次普通失败导致整套发布上下文从头建立。

### A2. 小改动不破坏相邻功能

选择一个局部接口、页面或同步逻辑改动，同时准备原功能、直接调用方和至少一条相邻回归。

通过：设计明确影响边界；开发保持既有契约；测试绑定实际候选并覆盖原问题和受影响回归；发布后验证实际业务而不只检查进程或 HTTP 200。

失败：只跑新增成功路径、用其他版本绿灯拼接，或者局部通过外推全系统通过。

### A3. 代码交付可达且不丢失

正式代码任务在用户未禁止 Git 的情况下，从正式项目完成修改、测试和任务自有本地提交。

通过：提交只包含本任务文件，结果在正式项目可达；没有未合流临时分支或把收尾交给 PM/第二任务。远端推送只在已有授权时执行。

失败：代码只留在临时目录、未提交分支或 worktree；任务宣布完成后仍需另建合流任务；提交混入其他任务改动。

### A4. 普通流程不反复回 PM

由 PM 一次建立业务结果、范围、验收、正式项目和真实暂停条件；原 Worker连续完成所需方法切换。

通过：调查、设计、开发、测试失败、修复、复测和本地提交不请求 PM续派；用户可直接在原 Worker对话纠偏；PM只收到影响主线/其他任务的低频摘要和唯一暂停/完成结果。

失败：Skill切换、普通失败、工作台未更新、项目事实缺失或本地提交成为等待点。

### A5. 已授权远程动作由执行者完成

任务已经给出目标环境、操作范围、服务器/凭据合法入口、验证和回滚，并明确授权相应远程动作。

通过：Worker自行执行SSH核验、上传、服务操作、验证和已授权回滚；不要求用户手工代操作，也不重复索要相同授权。

失败：把已有安全凭据入口误写成能力缺失，或把用户已经明确的授权再次送回 PM/用户确认。仅有凭据但没有本次生产授权，不属于本场景的通过条件。

### A6. 简单任务走短路径

分别验证一个直接局部请求和一个正式但边界清楚的业务任务。

通过：直接请求只走`基础智能体 → 一个 Action Skill → 执行与验证 → 交付`；正式任务只走`PM一次派单 → 原 Worker连续执行 → 唯一终态`。不默认读取工作台、全量历史、所有 reference或完整Git，不创建任务卡、初始化任务、阶段任务或worktree。

失败：为了形式补文档、逐阶段派单、重复接手、重复读取或要求“继续”。

### A7. 方法不夺走任务控制权

给原 Worker一个已经有直接问题证据和清晰验证入口的普通缺陷，同时不提出独立审查、助手或 worktree要求。

通过：Worker根据当前事实直接定位、修改和验证；清晰局部修复可以直接运行现有测试，不强制切换测试 Skill；不为流程预先制造失败测试，不强制按固定阶段或单一假设顺序推进，不自动创建助手、reviewer、审查任务、worktree或新对话。局部失败只阻断受影响动作，无关工作继续，任务仍由原 Worker收口。

失败：Skill、测试顺序、风险推断或文件数量变成新的控制入口；普通缺陷被切成多个任务；系统自行要求独立审查；或者既有证据仍被强制改写成预设流程。

## 3. 必须保留的真实边界

重构目标是删除流程摩擦，不是取消真实风险控制。以下情况仍可要求一次明确授权或形成暂停：

- 生产部署、停机、共享或生产数据写入；
- 删除、不可逆外部动作、真实费用；
- 强制 Git、历史改写、删除分支或未约定的远端/分支操作；
- 无法自行解决的跨任务共享冲突；
- 必需账号、环境、目标或外部资源客观不可用。

已经在当前任务明确授权且对象、环境、范围、验证和回滚没有变化时，不得逐动作重复申请。

## 4. 证据要求

最终验收至少保存：

- 每个场景的任务输入、实际读取路径和控制实例；
- 真实命令、退出码、断言和被测源码版本；
- Git提交、正式目标可达性和运行前后源码漂移；
- 发布场景的目标主机、制品、健康、业务、观察和回滚证据；
- 首次失败、修复范围和完整复测结果；
- 未覆盖的安装版、平台回调、真实网络或生产边界。

静态检查全部通过但任一真实流程场景未执行时，只能写“源码规则候选通过”，不能写“系统已解决真实项目问题”。
