# 真实案例与 90 秒演示

[English](en/real-case-and-90-second-demo.md) | **简体中文**

这不是概念动画，也不是把测试脚本包装成用户案例。下面的具体业务案例最早来自 BEYOND 3.2.2 在 Windows、Codex Desktop 和本地 Node.js 测试项目中的真实验证；BEYOND 3.2.4 又在真实 Windows 项目中回归了单任务回传、双任务独立回传、暂停后由原 Worker 恢复，以及错误项目编号在写入 pending 前被拒绝。项目名、绝对路径、thread ID 等私有现场信息已省略。

制作公开宣传内容时，使用与当前正式版本一致的[3.2.4 图文视频脚本](promotion/90秒演示制作脚本.md)，不要把下面的历史函数名冒充成当前版本的新功能。

## 90 秒演示分镜

| 时间 | 画面 | 旁白重点 |
| --- | --- | --- |
| 0–10 秒 | 用户在 PM 中给出目标、验收和权限 | 用户说明“要什么结果”，不需要先设计一套流程 |
| 10–20 秒 | PM 登记唯一 Worker 后立即结束当前回合 | PM 管主线和验收，不陪跑、不轮询 |
| 20–50 秒 | Worker 实现一个格式化函数、补测试并运行完整测试 | 同一个 Worker 连续完成开发和验证，不拆成多轮人工接力 |
| 50–65 秒 | Worker 冻结 final、保存短期回执、回调 PM，然后结束 | 回调负责叫醒，正式 final 与回执保存事实 |
| 65–80 秒 | PM 自动醒来，读取正式结果并核对提交和测试 | PM 不把“代码写完”误判成“已发布” |
| 80–90 秒 | 工作台显示任务已完成并归档，回执已删除 | 一个结果只验收一次，项目主线可继续推进 |

如果要把本页流程作为行为证据，应保留真实 Codex 任务、真实命令输出以及失败或暂停步骤。面向传播的图文视频可以简化画面，但不得冒充行为测试证据。

## 案例一：正常完成并自动收口

真实目标是在一个本地 CommonJS 工具包中新增 `formatEnvironmentKey` 并从统一入口导出。

结果证据：

- 一个正式 Worker 从实现连续推进到测试和本地提交；
- 完整测试 `25/25` 通过，`git diff --check` 通过；
- 形成一个本地提交；
- Worker 依次执行一次回执入队、一次原生回调和一次正式 final；
- 回调后没有继续调用业务工具；
- PM 执行一次验收、一次历史归档和一次回执确认删除；
- 没有纠正 turn、替代 Worker、重复验收、推送或发布。

这里证明的是“目标 → 执行 → 证据 → 回传 → 验收”的本地闭环，不证明代码已经推送、部署或生产可用。

## 案例二：真实暂停后由同一 Worker 恢复

另一个任务需要用户提供确认代号。Worker 没有猜测代号，而是形成“已暂停”终态，PM 将唯一原因和恢复条件登记在工作台。

用户后来提供代号 `R7-OK-03` 后：

- PM 只恢复原 Worker，没有创建替代任务；
- 原 Worker 输出 `REQUEST-R7=R7-OK-03`；
- 暂停和完成阶段各有一次回执、一次回调和一次控制面提交；
- 最终活动记录为 0、历史完成记录为 1、待处理回执为 0；
- 全程没有重复验收或重复归档。

这说明“暂停”不是丢任务。缺少真正的业务输入时停止；输入到位后，原责任人继续完成同一个结果。

## 你可以怎样复现

1. 按[安装、升级与项目初始化指南](../模板交付包/docs/安装升级与项目初始化指南.md)安装正式版本。
2. 用[快速开始](快速开始.md)建立或采用一个干净本地项目。
3. 在 PM 中给出一个可验证的小目标，明确允许的文件、Git 和环境边界。
4. 观察 PM 是否只创建一个正式 Worker并立即结束派发回合。
5. 核对 Worker 是否先形成自包含终态、保存短期回执、执行一次回调，再输出正式 final。
6. 核对 PM 是否只验收和归档一次，并在工作台事务成功后删除回执。
7. 再运行一次缺少必要业务输入的任务，确认它暂停后仍由原 Worker恢复。

## 这份证据不能证明什么

- 不能证明所有 Codex Desktop、CLI 或第三方平台版本都具有相同任务与回调能力；
- 不能证明测试通过的代码已经推送、部署或发布；
- 不能替代你的项目权限、服务器、数据和回滚验证；
- 不能用一次成功案例证明长期运行永远不会遇到平台偶发故障。

BEYOND 的承诺不是“永不失败”，而是尽量让责任、证据、暂停原因和恢复入口保持清楚、可读和可收敛。
