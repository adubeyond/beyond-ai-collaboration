# PM结果回传中断修复记录

## 1. 现象与裁决

- 真实现象：PM正在生成面向用户的长回答时，另一个正式Worker的完成消息被平台注入为新的用户消息；前一回答虽然已经生成，但界面随即切入回传处理，用户感受为原回答被打断或丢失。
- 根因：当前Worker规则要求在暂停或完成时直接调用平台消息能力写入来源PM。该路径把后台控制面结果变成了前台对话输入，无法保证只在PM安全边界消费。
- 本轮裁决：不增加Hook、轮询器、事件回合或新身份；把普通暂停/完成结果写入控制仓本机收件箱，由PM在用户主动触发的安全边界批量读取。

## 2. 保留边界

- 一个正式任务仍由一个用户可见Worker连续负责。
- 业务状态仍只有`进行中 / 已暂停 / 已完成`。
- Worker任务和正式证据入口仍保存完整结果；收件箱只保存裁决所需的紧凑增量。
- PM仍负责核验来源、更新工作台和项目主线，不成为过程消息中继。
- 直接用户任务没有PM来源时，仍直接向用户交付，不创建收件箱记录。

## 3. 最小实现

固定脚本`模板交付包/scripts/beyond-control.mjs`增加本机命令：

```text
inbox --action enqueue  # Worker写入暂停/完成增量
inbox --action list     # PM在安全边界读取当前项目待处理结果
inbox --action ack      # PM完成核验和工作台更新后归档
```

记录写入`local/inbox/pending/<project-id>/`，消费后移动到`local/inbox/history/YYYY-MM/<project-id>/`；`local/`已经由Git忽略。相同待处理结果幂等去重，每个项目独立读取；当前项目的损坏记录停止消费，不能拖死其他项目。

## 4. 明确不做

- 不向来源PM直接发送普通暂停/完成平台消息。
- 不在PM回答过程中后台轮询或自动消费。
- 不把收件箱做成第二张任务台、完整证据库或消息总线。
- 不修改、安装或初始化万事通。

## 5. 验收

1. Worker暂停/完成可以写入、列出、去重、按项目隔离和归档。
2. 无效状态、错误项目、错误来源或损坏记录必须失败可见。
3. PM只在用户新回合、显式状态查询或显式收取结果时消费，先回答当前问题，不被收件箱抢走话题。
4. Worker规则不再要求调用平台消息能力；现有直接回源断言全部替换，不能同时保留两条路径。
5. 现有静态、隔离、安装、团队协同和模型策略回归继续通过。
