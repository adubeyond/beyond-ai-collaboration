# BEYOND v3.2.3 Upgrade Guide

> Comparison: `v3.2.2 → v3.2.3`. This release fixes an operations-consumption gap where generic `task-ops` guidance was correct but a Worker could still miss the project's owned Git, PR, CI, or server entry and use an older copy. It adds no identity, business state, approval stage, or second runtime.

## Project operations routing

1. Before Git, PR, required-CI, SSH, deployment, release, or rollback actions, read the current project root and follow its project fact index to the unique formal owner.
2. The generic Git and runtime references keep common safety boundaries without hard-coding project IPs, accounts, remote protocols, scripts, or CI fields.
3. Migrated history, candidates, mirrors, and other working directories cannot replace the managed script or runbook declared by the project. A conflict stops only the affected action until one owner is confirmed.

## Installation boundary

- `v3.2.3` uses a new immutable Release ZIP and SHA-256. Changed Skill bytes must not continue to identify themselves as the official `v3.2.2` release.
- The upgrade still replaces the complete control candidate and all six Skills while preserving project `local/`, `projects/`, `shared/`, and native root rules. Run full installation verification and confirm the loaded version in a new process.
- This patch grants no Git, server, production, data, deletion, or credential authority. Project-specific authorization and protected entry points remain project-owned.

## Release acceptance

The candidate must pass public-content, implementation-path, installation-integrity, and project-routing regressions. A real project also needs a new task to prove it consumed the installed `task-ops` and the project's unique formal entry rather than merely searching the source tree.
