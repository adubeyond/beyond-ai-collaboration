# BEYOND v3.1.0 Upgrade Guide

> Comparison: `v3.0.9 → v3.1.0`. A published release does not automatically upgrade any real project or make it production-ready; installation, entry fusion, and the actual target still require separate verification.

## Added in this release

- One sibling `beyond-control` repository for BEYOND documents, project-level documents, team tasks, and collaboration records.
- A Git-ignored `local/` workbench with local backup and restore.
- Shared Markdown team tasks and collaboration with precise default-branch updates, conflict stops, and compact archives.
- Separate prompts for a new project and an existing-project adoption or upgrade.
- A fixed-action script for control-repository initialization, project inspection and registration, full `AGENTS.md` fusion with backup, synchronization, summaries, and archive operations.
- A project-level Codex identity guard that preserves session identity through continuation, resume, and compaction and mechanically blocks PM business writes while preserving existing project Hooks.

## Preserved from v3.0.9

- PM and Worker remain the only agent identities. Design, development, testing, and operations remain methods selected by the same Worker.
- One user-visible Worker remains responsible for a formal business result.
- Business state remains `in progress / paused / completed`.
- Personal tasks do not load the shared team path and gain no new approval, PM round trip, reviewer, or worktree workflow.
- Business code, branches, tests, releases, and rollback remain owned by each business project's existing mechanisms.

## Initialization

Installation displays two prompts with the global identity entry and does not scan or modify a project automatically:

- Enter `$identity-pm`, then `Use BEYOND to initialize this new project.`
- Enter `$identity-pm`, then `Use BEYOND to adopt or upgrade this existing project.`

Existing projects are inspected before the user confirms each fusion or migration group. The fixed-action script backs up the original entry and existing Hooks. A business project receives the full fused root runtime entry plus the `.codex` identity guard, not a copy of the whole BEYOND documentation tree. The user reviews and trusts the Hook once after first installation or a content change.

Local fusion does not grant remote Git authority. The fixed script creates a shared project record, a minimal project overview, and a minimal facts index so the fused entry has no broken targets. When these foundations must be shared, the user authorizes the push separately and only those three files for the same project may be sent through the `project-registration` scope. HTTP credentials and query parameters in a remote URL are never written into local or shared Markdown.

## Release validation

Before release, validation covered installation integrity, control-repository and project-Hook fusion, identity registration/restoration/write blocking, root-entry replacement continuity, control-repository initialization, project-entry fusion without stacking the v3.0.9 managed kernel, cross-drive and space-containing control paths, local backup and restore, precise pushes, remote sanitization, and path-traversal rejection. All 200 aggregate assertions across 71 real Codex isolated scenarios passed, the full PM-dispatch/unique-Worker/terminal-callback/PM-closeout chain passed 24/24 checks, and real long-context compaction restoration plus human freeze review were completed. These results cover only the tested Windows/Codex environment and declared scenarios; they do not claim that every platform, real project, or production environment has passed.
