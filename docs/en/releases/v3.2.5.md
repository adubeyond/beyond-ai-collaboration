# BEYOND v3.2.5 Stable Upgrade Guide

> Stable release: v3.2.5 (2026-09-05). Previous candidate tags remain unchanged.

## Stable release follow-up

- An actually ended, unfinished Worker turn reports progress to its original PM; ordinary parameter, path, test, and method errors are not business pauses.
- Callback handling, route correction, and task restoration preserve the user's remaining foreground questions.
- Read-only workbench inspection distinguishes active review, committed-state acknowledgement, and conflicting evidence without guessing or deleting records.
- Internal helpers remain advisory; registered Workers retain ownership of formal business outcomes.
- Approved project defaults use Sol/high for design/analysis and complex high-risk work, Terra/high for ordinary engineering, and Luna/high for frozen bulk processing. Existing Workers and the PM are not automatically reconfigured.

## A new PM learns the project before designing tasks

- On its first takeover, a new PM reads the root entry, current project identity and route, project overview, current workbench, project-fact index, and every current primary fact owner, then builds the project/repository/module map. The owner does not need a fixed phrase to reteach the project.
- A PM with established context reuses unchanged understanding and refreshes only the workbench, route, and fact owners affected by the current request. History, archives, candidates, every Worker chat, the full source tree, and raw evidence stay outside the default takeover chain.
- For a nontrivial short request, the PM uses the lightweight `task-design` mode to close the business result, context, boundary, acceptance, and the only real owner decision before producing a compact task contract. Technical design, implementation, testing, and release choices remain with the unique Worker.
- Ordinary task design stays inside the PM turn and creates no design document, plan, report, or artificial checkpoint. A task contract links only the exact relevant fact owners instead of copying a runbook or the project corpus.

Terminal delivery retains its existing order: freeze the result, enqueue a short-lived receipt, call back natively, verify and commit task state, then acknowledge the receipt. Nonterminal progress is not a completion receipt.

## R4-R6 follow-up improvements

- The first user-facing layer leads with the business result, impact, and next action instead of substituting internal fields, command inventories, or engineering jargon for judgment.
- When a user premise conflicts with current project evidence, explain the real situation before introducing a dependency, framework migration, or broader engineering scope.
- A vague request to "optimize" does not invent performance, refactoring, packaging, or future-capability goals; a verified defect receives only the smallest complete repair it needs.
- When the owner explicitly closes a non-running task with no pending receipt, `workbench.close` preserves the reason and authorization locator and records the task as closed in history.

## Package verification policy

- The ZIP is the only required download. The matching `.sha256` file is optional verification material; a missing or unavailable sidecar must not block installation.
- If a `.sha256` file is supplied and does not match the ZIP, installation must stop.
- The 65-file in-package manifest and post-install integrity verification remain mandatory with or without the external checksum.

## Project routing moves from one directory to four roots

- `canonicalProjectRoot` owns the formal BEYOND project identity; `repositoryRoot` owns the registered repository or delivery root for the task; `executionRoot` is the Worker's exact checkout; `controlRoot` owns the single control repository.
- All four roots may be identical for a local single-repository task. One BEYOND project may also cover multiple explicitly registered nested or external repositories and platform-provided existing worktrees without copying the control repository or creating another worktree.
- A cross-root task carries the complete `projectRoute` produced by `project.resolve`. The runtime revalidates project, path, Git/worktree, remote, host, and Codex project bindings before any pending write; drift fails closed instead of searching for or guessing another control root.

## Receipt isolation and upgrade preservation

- Short-lived terminal receipts use the `projectId + taskId` namespace, so same-named tasks in different projects cannot overwrite, scan, or acknowledge one another.
- Legacy task-only pending receipts migrate with concurrency-safe handoff. Duplicate copies converge only when receipt identity agrees, without creating a second business result.
- Installation and upgrade preserve registered repository roots, remotes, host bindings, and Codex project bindings. A changed current directory cannot silently rewrite formal registration.

## Unique rule owners

- Only `identity-worker/SKILL.md` owns the Worker terminal sequence. Only `identity-pm/references/lifecycle-and-closeout.md` owns matching, acceptance, pause, and receipt consumption.
- Historical return-path notes and the bilingual architecture explain evidence and component relationships without copying an executable algorithm that can drift.
- Static gates check both architecture documents, the historical record, release notes, and the changelog so the removed full-Worker scan wording cannot return as a current rule.

## Verification and usage boundary

- Local gates cover project identity, four-root routing, existing worktrees, independent-clone rejection, remote drift, project-scoped receipts, concurrent legacy migration, installation, upgrade, and public content.
- Published assets must match their source and manifest. Real installation, Codex restart, and platform callbacks remain separate evidence and are not implied by local gates or scenario reviews.
- A green candidate package is not proof of installation, publication, or long-project stability. It adds no Hook, notify branch, daemon, extra Codex CLI, or second scheduler.
