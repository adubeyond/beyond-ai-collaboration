# BEYOND v3.1.6 Upgrade Guide

> Comparison: `v3.1.5 → v3.1.6`. This release preserves one PM per project, one unique Worker per business result, three business states, same-Worker use of design/development/test/operations methods, no default worktree creation, and separate production authorization.

## 1. Problem addressed

After minimum adoption, the previous release did not persist the choice between full initialization and starting work with on-demand completion. Document migration, the project fact index, and root-entry cleanup could remain only in conversation memory, and minimum adoption could be mistaken for complete initialization.

v3.1.6 stores one managed initialization state in the project overview and provides fixed control actions to show, choose, record, and complete it. Ordinary tasks do not read this state.

## 2. Initialization path

1. Complete minimum adoption and installation verification.
2. Ask the user once: complete initialization now, or start work and fill remaining groups on demand.
3. Full initialization handles overview, architecture, development, testing, operations, security, and other project material one group at a time.
4. Every formal entry must exist; except for the overview, it must already be carried by the project fact index.
5. Completion revalidates every entry and the slim root `AGENTS.md`.
6. On-demand completion allows ordinary work immediately and later resumes at the first pending group.

The PM may migrate or register project Markdown, update the fact index, and slim the root entry only inside user-approved initialization. This does not authorize business code, tests, configuration, environments, data, remote Git, or release operations.

## 3. First step after upgrade

After upgrade and installation verification, start a PM at the project root:

```text
$identity-pm
Adopt or upgrade this existing project with BEYOND.
```

The PM resumes from the managed project-overview state. Users do not need old conversation memory, and no business task starts or resumes automatically.

## 4. Verification scope

- Two isolated legacy-project paths: 34 assertions passed.
- Team control repository: 66 assertions; implementation paths: 286 assertions.
- Installation, project-entry migration, existing-project adoption, and Worker-policy regressions passed.
- Strict public-candidate validation and `git diff --check` passed.

This evidence covers the source candidate and isolated local paths. It does not prove that a real project has already upgraded or that production is available.
