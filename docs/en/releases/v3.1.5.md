# BEYOND v3.1.5 Upgrade Guide

> Comparison: `v3.1.4 → v3.1.5`. This release preserves the main runtime: one PM per project, one unique Worker per business result, three business states, same-Worker use of design/development/test/operations methods, no default worktree creation, and separate production authorization.

## What changed

### Worker results no longer interrupt active PM answers

The previous path injected a Worker pause or completion result directly into the source PM conversation. That could preempt an answer the PM was already generating. v3.1.5 uses a project-scoped local result inbox instead:

1. A Worker registers one compact record only for a real pause or completion.
2. The PM reads the inbox once at a user-initiated turn, explicit status query, or explicit result-collection request.
3. The PM answers the current question first, then verifies the unique Worker, formal task, and main evidence.
4. The PM acknowledges and archives the record only after updating the workbench. Duplicate records are idempotent; corrupt or cross-project records fail visibly.

This intentionally removes immediate terminal wake-up that can interrupt the PM. Results are consumed at the next safe user turn; the PM does not poll in the background.

### New-Worker model policy has one owner

Project initialization shows two concrete choices:

- `platform-default`: omit model and reasoning parameters and keep platform defaults.
- `beyond-worker-matrix-v1`: Terra/high for ordinary engineering, Luna/high for large low-risk structured work, and Sol/xhigh for complex architecture, difficult diagnosis, or production risk.

An explicitly approved persistent choice is stored in a managed project-overview block and shown, saved, and resolved by the fixed script. Root overrides, the workbench, and old chat history no longer hold competing copies. A temporary choice in the current PM conversation can still override later new Workers without changing the current PM or existing Workers.

### Workbench and result facts are safer

- The PM uses a fixed validated writer for ordinary progress updates, with recoverable local backups.
- Terminal summaries preserve the original actual-versus-expected direction for field mappings, ownership, and before/after values.
- Completed tasks leave the active workbench for local monthly history; acknowledged inbox records also move to local history instead of becoming a second task board.

## Upgrade boundary

- After installation or upgrade, complete project adoption with the [Installation, Upgrade, and Project Initialization Guide](../../../模板交付包/docs/en/installation-upgrade-and-project-initialization.md). Copying files alone does not initialize an existing project.
- A legacy Worker-model line in the root override is not inherited silently. Initialization shows the actual choices; without explicit confirmation the project keeps platform defaults.
- The local result inbox is not shared through Git and does not replace the formal Worker task, main evidence, or team-collaboration documents.
