# BEYOND v3.0.3 Upgrade Guide

> Comparison: `v3.0.1 → v3.0.3`
>
> The v3.0.2 reconstruction branch never entered `main` and never received a release tag. It is not the foundation of this release. v3.0.3 was rebuilt from the v3.0.1 mainline.

## What this upgrade is

v3.0.1 established the BEYOND 3.0 collaboration framework. v3.0.3 rebuilds that framework into an operational engineering path with explicit identities, stable control, staged execution, verifiable evidence, and bounded recovery.

This is not a single prompt or isolated rule update. The comparison changes 63 files across project entry points, PM and worker identities, four professional Skills, the multi-agent protocol, task documents, handoff templates, and automated guards.

## At a glance

| Area | v3.0.1 | v3.0.3 |
| --- | --- | --- |
| Control | PM, worker, and professional Skills existed, but some paths could repeat routing or blur identity | PM controls the project, one worker controls each task, and design, development, testing, and operations Skills remain methods |
| Entry path | Simple requests and governed project work shared too much entry context | Formal project tasks and clear direct requests now have separate, minimal read paths |
| Single-task flow | Stage changes could return to PM too often | One worker can move through design, development, testing, and operations while the user continues in the same task |
| Multi-agent work | The shared protocol could become a heavy general entry layer | The protocol is read only when multiple tasks, shared writes, dependencies, or coordinated closeout actually exist |
| Return and recovery | Delivery, consumption, adjudication, and lost-instance recovery were incomplete | These facts are separate, with one terminal event per round, bounded waiting, evidence-based loss, replacement, and workspace transfer |
| Documents | Rules were repeated and long-running task records could grow continuously | Each rule has one owner; active work, formal delivery, and history are separated |

## The runtime paths

Formal project work now follows:

```text
Project documents → PM → worker → professional Skill → same worker → PM
```

A clear direct request follows:

```text
Current agent → matching professional Skill → direct delivery to the user
```

A direct request does not manufacture a PM, worker, task event, or project-takeover flow. A professional Skill inside a formal task does not become a new controlling agent.

## PM, worker, and coordination

- PM owns objectives, scope, authorization, task relationships, conflicts, and final adjudication. It does not execute development, testing, or operations commands.
- The worker is the single control instance for a business task and advances the result within the user's authorization.
- Ordinary progress may be aggregated, while completion, pause, failure, and red-light events keep explicit boundaries.
- Each task version and execution round permits one formal terminal event.
- Terminal delivery does not prove PM consumption, and consumption does not prove adoption or final adjudication.
- When multiple writers may touch the same formal object, the system must establish one writer first. If ownership cannot be established, it does not write.

## The four professional Skills

### Design

- Explains the current state, target, and approach in language the business can understand.
- Includes implementation, testing, and release paths instead of only technical vocabulary.
- Gives complex work a formal design document with active, delivery, and archive locations.
- Never describes an unimplemented proposal as developed, tested, or released.

### Development

- Reads the real stack, engineering rules, and code before deciding how to modify it.
- Reuses existing capabilities before creating new ones.
- Preserves necessary comments, contracts, failure boundaries, and engineering baselines.
- Keeps developer self-checks distinct from independent testing.

### Testing

- Operates as a software-engineering testing method rather than a generic checklist.
- Uses three verdicts: pass, fail, and cannot determine.
- Binds conclusions to actual commands, exit codes, assertions, and evidence.
- Stops equivalent retries after a platform-policy rejection and never turns “not executed” into a product failure or a pass.

### Operations

- Starts from durable server, environment, and runtime facts instead of rediscovering paths every time.
- Separates source, artifact, formal entry point, actual runtime version, and rollback baseline.
- Blocks when candidate, test, environment, or rollback anchors are missing instead of manufacturing evidence.
- Leaves cross-round pause and resume ownership with the worker while the operations Skill returns runtime facts.

## Task and document lifecycle

v3.0.3 realigns the workbench, task cards, handoff packages, complex designs, engineering baselines, test baselines, server facts, and release records:

- The workbench stores the current control snapshot without becoming a second protocol.
- A task card stores the task contract instead of absorbing every process detail.
- Complex designs and engineering facts have their own formal documents.
- Completed active work moves into one history location so primary documents do not grow without bounds.
- Templates define record formats without duplicating lifecycle or governance ownership.

## Validation

The candidate passed:

- eight public-content, mechanism-semantics, and read-path guard groups;
- 18 isolated runtime scenarios;
- 16/16 source-regression commands;
- the real minimal Node.js example test and syntax checks;
- ten release checks against a fresh export of the Git commit;
- PR validation and the post-merge `main` workflow.

These results validate the published source candidate and its documented runtime paths against the defined gates. They do not claim universal behavior across every Codex version, local installation, or production environment.

## Upgrade guidance

- New users can start with the [Quick Start](../quick-start.md).
- Existing v3.0.1 projects should preserve their project facts, task records, and business documents, then migrate template changes deliberately.
- Do not overwrite an existing project with the entire new template directory.
- No content needs to be inherited from the abandoned v3.0.2 branch.
