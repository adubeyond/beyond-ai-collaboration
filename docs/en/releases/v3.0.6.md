# BEYOND v3.0.6 Upgrade Guide

> Comparison: `v3.0.5 → v3.0.6`. A public release does not mean that any specific project has installed it or entered production.

## Why this release exists

Version 3.0.5 removed prescriptive method flows that could take control away from the task. Continued real-project and fresh isolated testing still found shorter-path problems: PM dispatch and tool commentary could remain verbose, Worker completion could duplicate the engineering report back to PM, user-facing status could expose unnecessary technical detail, and an SSH conflict could bypass the operations reference before asking for a password.

Version 3.0.6 adds no new identity or business state. It shortens the existing control path and closes the observed loading gaps.

## What changed

| Area | v3.0.5 | v3.0.6 |
| --- | --- | --- |
| PM dispatch | Business-oriented, but could still expand execution detail | Keeps only the result, scope, acceptance, formal target, fact entry, true pause boundaries, and authorization |
| Worker execution | One Worker continuously owns one business result | Preserved; design, development, testing, and operations remain methods selected by that Worker |
| Worker callback | Could repeat the full engineering report | Defaults to the business conclusion, one primary evidence entry, and impact/next action |
| PM commentary | Already reduced | Short tasks no longer narrate every read, edit, and verification step |
| User delivery | Technical evidence could appear by default | Leads with the business result, current usability, impact, and next step; technical detail is expanded on demand |
| Skill loading | Relied on Skill triggering and model behavior | An explicitly named or selected Skill must load its main instructions; references remain conditional |
| Server facts | Reusable production context | Canonical alias, verified host identity, latest resolved address, and credential source are recorded separately |
| Git concurrency | Path isolation with serialized Git mutation | Preserved; BEYOND does not create or recommend worktrees and stages task files precisely |

## Current managed-task path

```text
The user states a business result
→ PM registers one task and dispatches once
→ one user-visible Worker continuously designs, implements, tests, and completes authorized local delivery
→ the Worker returns one compact result
→ PM updates the original task and explains the current business reality
```

Ordinary repair, retesting, method changes, and task-owned local commits do not return to PM for approval. A pause is reserved for a real business decision, high-risk authorization, shared-object conflict, or an unavailable external prerequisite.

## Installing into a new project

1. Obtain the immutable `v3.0.6` Git tag rather than guessing from a moving branch.
2. Import `模板交付包/AGENTS.md` and `模板交付包/docs/AI编程协同机制/` into the new project root.
3. Install the six directories under `模板交付包/skills/` into that computer's Codex Skills directory.
4. Restart Codex and create a new task from the new project root.
5. On first takeover, establish only the project goal, formal directory, current workbench, and real technology/test/server/release entries that actually exist. Do not copy empty templates or facts from another project.

See the [Quick Start](../quick-start.md) for the installation entry.

## Upgrading from v3.0.5

- Preserve project-specific business boundaries, technology stack, server and credential entries, release paths, active tasks, and historical evidence.
- Update the root entry and all six Skills with their references.
- Remove residual fixed-stage gates, default-worktree instructions, duplicate approvals, duplicate task states, and copies of generic Skill methods from project files.
- When one environment has conflicting SSH or IP records, retain the exact canonical alias and credential source, then verify host identity from current configuration and runtime evidence.
- Restart Codex and use one low-risk real task to verify loading, Git, testing, Worker callback, and PM closeout before expanding adoption.

## Validation

The current candidate completed:

- a fresh isolated installation with candidate and installed Skill files matching;
- 102/102 baseline runtime assertions;
- 15/15 real-project problem simulations;
- 4/4 natural PM request checks;
- 24/24 persistent PM→Worker→PM control-path assertions;
- 105 public-candidate files, 143 implementation-path checks, and the minimal example;
- zero new worktrees and no access to a real project, network, server, or production system.

This evidence covers the tested Windows/Codex isolation environment and declared scenarios only. It does not prove every platform, a new project installation, real SSH access, or production deployment.

## Rollback

Restore the v3.0.5 template and six Skills, restart Codex, and preserve the project's own facts, business code, Git history, and runtime evidence. Rolling back BEYOND rules does not roll back project code or a production version.
