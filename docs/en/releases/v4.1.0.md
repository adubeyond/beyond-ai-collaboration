# BEYOND 4.1.0: collaboration and delivery

Version 4.1.0 promotes the existing isolated collaboration/delivery candidate into a complete release, not an incremental patch. This release pass adds no further business-process redesign. It preserves the 4.0.1 engineering-document foundation, native CLI sessions, and prior CLI fixes. Earlier assets remain unchanged; publication does not install into business projects.

## What changes

- **Three responsibilities, not three mandatory conversations.** Project PMs manage direction, tradeoffs, and real dependencies. Product-interaction owners make business behavior tangible through usable prototypes. Module owners combine planning and execution and may implement directly or use assistants and CLI tools.
- **Small outcomes that still compose.** Keep a user-verifiable result rather than splitting by activity. Separate frontend and backend only when coupling and parallel benefit justify it; one existing owner validates the real screen/API/data chain.
- **Prototypes complement engineering documents.** Confirm new interactions through prototypes while retaining requirements, data sources, permissions, errors, API contracts, and acceptance. Reuse existing documents, handoffs, and suitable UI Skills. Backend-only work and focused repairs do not require a UI prerequisite.
- **Acceptance follows the current design.** Optional delivery contracts bind design revisions, interface versions, and artifact references. Stale acceptance cannot close a revised contract. Machine checks validate relationships and state, not the truth of business evidence or human authorization.
- **A direct recipient for notifications.** CLI results go to their current direct owner, including checks around owner transfer. Do not broadcast to unrelated PMs, turn peer advice into user instructions, or revive paused goals from stale notifications.
- **Archived results remain inspectable.** The original owner can query a formally archived CLI task and request managed idle-manager cleanup, but cannot resume execution or create a session through that path. Manager exit and window closure remain separate; insufficient identity stays unknown.

## Compatibility and installation

The Desktop Worker terminal-receipt protocol and model policy remain on the existing foundation. Staged CLI delivery, document loading, same-session continuation, executable discovery, capability-based compatibility, managed stopping, and cleanup are retained.

The complete package contains seven Skills, including `identity-product`. Upgrade only within an authorized maintenance window. Preserve native project rules, business files, configuration, engineering sources, workbench state, CLI sessions, results, reviews, and artifacts. Do not migrate tasks or resume work automatically. Shared-Skill updates require a safe Codex restart; writing files does not prove an existing conversation has reloaded them.

Use the [installation guide](../../../模板交付包/docs/en/installation-upgrade-and-project-initialization.md). The package does not ship private gateway credentials, local profiles, or private project evidence.

## Evidence and limits

Historical candidate checks include 180 local tests and 47 installation-related checks, each tied to its own snapshot. They are not new test counts for the formal release and do not represent real business delivery cases. Current release verification must be bound to the actual source, CI, manifest, and release assets.

The observed direct two-owner handoff revalidated already completed functionality. It was not a new feature built from scratch or a fresh native execution/callback loop. Earlier network timeouts and recovery limitations are not erased by a later successful trial.

No guarantee is made for improved business quality, token savings, arbitrary concurrency, every provider/model combination, or long-term unattended reliability. Static model review is not execution acceptance; machine references do not authenticate business facts.
