# BEYOND v3.0.9 Upgrade Guide

> Comparison: `v3.0.8 → v3.0.9`. This is a control-kernel and field-regression patch. It adds no identity, business state, approval stage, or worktree workflow.

## Why this release exists

Version 3.0.8 fixed hybrid installations and model scope, but remote and real-project runs still exposed control-plane drift: a formal task could fall back to a fork, projectless task, or internal helper; PM could keep waiting and relaying after dispatch; an ordinary Worker final could be mistaken for terminal return; and model selection could follow task size while ignoring the nature of the work.

Version 3.0.9 does not add another process layer. It reduces formal task creation, PM exit, Worker terminal return, and model selection to one verifiable path.

## What changed

- PM resolves exactly one saved project by normalized path and `hostId`; zero or multiple matches stop dispatch instead of selecting a fallback project.
- A formal Worker can run only in a fresh, user-visible top-level task bound to the formal project. Forks, projectless tasks, internal helpers, and new worktrees do not carry formal task control.
- Creation succeeds only with a real platform `threadId + hostId`. A queued client identifier, title failure, or first routing failure cannot trigger a second construction path.
- After creation, PM takes one zero-time snapshot and ends the turn instead of waiting, polling, or relaying ordinary progress.
- On a real pause or completion, Worker sends one terminal result to the platform-injected direct source before ending its own task. An ordinary final does not pretend to be delivered upstream.
- When the project has adopted a model matrix, ordinary code work uses Terra/high, large low-risk non-code review uses Luna/high, and complex architecture, difficult debugging, or production risk uses Sol/xhigh. The setting applies only to newly created Workers.
- The root entry owns tool-process communication frequency; PM and Worker no longer restate parallel rules.

## What stays the same

- PM owns the mainline and team; one Worker continuously owns one business result; design, development, testing, and operations remain on-demand methods.
- Business state remains `in progress / paused / completed`.
- Ordinary implementation, repair, testing, retesting, and task-local commits do not return to PM.
- BEYOND still does not create or recommend worktrees; Git writes remain exact, serialized, and attributable.
- Remote Git, production, data, downtime, irreversible actions, and external cost remain separately authorized.

## Upgrade from v3.0.8

1. Preserve project-specific overrides, project facts, workbench state, task records, business code, and Git history.
2. From the immutable `v3.0.9` tag, replace the managed project entry and every file in the six Skills; do not retain old-version residue.
3. Run the installation verifier:

   ```text
   node 模板交付包/scripts/verify-install-integrity.mjs --installed-skills-root "<Codex Skills directory>" --project-agents "<project root>/AGENTS.md"
   ```

4. Treat the content as installed only after exit code `0`, then restart Codex and verify takeover plus formal Worker creation in a new PM task.
5. Complete or pause active old tasks before replacing runtime rules; do not hot-swap them during execution.

## Verification

- Implementation paths: 221/221; installation integrity: 5/5; strict public candidate: 120 files.
- R2 core isolated acceptance: 172/172; model matrix: 9/9; real business-language cases: 12/12; project-problem simulations: 30/30.
- Scope control: 13/13; formal control-plane integration: 24/24.
- After restart, all five formerly timed-out cases completed on their first attempt in one short sequence with exit code 0; frozen-candidate and source identities did not drift.

These results cover the declared Windows/Codex isolation target. They do not prove that a specific project has upgraded or that a real server or production release has passed.

## Rollback

Restore the v3.0.8 managed template entry and all six Skills, run installation verification, and restart Codex. Preserve project facts, business code, Git history, and runtime evidence. Rolling back BEYOND rules does not roll back business code, data, or production versions.
