# BEYOND v3.0.5 Upgrade Guide

> Status: released · 2026-08-03
>
> Comparison: `v3.0.4 → v3.0.5`. A public release does not mean that any specific project has installed it or entered production.

## Why this release exists

v3.0.4 reduced formal work to PM, one worker per business result, and three business states. Real-project use still exposed two costs: prescriptive methods inherited from external workflows could interrupt the result, and production tasks could repeatedly reopen the same target, artifact, authorization, verification, and rollback decisions.

v3.0.5 does not redesign the system. It freezes the current repair as a reproducible release: task outcomes take priority over method rituals, and one release task establishes its production context once while preserving the project-fact, testing, Git, release, and rollback capabilities already validated in v3.0.4.

## At a glance

| Area | v3.0.4 | v3.0.5 |
| --- | --- | --- |
| Engineering method | Some fixed pre-design, test-order, and review habits remained | The worker chooses reproduction, diagnosis, implementation, and validation from current facts; no universal order is required |
| Independent review | Some paths could infer it from risk or expected value | It requires an explicit user request, acceptance criterion, or pre-registered project rule |
| Subagents | Boundaries could be too tight or helpers could mirror process steps | They only assist with separable parallel investigation, testing, cross-module checks, or research and never own the task |
| Worktrees | Automatic creation was removed, but planning and closeout paths remained | BEYOND neither creates nor recommends worktrees and only handles an existing user- or platform-provided scene |
| Parallel writes | One formal project could become globally serialized | Workers with non-overlapping paths and side effects may edit and validate in parallel; shared objects and Git writes remain serialized |
| Production | Safety anchors were complete but could be rebuilt at every step | A release task creates one production context, refreshes only changed facts, and continuously performs precheck, release, verification, and pre-authorized rollback |
| PM traffic | Ordinary checks or failures could still become tasks or callbacks | Read-only checks and ordinary progress create no formal task; ordinary failure closes inside the original worker |

## Capabilities that remain

- One PM per project and one user-visible worker per business result; design, development, testing, and operations remain professional methods selected by that worker.
- Business state remains only `in progress / paused / completed`.
- Stack, test commands, servers, release, rollback, and credential entry points remain reusable project facts.
- Test verdicts remain bound to the actual object, version, environment, command, exit code, and assertions.
- Git still requires exact staging, preservation of unrelated changes, and serialized index, HEAD, and history operations.
- Production still requires one source and artifact, the actual target, health checks, critical business checks, and executable rollback.
- Complex design still uses one implementable, testable, deliverable, and archivable document.

## Prescriptive flows removed

- mandatory brainstorming or pre-design rituals;
- mandatory RED→GREEN, test-first failure manufacture, or one-hypothesis-at-a-time sequencing;
- reviewer or independent-review tasks inferred from risk;
- helper-per-step, new-task-per-stage, or routine PM approval loops;
- BEYOND-created, recommended, or automatically merged worktrees;
- repeated reads and approvals for unchanged facts inside one production task.

Result requirements replace those rituals: design must explain implementation, test, and release paths; code must satisfy the business result; testing and production must leave sufficient first-hand evidence. BEYOND no longer forces every task through one method order.

## Migrating from v3.0.4

1. Finish or pause active tasks before replacing rules that their workers may still read.
2. Preserve project code, workbench, project facts, servers, release records, credential entry points, and historical evidence. Do not overwrite a real project with the whole template.
3. Update root `AGENTS.md`, PM/worker, and the four Action Skills, then synchronize only the workbench and 03 entry actually used by the project.
4. Remove three legacy references so stale rules cannot still be discovered:
   - `identity-pm/references/cross-task-coordination-and-review.md`
   - `task-dev/references/implementation-debugging-and-repair.md`
   - `task-ops/references/git-worktree-and-resource-closeout.md`
5. Use the replacement `cross-task-coordination.md` and `git-and-resource-closeout.md` references.
6. Restart Codex so a fresh process discovers the new Skills, then observe one low-risk real task before expanding adoption.

To roll back, restore the v3.0.4 template and six Skills, remove the v3.0.5 replacement references, restart Codex, and follow the project's backup record for replaced entry files. Rolling back BEYOND rules does not roll back business code or a production version.

## Validation boundary

The release gate covers public content, runtime paths, shared Git, the minimal fixture, a fresh isolated installation, post-install Skill discovery, and one low-risk real-project observation. Isolated and real-project evidence only proves the tested object and environment; it does not claim universal behavior across every Codex platform, real SSH target, or production system.
