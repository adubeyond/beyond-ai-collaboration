# BEYOND 3.2.15: transfer an auxiliary CLI without losing its session

This release extends the existing owner-transfer mechanism to one unregistered `assist` CLI task under explicit user authorization. Its current run must have completed and process ownership must be verifiable. The task remains auxiliary: no formal workbench entry or new execution session is created.

The transfer preserves the task ID, native session ID, model and effort configuration, contract, historical results and reviews. The previous owner loses control. The successor independently reviews the preserved result before continuing the same session within the existing business authority; historical reviews remain evidence rather than becoming the successor's decision.

Duplicate requests reuse the original transfer journal. Competing destinations and interrupted transfer phases cannot both acquire control. A process crash leaving an orphaned lock keeps control blocked until existing recovery checks verify that the process has exited and the state still matches; the implementation does not ignore locks or seize live processes. Tasks already registered or archived in the workbench are not implicitly reassigned through the auxiliary route. Existing formal CLI transfers remain compatible.

The candidate passed 149/149 isolated CLI regressions across 11 groups, including 41 transfer tests with 19 new auxiliary cases. These cover identity preservation, successor review, former-owner rejection, duplicate and competing requests, interruption recovery and a real child-process exit with an orphaned lock. This is not a claim of a live provider-session handoff or production business acceptance. Full-product validation, clean-source packaging, upgrade/rollback verification and public Windows/Ubuntu CI are separate release gates; see the release artifacts and PR checks for their actual results.

The release retains the 3.2.14 requirements/design workflow, engineering-document integration, artifact retention, receipt-write retry and existing CLI fixes. Six Skills, Desktop Worker callbacks, receipt order, task states and the model matrix are unchanged. Installation does not transfer, resume or start any existing task, change local authentication, or add business authority.
