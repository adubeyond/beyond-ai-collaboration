# BEYOND v3.0.4 Upgrade Guide

> Status: released · 2026-08-01
>
> Comparison: `v3.0.3 → v3.0.4`. The current public release is `v3.0.4`; a public release does not mean that any specific project has installed it or entered production.

## Why another revision

v3.0.3 rebuilt the real root, PM, worker, and professional-Skill chain. Real-project feedback still showed that task versions, execution rounds, terminal events, default worktrees, and layered document gates could make ordinary work take a long route and keep PM busy with process callbacks.

Version v3.0.4 shortens the default path instead of adding another layer of exceptions. PM manages the team, one worker continuously owns one business result, and design, development, testing, and operations remain professional methods selected by the worker or a direct caller.

## At a glance

| Area | v3.0.3 | v3.0.4 |
| --- | --- | --- |
| Business state | Task state coexisted with terminal-event, consumption, and adjudication facts | Business state is only `in progress / paused / completed`; test and operations verdicts are not task states |
| Worker execution | Cross-Skill execution was possible but still carried round and terminal protocols | One worker controls one result; ordinary failures, repair, retest, and task-local commits do not return to PM for approval |
| PM | Managed the mainline and consumed formal terminal events | Maintains a low-frequency workbench, task relationships, and evidence-based closeout without acting as a message relay or stage approver |
| Project takeover | Entered the full document entry by default | Reads the workbench first and enters document governance only when the workbench is empty, missing, conflicting, or document work is actually needed |
| Workspace | Worktrees were a common isolation mechanism | The user-selected project is the default workspace; BEYOND does not create worktrees automatically, serializes shared-directory writes, and uses Git across independent clones |
| Coordination | Centered on a multi-agent event protocol | The 03 mechanism only handles real cross-task dependencies, shared objects, write order, and handoff; it is not part of single-task startup |
| Project facts | Could drift toward capability initialization | Stack, tests, servers, release, rollback, and credential entry points remain, but they are no longer startup licenses or capability states |

## Default runtime paths

### PM-managed formal task

```text
User → PM creates a user-visible formal task with one worker
     → worker selects design/development/testing/operations as needed
     → internal subagents only assist locally and return to that worker
     → ordinary failure closes inside the same worker
     → pause or completion returns to PM at low frequency
     → PM updates the workbench from the formal target and first-hand evidence
```

### Clear direct request

```text
User → current base agent → matching Action Skill → direct delivery
```

A direct request does not manufacture a PM, worker, workbench row, event, or execution round. An Action Skill inside a formal task does not become a new controlling identity.

## Production-grade boundaries that remain

- File, Git, service, data, environment, production, and external-cost permissions remain separate dimensions.
- Only one worker writes a formal directory at a time; unrelated dirty changes are preserved and task commits contain only task-owned files.
- Complex design keeps one active document that is implementable, testable, deliverable, and archivable.
- Testing keeps `pass / fail / cannot determine` and binds verdicts to real commands, exit codes, and assertions.
- Release still binds one candidate, target environment, actual runtime, and executable rollback; health checks do not replace critical business checks.
- Only a business choice, high-risk boundary, unresolved shared conflict, or unavailable required external resource can pause work.
- Completion requires the result to reach the agreed formal target and pass current first-hand acceptance.

## Legacy mechanisms intentionally replaced

The following are no longer part of the default runtime contract:

- the full task-version, execution-round, event-ID, and one-terminal-per-round protocol;
- claim, start, candidate-completion, and ordinary-progress lifecycle messages;
- PM confirmation for ordinary stage changes, repair loops, and task-local Git commits;
- automatic worktree creation or switching;
- capability-state or full project-fact initialization as a task prerequisite.

They are replaced by more direct sources of truth: the workbench stores low-frequency team state, the formal task stores process, Git stores version and ownership, and tests and runtime store first-hand evidence.

## Migrating from v3.0.3

1. Preserve project code, the current workbench, task records, stack, server, release, and credential entry points. Do not overwrite a real project with the full template directory.
2. Update root `AGENTS.md`, PM/worker, and the four Action Skills, then migrate the workbench and document entry only where the project needs it.
3. Point active references from the old 03 protocol to the cross-task coordination and shared-object mechanism.
4. Keep existing task-version and execution-round evidence as read-only history; it does not need to be rewritten into the three-state model.
5. Finish or pause active tasks before the gray switch. Do not replace rules while multiple workers are writing the same directory.
6. After isolated installation passes, use one low-risk real task to verify reading, Git, testing, and return behavior before expanding adoption.

## Current validation

The released version has completed:

- structure, link, Skill-entry, and key-rule checks across 94 public files;
- 40 implementation-path guards, including explicit formal-worker identity, internal-subagent, and direct-PM return boundaries;
- a fresh isolated installation and nine real Codex paths with a 34/34 machine verdict;
- a source-direct Codex Desktop topology probe, preserving three defect traces before a passing user-visible worker with explicit `$identity-worker` startup and a direct-PM-only return path;
- direct modification, formal worker repair, design → development → testing, complete-artifact release, controlled-failure rollback, real pause, and PM cold-start A/B;
- `git diff --check` and isolated-authentication cleanup.

This evidence still does not prove that the local patch has been installed and automatically discovered by a fresh process, nor SSH, production release, remote Git integration, or universal behavior across all platform versions. Source-direct Desktop creation and callback behavior has passed, but it does not replace installed-runtime validation.
