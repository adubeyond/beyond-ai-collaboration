# 安装、权限与平台支持

[English](en/install-permissions-platform.md) | **简体中文**

> 核心边界：能读取`AGENTS.md`、能加载 Skill 或能启动内部子智能体，都不等于当前 Codex 表面已经具备 BEYOND 的完整正式任务协作。完整模式还要求 PM 能创建用户可见任务、向指定任务继续发消息、读取任务结果，并允许用户直接进入该任务纠偏。

本页是安装链、Codex 运行权限和平台能力的唯一公开产品事实入口。项目任务包继续拥有业务授权；各 Skill 只执行本页契约，不自行发明平台能力。

## 1. 零依赖项目模板管理器

本版本唯一正式支持和验收组合是 Windows + Codex Desktop，要求 Node.js 24.x 作为当前脚本实测基线。管理器只把`模板交付包`中的`AGENTS.md`、`docs/AI编程协同机制/`和`skills/`安装到一个显式项目目录；它不会安装到 Codex 或其他工具的真实运行目录，也不会覆盖目标项目自己的`README.md`。

从当前 BEYOND 来源根目录运行：

```text
node scripts/beyond-install.mjs install --target <目标项目绝对路径> --dry-run
node scripts/beyond-install.mjs install --target <目标项目绝对路径>
node scripts/beyond-install.mjs version --target <目标项目绝对路径>
node scripts/beyond-install.mjs verify --target <目标项目绝对路径>
```

升级必须来自准备采用的新 BEYOND 来源，并先验证当前受管文件没有漂移：

```text
node <新来源>/scripts/beyond-install.mjs verify --target <目标项目绝对路径>
node <新来源>/scripts/beyond-install.mjs upgrade --target <目标项目绝对路径> --dry-run
node <新来源>/scripts/beyond-install.mjs upgrade --target <目标项目绝对路径>
```

成功升级会输出备份 ID。回滚前仍会验证当前树，避免覆盖升级后的用户改动：

```text
node <当前来源>/scripts/beyond-install.mjs rollback --target <目标项目绝对路径> --backup <备份ID> --dry-run
node <当前来源>/scripts/beyond-install.mjs rollback --target <目标项目绝对路径> --backup <备份ID>
```

每次安装或升级都按原始字节生成逐文件 SHA-256 与整树摘要。目标已存在同名文件、受管文件被修改、目标或父路径出现符号链接、清单损坏、来源缺文件或哈希复核失败时，操作直接停止。升级先在唯一 pending目录构造并逐文件复核备份，完整清单写成后才以同一文件系统原子重命名发布为可选备份；构造失败只清理本次 pending目录，不暴露半成品，也不改变目标树或安装清单。升级替换中途失败会恢复旧文件与旧安装清单；回滚中途失败会恢复回滚前候选，保持可重试。

项目运行后通常会修改工作台或项目事实文件；这些都是受管文件漂移。管理器不会自动合并或覆盖，必须先人工审查并决定怎样保留项目事实，再重新取得可验证状态。

## 2. 权限配置契约

BEYOND 把六件事分开：

| 边界 | 回答的问题 | 事实来源 |
| --- | --- | --- |
| 业务授权 | 这项任务允许改哪些文件、Git、服务、数据或生产对象 | 用户与正式任务包 |
| 审批策略 | Codex 何时暂停并请求用户或自动审查 | 当前回合实际`approval_policy` |
| sandbox | 旧配置体系下命令能接触哪些文件与网络 | 当前回合实际`sandbox_mode`及对应设置 |
| permission profile | 新配置体系下文件与网络的组合规则 | 当前回合实际 profile 与规则 |
| 文件边界 | 哪些根可读、可写或拒绝 | 当前回合实际 filesystem/writable roots |
| 网络边界 | 是否可联网以及允许的目标 | 当前回合实际 network 规则与一次无副作用探针 |

平台实际注入值是运行真值；项目设置、旧回合、创建请求或界面预期只能说明期望。平台没有暴露某个必要能力时，最多用一次无副作用标准调用探针确认。工具允许执行不等于业务已授权；业务授权也不能扩大 sandbox。

Codex 当前文档定义了两套不能混用的 sandbox 配置：

- permission profiles：`default_permissions`与`[permissions]`，用于组合文件和网络规则；
- 旧 sandbox：`sandbox_mode`与`[sandbox_workspace_write]`。

如果任一加载配置、CLI 参数或选中 profile 提供旧`sandbox_mode`，Codex 会按旧体系处理，而不是把它与`default_permissions`合成更大权限。`approval_policy`另行控制审批暂停；因此`default_permissions`单独出现不能证明`approval_policy=never`，也不能证明某个新任务实际为不弹审批的 Full Access。旧体系中“无沙箱且不弹审批”需要当前回合实际同时为`danger-full-access`与`never`。permission profile 路径也必须分别核对实际 profile、审批策略、文件和网络结果。

正式来源：[Permission modes](https://learn.chatgpt.com/docs/permission-modes)、[Permission profiles](https://learn.chatgpt.com/docs/permissions)、[Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)。permission profiles 当前仍标为 Beta，兼容结论必须绑定实际客户端版本和运行证据。

## 3. Codex Desktop 支持边界

| 运行组合 | 当前产品状态 | 正式任务能力要求 | 缺能力时的边界 |
| --- | --- | --- | --- |
| Windows + Codex Desktop | 本版本唯一正式支持和验收组合 | 当前会话必须实际暴露用户可见的任务创建、指定任务消息、任务读取和用户直接纠偏；不能从“能用 Skill”推导 | 不宣称完整 PM→worker；只在当前会话已授权边界内采用单任务执行或用户手工创建/转发 |
| Codex CLI、IDE、cloud、Linux（含 Ubuntu）、macOS或其他客户端 | 未承诺、未验证，不属于本版本支持范围 | 即使能读取`AGENTS.md`、加载 Skill 或显示 subagent，也不能证明满足正式任务契约 | 不建立虚假的正式任务生命周期；未来兼容性另立任务，当前差异不列为`PROMOTION_GATE`阻塞项 |

产品版本、账号、管理员策略和当前会话暴露的工具都可能缩小 Windows + Codex Desktop 的能力；一个表面的证据不能外推到另一个表面。其他平台上的标准库脚本可能可以运行，但代码可移植性不构成产品支持或验证证据。

## 4. 自然语言控制回归

公开 CI 在`windows-latest`和 Node.js 24上运行：

```text
node scripts/check-control-contracts.mjs
```

它只确定性检查跨文件规则所有者、依赖入口、权限互斥、快速开始警示、安装入口、编码策略和 CI 接线，并明确输出`behavior=NOT_RUN`。字符串存在或静态脚本通过不是模型行为 GREEN，也不能代替 Codex Desktop 的真实行为验证。

取得可重复的真实行为探针计划：

```text
node scripts/check-control-contracts.mjs --list-behavior-probes
```

计划至少覆盖真实事故精确两轮、PM 同义动作词、无 PM 的直接执行、明确 PM→执行者移交、终态后的身份释放/下一任务、组合动作、含糊指令和用户可见任务标题。标题 case 要同时保留子任务首条提示中的机器 Skill ID、`create_thread → set_thread_title`顺序、最终中文标题及标题失败不阻塞业务任务的相邻证据；PM 不得为标题打开、读取或等待子任务。每个 case 必须在互相独立的全新 Codex 任务中逐字发送；保留表面、客户端版本、Skill树哈希、原始输出、任务定位和人工裁决。只有同一冻结候选的真实任务结果才能关闭行为发布门禁。

## 5. 换行、编码与平台证据

- 所有公开文本使用 UTF-8 无 BOM和 LF；根`.gitattributes`对 Markdown、JavaScript、JSON、YAML和 PowerShell文本固定`eol=lf`，PNG标记为 binary。
- Git blob、安装来源、安装清单和运行副本都按原始字节计算哈希，不做 CRLF/LF归一化。未登记的换行变化就是漂移。
- Windows checkout 必须让 Git遵守`.gitattributes`；手工复制应使用保持原始字节的文件复制。编辑器把文件改成 CRLF或加入 BOM后，`verify`应失败，而不是把它登记成同一候选。
- 当前候选的管理器和测试只依赖 Node.js 标准库。原生 Windows/Node.js 24测试是当前一手证据；公开 CI 在`windows-latest`和 Node.js 24上重复控制契约、安装事务、promotion checker和最小示例，但仍只验证脚本，不能代替 Codex Desktop 真实行为。CLI、Linux（含 Ubuntu）、macOS、IDE和云表面均未承诺、未验证，不是本版本发布阻塞；代码可能可运行不等于产品支持。
- 项目模板安装与 Codex runtime Skill 安装是两条链。当前管理器不写运行副本；运行时安装、版本切换和缓存刷新必须使用对应 Codex 表面的正式路径。

当前候选只完成建设源，不等于已经晋级、发布或安装到任何运行环境。
