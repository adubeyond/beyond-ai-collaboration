# BEYOND 3.2.14：先把需求与设计说清，再连续交付

简短业务目标仍然可以作为起点，但不再被自动当成完整设计和开发批准。PM先调查项目事实，带着推荐方案与用户讨论，将相关需求和技术设计写回已有正文；用户确认本轮范围后，同一执行者连续开发、测试及完成已授权交付。

## 本次变化

- **需求说清楚**：用户、完整流程、做什么与不做什么、数据来源、权限、异常和可观察验收。不编造性能指标，也不要求用户填写技术问卷。
- **设计落实到依据**：复用的技术栈、中间件、接口、模块边界、失败处理和验证入口。小任务只写相关章节，不要求每次创建三份文档或填满全部模板。
- **批准范围可追溯**：保留需求/设计路径、章节、适用修订和用户确认来源；已有批准切片、正常修复和复测继续执行。业务范围、公开契约、权限、验收或关键路线发生变化，只重新确认受影响部分。
- **多模型讨论**：主设计者加一个不同模型独立审查，重大分歧再加第三个。按具体证据融合，不投票，不把不同CLI或同模型别名算成异模型，也不把审查通过当成用户批准。
- **反复失败换分析方法**：两轮针对性修复仍失败且没有新证据时，先进行异模型诊断；有新定位证据则继续，不机械停工。协助者只读分析，原执行者保留写入和交付责任。
- **文档随实现维护**：保留目标、设计和实际实现的区别；共享文件当次一位写入者，架构只保存稳定事实与决策入口，不堆每轮审批流水。

## 一并交付的既有维护

纳入此前完成但尚未公开发布的生成物回收和备份去重修补。测试临时目录有明确所有权与回收路径；保留紧凑证据、源码快照和必要恢复材料；范围备份复用已验真的内容。不会根据时间或体积自动删除业务目录、独有成果或用户恢复包。

## 不变的部分

回执文件被Windows临时占用时，最终原子替换复用既有重试函数，最多200次、每次请求等待5毫秒；实际耗时受系统调度影响，不承诺固定秒数。次数耗尽仍失败则保留错误，不无限重试、不删除旧文件再重建。这是唯一获准的回执实现修补。

回调顺序、短期回执格式、任务状态、原执行者恢复、三种CLI协作和模型矩阵保持原协议。新审查规则复用已有模型入口，不安装新CLI、不修改全局认证或强制所有用户购买额外服务。模型不可用时明确说明未完成审查，用户可指定替代或明确豁免范围；调查与方案讨论不因此停止。

这是完整升级包；已有项目不重做初始化，不撤销现有批准、不恢复旧任务。安装和正式业务验收需在目标项目分别确认。本次发布不包含业务项目安装。
