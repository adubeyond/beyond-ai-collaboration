# BEYOND v3.0.3 升级说明

> 对比范围：`v3.0.1 → v3.0.3`
>
> `v3.0.2`的重构分支未进入`main`、未创建正式标签，也不是本次发布的基础。`v3.0.3`从`v3.0.1`主线重新建设。

## 这次升级是什么

v3.0.1建立了BEYOND 3.0的协作框架；v3.0.3把这套框架重构为一条身份清楚、控制权稳定、能够分层执行、可以验证和恢复的真实工程运行链。

这不是单个提示词或局部规则更新。两个版本之间实际改变63个文件，覆盖项目入口、PM与Worker身份、四个专业Skill、多智能体机制、任务文档、交接模板和自动化守卫。

## 主要差异

| 维度 | v3.0.1 | v3.0.3 |
| --- | --- | --- |
| 控制关系 | 已有PM、Worker和专业Skill，但部分路径仍可能重复路由或混淆身份 | PM负责项目总控，Worker控制具体任务，设计、开发、测试、运维Skill只提供方法 |
| 启动路径 | 入口和背景材料较多，简单请求与项目任务的边界不够集中 | 明确区分正式项目任务与清晰直接请求，只读取当前动作真正需要的内容 |
| 单任务推进 | 阶段切换可能频繁返回PM，增加控制面占用 | 同一Worker可以连续选择设计、开发、测试和运维方法；用户也可直接在该任务对话继续指挥 |
| 多智能体协同 | 协同规则较重，存在被当成通用启动层的风险 | 只有多任务、共享写入、依赖或统一收口真实出现时才读取03协同机制 |
| 结果与恢复 | 回传、消费、裁决和失联恢复的边界不够完整 | 分开记录送达、消费和裁决；补齐唯一终态、有界等待、失联证据、替补与工作区移交 |
| 文档治理 | 规则在多个入口重复，长任务容易持续膨胀 | 每类规则只有一个所有者；活动文档、正式交付和历史归档分离 |

## 真实运行链

正式项目任务现在沿以下路径运行：

```text
项目文档 → PM → Worker → 专业 Skill → 原 Worker → PM
```

清晰直接请求沿以下路径运行：

```text
当前智能体 → 对应专业 Skill → 直接交付用户
```

直接请求不会凭空创建PM、Worker、任务事件或项目接管链。正式任务中的专业Skill也不会成为新的控制智能体。

## PM、Worker与协同机制

- PM负责目标、范围、授权、任务关系、冲突和最终裁决，不下沉执行开发、测试或运维命令。
- Worker是具体业务任务的唯一控制实例，在用户授权范围内连续推进结果。
- 普通进展可以聚合，完成、暂停、失败和红灯等关键事件保持明确边界。
- 每个任务版本、每个执行回合只允许一个正式终态。
- 终态送达不等于PM已经消费，PM消费也不等于已经采纳或完成业务裁决。
- 多个写入者可能触碰同一正式对象时，必须先确定唯一写入者；无法确认所有权时不冒险修改。

## 四个专业Skill

### 设计

- 使用业务可理解的语言说明当前状态、目标和方案。
- 给出实现、测试和发布路径，而不只罗列技术名词。
- 复杂需求形成独立设计文档，并明确活动位置、交付位置和归档位置。
- 尚未实施的方案不会被描述成已经开发、测试或上线。

### 开发

- 先读取现有技术栈、工程规则和真实代码，再决定怎样修改。
- 优先复用现有能力，避免重复造轮子。
- 保留必要注释、接口契约、异常边界和工程基线。
- 开发自检只证明开发侧检查，不冒充独立测试。

### 测试

- 明确定位为软件工程测试方法，不是泛化检查清单。
- 使用“通过、不通过、不能判断”三态裁决。
- 结论必须绑定真实命令、退出码、断言和证据。
- 平台策略拒绝执行后停止等价重试，不把“没有执行”写成产品失败或测试通过。

### 运维

- 从稳定的服务器、环境和运行事实记录开始，避免每次重新猜测路径。
- 分开源码、制品、正式入口、实际运行版本和回滚基线。
- 缺少候选、测试、环境或回滚锚点时明确阻断，不临时制造证据。
- 长时间观察由Worker持有暂停、恢复触发和下一回合，运维Skill只返回运行事实。

## 任务与文档生命周期

v3.0.3重新整理了工作台、任务卡、交接包、复杂设计、工程基线、测试基线、服务器信息和发布记录之间的关系：

- 工作台只保存当前控制快照，不成为第二套协议。
- 任务卡保存任务契约，不无限吸收所有过程记录。
- 复杂设计和工程事实进入各自正式文档。
- 活动任务完成后进入统一历史位置，避免主文档持续增长。
- 模板只定义记录格式，不重复拥有生命周期和治理规则。

## 验证

本次候选完成并通过：

- 8组公开内容、机制语义和读取路径守卫；
- 18个隔离运行场景；
- 16/16源码回归命令；
- 最小示例真实Node.js测试和语法检查；
- 从Git提交对象重新导出后的10项发布复验；
- PR检查和合入`main`后的远端CI。

这些结果证明当前公开源码候选及其文档运行路径通过既定门禁，但不外推为所有Codex版本、所有本机安装环境或真实生产部署均已验证。

## 升级建议

- 新用户可直接从[快速开始](../快速开始.md)建立项目。
- 已使用v3.0.1模板的项目，应先保留自己的项目事实、任务记录和业务文档，再对照新版模板逐项迁移。
- 不要用整目录覆盖的方式抹掉现有项目事实。
- 本次发布不包含任何需要从废弃`v3.0.2`分支继承的内容。
