## V2EX / 开源中国

标题候选：

> 做了一个让 Codex 多任务完成后自动回到 PM 验收的开源项目

正文：

> 最近持续使用 Codex Desktop 做真实项目时，我发现难点不再是“会不会写代码”，而是多个任务的责任、回传、暂停恢复和验收越来越混乱。
>
> 所以做了 BEYOND：一个本地项目中的 PM 管主线和验收，每个 Worker 负责一个结果。Worker 完成或真正暂停时保存短期回执并回调 PM；PM核对正式 final 后只验收、归档一次。
>
> 我用真实 Windows 项目做了单任务回传、双任务独立回传、忙碌 PM、暂停恢复、错误项目隔离和非 Git 项目安装测试。它不是云服务，不收集安装遥测，也不安装额外守护进程。
>
> 目前最希望得到的是实际 Codex Desktop 用户的安装反馈和失败现场，不是单纯求 Star。
>
> 项目：https://github.com/adubeyond/beyond-ai-collaboration
> 国内镜像：https://gitee.com/adubeyond/beyond-ai-collaboration

建议在文末明确提问：

> 你在 Codex 多任务协作中最常遇到的是上下文丢失、无人收口，还是权限边界混乱？

## 掘金短帖

标题候选：

> 我用两天测试了 Codex 多任务回传：真正难的是任务收口，不是写代码

导语：

> 两个 Worker 都说“完成了”，不代表项目真的完成。谁核对测试？谁确认提交范围？暂停后由谁恢复？如果 PM 必须持续轮询，所谓多智能体只是把人工催促放大了。本文用一个真实本地 Node.js 项目，记录 BEYOND 3.2.4 从派发、执行、回传到验收的完整链路，以及失败时为什么不能把“原生 final 可读”直接当成已验收。

正文直接采用[中文首发长文](BEYOND-3.2.4中文首发长文.md)，但保留掘金代码块、流程图和安装命令，不复制 GitHub README 全文。

## 知乎文章 / 回答

问题式标题：

> 如何让 Codex 在多个任务完成后自动回到项目主线，而不是靠人不断询问？

开头：

> 我的答案不是“再写一个更长的提示词”。长期项目的问题是状态和责任没有正式落点：聊天记录能说明模型说过什么，却不等于项目当前主线、唯一执行者、正式证据和验收状态。BEYOND 的做法是把这些内容放回本地项目，再让 PM和Worker分别承担协调与交付责任。

知乎正文应先讲痛点和取舍，再介绍项目。项目链接放在第一次完整解释方案之后，不要首段堆链接。

## GitHub Discussion 首帖

标题：

> What breaks first when you run multiple Codex tasks on a real project?

正文：

> BEYOND 3.2.4 is now available. Instead of announcing another feature list, I would like to collect concrete failure modes from people using Codex Desktop on real local projects.
>
> Which problem costs you the most time?
>
> 1. a new task loses the current project line;
> 2. finished Workers do not return to the coordinating task;
> 3. design, development, testing, and operations require repeated manual continuation;
> 4. “tests passed,” “committed,” “released,” and “working in production” get mixed together;
> 5. parallel tasks overlap or close twice;
> 6. a paused task cannot reliably resume with the original owner.
>
> Please include your Codex host, whether the project is local or worktree-based, and the smallest reproducible task. Do not post credentials, private paths, or production data.
